## Method

Access date 2026-11-11. There was no new reading, search, run or measurement: this synthesis restates and weighs the 17 briefs above, which reached `main` on the dates shown (the date of the first commit that added each file). The Verdicts table was built from each brief's own `## Verdicts` lines by script: every hypothesis H1 to H27 has at least one such line, and the Briefs column lists exactly the briefs that gave one. I then read each verdict line in full and wrote the "What the briefs add" and Evidence columns by hand, keeping each figure as its brief states it and not rechecking it against a paper. Paper claims therefore carry the brief's own evidence label (abstract only, passages, full text); a reader reaches the paper one hop away through the brief.

Evidence column, as used here: measured means measured by this project for this question (only R16); literature means papers the briefs cite; docs means host or tool documentation, tool source or this repository's own records; design-only means R10 designed an experiment and nothing was run; none means no source for the central claim.

I read no file outside the repository, and I started no subagent. The synthesis also records the owner's decisions of 2026-11-11 (task source and experiment spend cap deferred, stack recommended, budget setting as a candidate requirement, and an auto mode recorded as candidate epic B9 with a candidate hypothesis); they are the owner's, not findings.

## Evidence and conflicts

- Measured: only R16 measured anything for this project. Ten scratch skills added 340 tokens in Claude Code 2.1.321 and 1,633 in pi 1.5.0 (same model; one run with skills for Claude Code; for pi two runs on one model and one on a second model, all giving the same figure), and Claude Code did not read a skill under `.agents/skills` in one headless run. The raw outputs were deleted with the scratch directory, so the totals cannot be re-audited [S16].
- Design only: R10 designed ten experiment protocols and a 50-row triage of candidate measurements drawn from 12 briefs, with sample-size limits (at 80 tasks only 15 to 21 point differences are detectable). Nothing was run, so every R10 verdict is literature-supported, not measured [S10].
- Everything else rests on literature and documentation the briefs read, much of it at abstract level only. R13 marks 20 of its own sources abstract only. R11's paper claims rest on abstracts except for passages of three papers, so H21 to H23 should be weighed that way. R15 read named passages of the full text of its papers S1 to S16, and every number in its verdicts comes from such a passage; the 13 papers it read only to the abstract or by title bear on no verdict. Numbers from abstract-level sources are unchecked against full text [S13][S11][S15][S16].
- Conflict (tier escalation): R9 recommends escalating on the first verified failure, by effort and then by tier, while R10 reads one study as showing that continuing a cheaper model's trajectory recovers less than half the gap and that every Claude escalation configuration cost more than starting with the stronger model, and it makes the stronger tier the baseline to beat; in that study the switches came at points fixed in advance, not after a verified failure, and the GPT results are mixed. R10's proposed default to test is to abandon the attempt and restart the stronger tier from the original task state; R9 marks the tier order as an inference [S9][S10].
- Conflict (prompt-level defences, H23 and H6): R11 cites a benchmark where prompt-level hardening cut attack success from 58.2% to 14.3%, while R13 cites work where no prompt-layer defence held across endpoints and advisory text was often ignored. These are different studies, so no single conclusion follows [S11][S13].
- Conflict (when to enforce, H6): R1 restates the hypothesis as evidence checks inside the workflow with hard blocks later or never, while R13 makes the evidence gate the first enforced rule, added after an observed failure. The first release here keeps the done gate because R14's ledger holds one live catch for it, which is the observed failure R13 asks for [S1][S13][S14].
- Conflict (handoff note, H26): the first release includes an engine-written handoff note, while R12 finds a raw trace beat notes on effort in the one handoff study and keeps only the narrower claim that a bounded, verified note is a reasonable trade against a raw trace, not better than one [S12].
- Conflict (context files): one study finds context files do not generally raise task success and add over 20% cost, another finds lower median runtime and fewer output tokens with an AGENTS.md, and a controlled ablation finds no measurable change in correctness; the advice to keep AGENTS.md short rests on that mixed evidence [S8][S12][S16].
- Conflict (seed spec against the evidence): SEED-SPEC goal 3 makes parallel work a design goal, while R6 finds the supported default is sequential writing, with read-heavy work parallelized first and a mechanical overlap check before any parallel write [S6].
- Extension, not a conflict: R5 proposed a command-line engine called from hooks; R13 confirms that shape and adds that Claude Code and Codex also accept HTTP or MCP-tool hooks and treats a server as a later option once the per-call cost is measured [S5][S13].
- Gap no brief closes: the cost per tool call of a CLI engine. The only per-call figure found is a median paired hook overhead of about 85 ms in one abstract-only paper on local agent authorization, with no CLI-against-server comparison and nothing for a Node CLI [S13].
- Gap: no brief holds a coding-agent comparison of ceremony levels, of gate retirement, or of a handoff note against a live transcript on repository work (unsourced).

## Minimum useful first release

The minimum useful first release is the smallest build that makes one claim true and checkable: an agent's "done" is a declared command that an engine ran after the last edit, in a loop two hosts can call, with state in plain files and a log that shows what the gate caught. This is the agent's synthesis of the briefs, not a finding: no brief tests that this combination is useful (unsourced). In scope: one engine command-line program with the evidence gate, the terminal states and a one-shot, owner-authored, logged escape hatch; plain-file state and a handoff note written only by the engine; thin adapters, Claude Code first because its command hooks call the CLI directly, and pi in the same release if its TypeScript wrapper stays small (goal 1 of SEED-SPEC names both; this is a judgment, unsourced); a small SKILL.md catalog with one entry command per host; and a per-repository budget setting with cost always shown (the owner's candidate requirement; its defaults are untested). Out of scope for the first release: parallel writing, routing beyond named tiers, a learned router, a database, a compaction implementation, retirement logic for gates, cross-host dispatch and the auto mode (B9).

The other three SEED-SPEC section 9 questions:

- Engine form: a command-line program that reads JSON on stdin and answers with an exit code. Claude Code, Codex CLI and Gemini CLI call it from a hook; pi and opencode wrap it in a small TypeScript module. One package that is also an importable library; an HTTP or MCP server is a later option once the per-call cost is measured [S5][S13].
- Shared state: plain repository files written only by the engine through a format-preserving writer, with both hosts calling the engine, because this repository's own helpers rewrote state files in a different style twice. No database-backed tracker without a failure that plain files cause. The two-host claim is untested [S12][S13][S6].
- Skills and engine: the engine enforces only what is mechanical and cheap to check, namely the done gate, protected paths and destructive commands through a hook (not deny rules), ceilings the engine counts, and the single-writer state; everything else (workflow steps, planning, review) is advisory skills, because advisory text helped in one setup and was ignored in others. The done gate is enforced from the first release because R14's ledger holds one live catch for it, which is the observed failure R13 asks for before a gate. Ceremony levels at first (the agent's judgment): one trivial path and one full path, since no source measures risk-scaled ceremony [S13][S14][S11][S15][S1][S3].
- Parallelism: none in the first release. The supported default is sequential writing, with read-heavy work (review, exploration, test runs) parallelized first. When parallel writing comes, add a mechanical file-overlap check, engine-created worktrees and an integrator that re-runs the declared verify commands on the merged tree [S6].

Recommended stack (the owner accepted this recommendation on 2026-11-11): TypeScript on Node, as one package that is both the command-line program and a library. The project's provisional SEED-SPEC (section 5; a project document, not a research source) already sketches a TypeScript engine, the hooks of pi and opencode are in-process TypeScript, and one language then serves the engine, the library and the wrappers [S5][S13]. It is to be confirmed or changed at the e04 checkpoint, and the per-call startup cost of a Node CLI is unmeasured [S13].

Deferred owner decisions (2026-11-11). Task source: no repository is named and no outside path is read. The leading source is the first build epic's own tasks; for the first experiment (E1, the done gate against seeded false successes) a small fixture repository inside weftwork with planted defects is proposed, which is the agent's inference, since R10 marks task sources unsourced [S10]. Spend cap: the owner sets a hard dollar cap per experiment when one is about to run and starts with a small pilot; no figure is set now [S10]. The product's budget setting is recorded under Implications.

## Implications for weftwork

These are inputs for the v1 spec. Each is a proposal with its source; none is a tested result.

- Input for the v1 spec, the first enforced rule: the evidence gate. The engine runs the declared command after the last edit and holds the done verdict in a place the worker cannot write. A Stop-hook gate is never the only guard in Claude Code, because there it fails open when it cannot start. An error or an exhausted budget never counts as done. Try each gate against a held-out failing case, since a gate that cannot fail is vacuous [S13][S15][S14][S7].
- Escape hatch and ledger: owner-authored, one-shot, logged with counts, and the agent may not propose allow-rules. Build no retirement logic until there are overrides to count, and count false alarms as well as overrides [S14][S13].
- Terminal states: done (verified), blocked, stalled, exhausted and killed, each logged with its counters. Key any no-progress breaker to evidence that can move, and start thresholds as tunable defaults, not findings [S15].
- Engine and adapters: a command-line program that reads JSON on stdin and answers with an exit code, with a TypeScript wrapper for pi and opencode. The adapter sets the host's fail-closed option, registers the hook, gets it trusted where the host asks, and checks that it is live; the engine fails loudly when its own hook is missing, because R2 found a guard hook that was not registered in this repository's settings [S5][S13][S2].
- Stack (owner accepted the recommendation, 2026-11-11): TypeScript on Node, one package that is a CLI and a library, to be confirmed or changed at the e04 checkpoint. Write the code-style and test sections of CONVENTIONS.md after the stack choice, as a short list of commands and links to tool configuration, not prose rules [S5][S13][S8].
- State and handoff: plain repository files with a small documented field set, written by one format-preserving tool. Write the handoff for a session with no memory and verify it against the repository at resume. No database tracker in the first release [S12][S13][S2].
- Skills: SKILL.md directories, a small catalog and one entry command per host, with a router if the catalog grows. Place skills where each host reads them (`.agents/skills` for pi, `.claude/skills` for Claude Code, from one provisional run), write descriptions as routing metadata and check the catalog for near-duplicate skills [S16][S1][S3].
- Ceremony: a trivial path and a full path, with a declared risk field only if it is used; there is no measured rule for scaling [S1][S2][S3][S13].
- Budget setting (an owner decision of 2026-11-11 recorded as a candidate requirement, and the agent's suggestion): a per-repository setting in a plain file, a user-level global default that a repository overrides, stopping a run on a budget off by default, and counting and showing cost always on. The engine counts the ceilings, covers the whole loop and keeps a reserve so that a hard stop leaves a handover note [S15][S9].
- Security baseline: treat all repository content, including AGENTS.md and skill files, as untrusted. Compose the host's sandbox and do not build one. Keep a portable protected-paths list, enforce it with a hook or sandbox and not deny rules, start autonomous runs from a clean branch with a commit before risky steps, and keep credentials out of the agent's environment [S11].
- Context: do not build compaction. Configure the host's trigger and re-inject what must survive through the host's hook points. Keep AGENTS.md short and about non-standard practice, and lint its commands in Preflight as a candidate story [S12][S8].
- Model routing: named tiers (light, standard, heavy) and an effort level per role, resolved to a host alias in each adapter, every cell unmeasured until tested. Escalate by effort first on a verified failure, build no learned router for the first release, and record cache-read tokens per dispatch [S9][S10].
- Measurement harness and task source: record one row per run (arm, task, model id, host version, token counts by type, price-table date, declared-command result, oracle result, rule breaks, escalations) in a plain file, and start with the cheap measurements. The task source is deferred; see the first-release section for the options [S10].
- Review: keep the evidence gate separate from review, make the reviewer's model a setting, prefer a reviewer that can run a focused command, cap review rounds and hand over at the cap. Mutation testing in a review round is a candidate experiment, not a gate [S7][S2].
- Auto mode (an owner request of 2026-11-11, recorded as a candidate requirement): a toggle that takes a story to an open pull request with a decider subagent answering reversible questions. It builds on the decider option in SEED-SPEC goal 4; the story-to-pull-request scope is the owner's request. Escalate on fixed rules, not on the model's own sense of when to ask, because models judge that poorly; do not copy GSD's auto-select of the first option, whose premise is untested. Build it after the done gate, the ceilings and the security baseline, since an autonomous loop without them is the false-success case R15 describes [S7][S15][S11].
- Parallel work, after the first release: a mechanical file-overlap check, engine-created worktrees, an integrator that re-runs the declared verify commands on the merged tree, and single-writer state [S6].

## Candidate build epics

These are candidates for the first release. They are sliced into stories with `slice-tasks` at the e04 checkpoint, as for e05. The existing e05 epic (repository and environment setup) is not repeated here; B1 depends on it for the repository, CI and environment. Each candidate names the briefs that justify it, and none is estimated.

- B1 (engine core and done gate): a TypeScript command-line program that reads JSON on stdin and answers with an exit code, with the evidence gate, the terminal states, a counts ledger and the one-shot owner-authored escape hatch [S5][S13][S14][S15]; depends on e05.
- B2 (state and handoff): plain-file workflow state written only by the engine through a format-preserving writer, and the handoff note checked at resume [S12][S13][S2]; depends on B1.
- B3 (host adapters): a Claude Code command hook and, if it stays small, a pi TypeScript wrapper, which set fail-closed behaviour, register and trust the hook and check that it is live [S5][S13]; depends on B1.
- B4 (skills and entry command): a small SKILL.md catalog with one entry command per host, placed where each host reads it, with descriptions written as routing metadata [S16][S1][S3]; depends on B3, which installs the skills on each host.
- B5 (budget and ceilings): the per-repository budget setting with a user-level default, engine-counted ceilings over the whole loop, a handover reserve and always-on cost reporting [S15][S9]; depends on B1.
- B6 (security baseline): the protected-paths list, the untrusted-content rule for the engine and its skills, a per-host report of the boundary the host gives, and credential-scrubbing guidance [S11]; depends on B3.
- B7 (measurement harness and first experiment): the per-run row file, a fixture repository inside weftwork with planted defects and a held-out oracle, and the done gate against seeded false successes with the cheap measurements first [S10]; depends on B1 and B3, on the owner setting a spend cap and on the owner confirming the task source.
- B8 (parallel work, after the first release): a mechanical file-overlap check, engine-created worktrees and an integrator that re-runs the declared verify commands on the merged tree [S6]; depends on B1 and B2.
- B9 (auto mode, after the first release; owner request, 2026-11-11): an owner toggle that runs one story from plan to an open pull request without stopping for routine questions. A decider subagent answers reversible questions and logs each answer; rule-based triggers (an irreversible or destructive action, a security-sensitive action, an effect outside the worktree, a plan too broken to follow) and push, merge, spend past the budget and any outside path still go to the owner. The run ends only on the engine's done verdict or a terminal state, inside the host's sandbox, from a clean branch [S7][S15][S11][S10]; depends on B1, B2, B3, B5 and B6, and measuring its candidate hypothesis depends on B7.

## Earns its place vs ceremony

- Earns its place: the evidence gate, a declared command the engine ran after the last edit, with the oracle caveat. It is the only gate with a live catch in the legacy ledger and it matches the literature on external feedback over self-report. R7 rates a declared command as the done signal unproven with a positive signal, so this rests on R14's one live catch, not on a measured effect [S14][S4][S7].
- Earns its place: a one-shot, owner-authored, logged escape hatch with counts. It is cheap and needed to measure any gate [S14][S13].
- Earns its place: a mechanical file-overlap check before parallel dispatch, and re-running verify commands on the merged result; it is cheap and deterministic, though no source measures that a pre-dispatch overlap check lowers conflicts [S6].
- Earns its place: plain-file state with one format-preserving writer, because tools rewriting a file's style caused real failures in this repository [S13][S12].
- Earns its place: a SKILL.md catalog with one entry command per host, kept small. The format is shared and the listing cost measured was small at ten skills; the catalog size is what needs a limit [S16][S3].
- Earns its place: the host's own sandbox, composed and reported per host, with a hook or sandbox, not deny rules, for protected paths [S11].
- Ceremony until measured: ceremony dials and risk tiers beyond a trivial path and a full path; no source compares risk-scaled with fixed ceremony [S13][S14][S10].
- Ceremony: gate retirement logic and ledger rotation with an archive chain, since there are no overrides to count [S14][S13].
- Ceremony: hashed managed blocks for generated files; no host documents them and no observed failure is an overwrite [S8][S13].
- Ceremony until proven: typed message envelopes, agent teams that message each other, lock files for stories and a database tracker for coordination [S6].
- Ceremony until proven: mutation testing as a gate in an agent review round, and two blind reviewers with an AND-gate; no source measures either [S7].
- Not for the first release: a learned router or planner-model sizing step, a learned early-stop predictor and a new compaction implementation [S9][S15][S12].
- Negative signal: very large catalogs (80 skills in bigpowers, 54 commands in GSD) needed routers to cope, and no measurement shows they help [S1][S2].
- Prose "HARD GATE" instructions as the only enforcement are a request, not a gate [S2][S13].

## Open questions

- Task source (deferred by the owner, 2026-11-11): which repository supplies the tasks for the first experiment. The leading option is a fixture repository inside weftwork, which needs no outside path; any outside path must be named again by the owner [S10].
- Spend cap (deferred by the owner, 2026-11-11): the owner sets a hard dollar cap per experiment when one is about to run. Until the task source and the cap are decided, no experiment can start [S10].
- Stack commitment: the e04 checkpoint confirms or changes the TypeScript on Node recommendation. The per-call cost of a Node CLI hook is unmeasured, and the hook overhead of about 85 ms found by R13 is for another system [S13].
- R7 remainder: the peer-review venues of its 32 papers, full texts of its S2, S8, S12, S13 and S14, and a wider search for mutants in an agent review round and for reversibility classes limiting auto-answers, which its queries did not find. Its other four questions (different-family reviewer, fresh context, round cost, Ask-F1) are now R10's protocols E7 to E10 [S7][S10].
- Candidate hypothesis from R10, not added to planning-context.yaml: a workflow claim is a finding only when it is a paired difference with an interval against a held-out oracle the agent never saw. The e04 checkpoint decides whether to add it [S10].
- Candidate hypothesis from R15, not added to planning-context.yaml: an autonomous loop ends only on conditions the harness or engine enforces (a verified gate verdict, a counted ceiling over the whole loop, a progress-based breaker on evidence that can move), never on the model's own judgment alone. H1 covers the first part and H15 the ceilings; neither covers the breaker [S15].
- Candidate hypothesis from the owner (2026-11-11), not added to planning-context.yaml: an auto mode with rule-based escalation takes a story to an open pull request with fewer owner interruptions, without lowering the accepted-task rate. R10's harness could measure it by counting interruptions alongside pass rate and scoring the decider with Ask-F1; no brief tests it [S10][S7].
- Reading routed and not done: four R11 papers (not read, by owner decision on 2026-11-11), and the R13 and R15 papers read only in part (also routed to R16 and not done). R13's abstract-only numbers are unchecked against full text; R15's numbers come from full-text passages but were not checked against each whole paper [S16][S13][S15].
- Candidate measurements from R13: whether a missing, erroring or untrusted hook blocks a call on each host, how many overrides and false alarms a logged hatch collects over a longer window, whether risk-scaled ceremony matches fixed ceremony, and which protected-paths list weftwork requires when hosts disagree [S13].
- The budget defaults (stopping off, cost always shown) are untested, and no source tests defaults of this kind; R15 supports only that the engine counts its own ceilings [S15].
- Housekeeping, not research: archive `docs/SEED-SPEC.md` to `docs/archive/` when the v1 spec replaces it, and revisit the standing gate-trace waiver at the e04 checkpoint (project conventions, unsourced).
