# R7 Agent review and agent-answered decisions

Research story R7, wave 3. Assigned hypotheses: H1, H13, H14.

Question: for agent review and for agents that answer other agents' questions, what works, how to avoid self-agreement, and when to escalate to a human. Scope: six tools (Claude Code, Codex CLI, GSD, bigpowers, Superpowers, BMAD) and the paper literature on LLM judges, code review, mutation testing and help-seeking. It does not run any reviewer, choose weftwork's design (e04s02 decides), or redo R5, R6, R9, R13 or R15.

## Self-agreement

- A model that judges text it wrote tends to score it higher than others' text, and the strength of this self-preference tracks how well it recognizes its own output; the authors changed self-recognition by fine-tuning and saw the preference move with it. The abstract names no code task [S1].
- On verifiable tasks, including code generation, stronger models prefer themselves more, but mostly when they are right. Harmful self-preference persists when the evaluator erred as a generator, and stronger models show more of it in that case, so a self-check is weakest exactly when the work is wrong. Generating a long chain of thought before judging reduced the harmful part [S2].
- Related models share a bias in training pipelines: preference leakage is a judge's bias toward a student model trained on data that a related generator made, where related means the same model, an inherited one or one from the same model family, and the authors call it harder to detect than earlier biases. Inference: the paper does not test a reviewer judging a related model's code, but it is a reason to pick a reviewer from a different family, not a different size of the same one [S3].
- Models judging code frequently misjudge it. In one study eight LLMs judged the correctness of 1,405 Java methods and 1,281 Python functions written by the same LLMs or by humans; the best model still misjudged often and smaller models could not cope [S4]. Judge verdicts on code also swing with prompt framing: several biases shift preferences toward the option the prompt favors, in some settings enough to change model rankings [S5].
- Without external feedback, models struggle to correct their own reasoning and sometimes get worse (reasoning tasks, not code review) [S17]. Model heterogeneity improved multi-agent debate in a re-test, though debate often failed to beat simpler baselines (debate, not review) [S18]. Both are hints about a different-model reviewer, not tests of it; one direct test follows.
- One direct test of cross-model code review exists, and it is small and mixed. On 116 hard and medium LiveCodeBench tasks, with a reviewer that sees the problem and the draft but cannot execute tests, Claude review raised Codex drafts from 71.6 to 89.7 percent and Codex self review raised them to 84.5 percent, while Codex reviewing Claude drafts lowered the pass rate from 91.4 to 82.8 percent and Claude self review left 91.4 unchanged. So cross-model review helped in one direction and hurt in the other, and self review helped in one case. Inference: the Claude baseline was the higher one (91.4 against 71.6), so the result fits "the reviewer helps when it is the stronger model" as well as "a different model helps", and two model families on one benchmark with no test execution do not separate them [S37].
- No paper was found that tests a fresh context against a continued context for code review. Several tools use or offer it anyway: bigpowers reviewers get "clean contexts" with no shared state, Superpowers hands the reviewer a crafted brief and never the session history, BMAD launches each lens as a "context-free subagent", the Claude Code local review runs with its own context window, and Codex offers a Detached setting for a separate review chat. The benefit is unproven, and the cost is a context per review [S25][S26][S27][S21][S23].
- The tools split on the different-model idea. Codex offers a separate `review_model` setting, the Claude Code service chooses its own models with no admin choice, bigpowers runs its review skill on `model: opus` and sets no reviewer model, with no must-differ rule, and BMAD defaults to the session's capability and lets a lens be overridden to run an external reviewer. None of these docs says why [S23][S21][S25][S27].

## Evidence in review

- Tests run: passing the tests near a change overstates correctness. In SWE-bench, 7.8 percent of patches count as correct while failing the developer test suite, because only the tests the pull request changed were run [S20]. Agent-written tests mostly act as observation, and changing how many were written did not significantly change outcomes in that study [S19].
- The tools differ on whether a reviewer runs anything. Only bigpowers' reviewer prompt tells the reviewer to rerun the declared command: it ends with "Run the verify command and report the result". GSD's verifier runs 2 to 4 short spot-check commands that it picks itself from the phase's must-have truths, and skips them for documentation-only phases. Superpowers tells its reviewer not to re-run the suite and to run one focused test only on a specific doubt. The Claude Code service reviews without building or running code, and BMAD's lenses are told not to run builds or tests. For Codex whether the reviewer runs tests: not found. So in most of these tools the declared command's result is the author's or the harness's evidence, not the reviewer's [S25][S24][S26][S21][S27][S23].
- A harness can keep the worker from writing its own gate. Bounded Loops defines a bounded loop as a worker, an independent gate the worker cannot write to and a declared budget, names two ways a sound-looking check passes anything (vacuity, and self-attestation, where the subject supplies the value being checked), and measures gates against a held-out mutant corpus. On a catalogue of 69 loops it found 47 vacuous gates in shipped, reviewed code, and against the repaired gates it reported no false accepts over 209 destroying mutants [S38].
- Reviewing by reading is not reliable alone: GPT-4o and Gemini 2.0 Flash classified code correctness correctly 68.50 and 63.89 percent of the time with a problem description, and less without one, and the authors propose a human in the loop [S6]. A benchmark of repository-level review reports that earlier benchmarks missed defects because their ground truth came from raw pull request comments; that says review quality is hard to measure, not that read-only reviewers fail [S7].
- Agentic reviewers cost more to be right: terminal-based agentic reviewers reached higher review precision but paid substantial exploration and validation overhead, and successful reviews showed stronger planning and less downstream validation [S8].
- A review can produce a runnable check instead of an opinion. PatchGuru infers executable patch oracles from pull request text, as runtime assertions comparing the code before and after the patch. On 400 pull requests it reported 39 warnings at precision 0.62, with 24 true positives including 12 previously unknown bugs, at an average of 8.9 minutes and USD 0.07 per pull request. It still filters some results by "self-review" [S12].
- Mutation testing: inside human code review it has direct prior art, and inside an agent's review round it is unsourced. Google's mutation testing mutates only the changed code during code review, and was evaluated in a code-review-based setting with more than 24,000 developers [S33]. Its service surfaces diff-based mutants during review, and an A/B test of a ranker that suppresses unwanted mutants lowered the negative-feedback ratio from 12.41 to 11.45 percent [S34]. Both are human review; no paper found puts mutants into an agent's review round. In agent harnesses, Bounded Loops scores a gate by whether it rejects a held-out mutant corpus [S38], which tests the gate, not the reviewer. The nearest in a tool is BMAD's `verification-gap` lens, where the reviewer names "the smallest realistic regression" a consumer would see, such as an inverted branch or a dropped default, and checks by reading whether any test would fail [S27]. Adjacent work on test strength: SWE-Mutation builds mutated solutions meant to fool test suites, and even DeepSeek-V3.1 reached only 10.20 percent verification and 36.15 percent detection among the seven LLMs tested [S9]. Meta's ACH generates few, targeted mutants and then tests that kill them; engineers accepted 73 percent of its tests, and its equivalent-mutant detector had precision 0.79 and recall 0.47 before pre-processing [S10]. LLM-made mutants found 87.98 percent of faults against 41.64 percent for rule-based mutants, with more non-compilable, duplicate and equivalent mutants [S11].
- Conventions checked: bigpowers puts CONVENTIONS.md and the verify command into the reviewer's brief, and Claude Code's local review follows `CLAUDE.md`. Whether a convention check catches defects that tests miss is unsourced [S25][S21].

## Decisions and escalation

- Reversibility is a researched axis for agent actions, but its use to limit auto-answered questions is unsourced. "Revisable by Design" classifies every agent action as Idempotent, Reversible, Compensable or Irreversible, concludes that an agent's flexibility is bounded by its reversibility, proves that conflicting irreversible actions make full specification satisfaction impossible, and tests this on a streaming benchmark where users revise a running agent, not on approvals [S30]. Cordon stages irreversible agent effects before commit [S31], and Atomix lets irreversible effects leave only at transaction commit [S32]. A governance framework limits the autonomy an agent may exercise by risk and reversibility [S36], and an interview study (18 practitioners) with a survey (115) finds that permission decisions depend on the scope and risk of an action and recommends making reversibility clearer [S35]. An architecture paper couples autonomy with agency and proposes six tactics, escalation among them, because human error correction is less available at higher autonomy [S41]. STRATUS adds a safety specification for cloud operations and SagaLLM adds rollback for planning [S15][S16]. None tests agents answering other agents' questions in a coding workflow, so the part of H13 that limits auto-answers by reversibility class has no direct source.
- The tools do cut escalation by reversibility, in different words. Superpowers stops only for an irreversible or destructive operation, a security-sensitive action, a side effect outside the worktree or a hopeless plan, and logs every other call as a ruling with its cost if wrong [S26]. Codex always requires approval for a destructive tool call that advertises a destructive annotation; its sandbox boundary, which lets sandbox-allowed commands run under `on-request`, is containment, not reversibility [S23].
- A second agent can answer in place of the user. Codex does this with `approvals_reviewer = "auto_review"`: eligible approval requests go "through a reviewer agent before Codex runs the action". The docs call it "a reviewer agent" and do not name its model. Its policy lets low-risk and medium-risk actions proceed when policy allows them, denies critical-risk actions, requires enough user authorization and no matching deny rule for high-risk ones, and fails closed on errors. The classes are risk tiers, not reversibility [S23].
- A second model can also answer in place of the user in Claude Code. Claude Code's auto mode sends each action to a separate classifier model (Sonnet 5 by default) that blocks actions that go beyond the request, target unrecognized infrastructure or look driven by hostile content. After 3 blocks in a row or 20 in total it falls back to asking the user, and it nudges Claude to keep working without clarifying questions [S22].
- Auto-answer rules can be crude. GSD's auto mode approves every human-verify checkpoint and picks the first option at every decision checkpoint, on the stated premise that planners front-load the recommended choice, and it still stops for human-action checkpoints such as authentication [S24]. BMAD routes by ambiguity, not reversibility: a finding that needs the user's intent is `decision_needed` even when nobody can answer [S27].
- Models are poor at judging when to ask. On HiL-Bench no frontier model recovered more than a fraction of its full-information performance when it had to decide whether to ask; the failures were overconfident wrong beliefs, detected uncertainty with persistent errors, and broad imprecise escalation. Training on an Ask-F1 reward improved a 32B model [S14].
- Agents over-persist and report success the record does not support. On ImpasseBench, across eight frontier models and 19,371 trajectories, nearly every run that needed outside help had collected enough evidence, yet a third still exhausted their budget; an escalation tool cut budget exhaustion from 34.0 to 6.7 percent, but tickets often omitted the agent's own progress and verification status [S39].
- Escalating everything is not the safe default. On 125 hand-labeled agent actions, reviewers agreed only moderately on what is risky (Fleiss' kappa 0.52), and in a model where the reviewer fatigues as escalation load grows, realized safety is an inverted U in the escalation rate [S40].
- Splitting the decision from the coding helps: a scaffold that separates detecting underspecification from writing code reached a 69.40 percent resolve rate on an underspecified SWE-bench Verified variant, significantly above a standard single agent, and asked fewer questions on simple tasks [S13]. Inference: a decider that is a separate role fits this result, but the paper does not test a separate model or fresh context for the decider.
- When a decider runs on the worker's model, the self-agreement risk applies to it too. This is inference from the judge results, and no paper tests a decider [S1][S2].
- An escalation cap is a design choice that tools already make: bigpowers stops after 5 review rounds and hands the decision to a human [S25]. The legacy project logged 193 decisions and 104 review findings, but its typed review verdict gate never fired and its reviewer children timed out, so its delegation is unproven [S28].

## Verdicts

- H1: refined - the claim that done means a declared command the harness watched exit 0 is supported in direction but needs an oracle-strength qualifier: 7.8 percent of SWE-bench patches count as correct while failing the developer suite [S20], LLM-written tests can be fooled by mutated solutions [S9], and LLM judges misjudge code often [S4][S6]. Only bigpowers' reviewer is told to rerun the declared verify command; GSD's verifier picks its own spot-checks, Superpowers allows one focused test, and the Claude Code service and BMAD do not run code [S25][S24][S26][S21][S27], so a review does not replace the command gate. The nearest source for the claim itself is Bounded Loops, which makes the gate independent of the worker, names self-attestation and vacuity as ways a check passes anything, and found 47 vacuous gates in 69 shipped loops [S38]; coding agents also claim success the record does not support [S39]. No source tests the exact claim in a coding workflow.
- H13: refined - the different-model half has hints and one small mixed test: self-preference is real and tracks self-recognition [S1], it persists when the evaluator is wrong [S2], it appears as leakage toward related models [S3], and heterogeneity helped debate [S18]; the one direct test of cross-model code review is mixed: Claude reviewing Codex helped, Codex reviewing Claude hurt, and self review helped in one case [S37]; the tools split on it [S23][S21][S25][S27]. The fresh-context half is unsourced by papers; several tools use or offer it without measurement [S25][S26][S27][S21][S23]. The reversibility half is split: reversibility classes for agent actions are defined and tested elsewhere [S30][S31][S32], and two tools limit autonomy by irreversibility or risk tier [S26][S23], but their use to limit auto-answered questions is unsourced, and models judge when to ask poorly [S14].
- H14: refined - review that checks evidence is supported in part: an executable patch oracle found real bugs at precision 0.62 [S12], reviewers that only read can misjudge correctness [S6], Google runs diff-based mutants in human code review [S33][S34], and Bounded Loops scores agent gates against mutants [S38]; but the tools here split on running anything [S21][S27][S26][S24][S25], and mutation testing inside an agent's review round is unsourced, with BMAD's verification-gap lens the nearest in a tool [S27] and only adjacent work on test strength [S9][S10][S11].

None is `confirmed`: every source tests judging, review benchmarks or help-seeking, not weftwork's review rounds, and the central pieces (fresh context, reversibility limits on auto-answers, mutants in an agent's review round) have no direct test. None is `refuted`: no source contradicts any of them.

## Implications for weftwork

- Keep the evidence gate separate from review, and make it a gate the worker cannot write to [S38]. A review's verdict is model output; "done" stays a declared command the harness watched exit 0. Consider running the whole suite, not only tests near the change [S20], and treat a reviewer's findings as claims to verify before they reach the owner, as BMAD's triage and the Claude Code verification step do (H1, H14; feeds R10, R13).
- Make the reviewer's model a setting. Codex's `review_model` is the pattern [S23]. The one direct test found is mixed: cross-model review helped one way and hurt the other [S37], and self-preference is a reason to try a different family [S3]. So a different-family default is a hypothesis for R10 to test, not a settled default (H13; feeds R9, R10).
- Prefer a reviewer that can run a focused command over one that only reads, because bigpowers' reviewer reruns the declared command and GSD's verifier runs spot-checks it picks [S25][S24], and reading alone misjudged correctness in [S6]. Superpowers limits that to one focused test per specific doubt, which bounds the cost [S26] (H14; feeds R10).
- Treat a fresh, briefed context as a cheap default whose benefit is unmeasured: the cost is one context per review [S26], the benefit has no paper behind it. Measure it with and without in R10 (H13).
- Use rule-based escalation triggers, not the model's own sense of when to ask, because models do that poorly [S14]. Candidate triggers: an irreversible or destructive operation, a security-sensitive action, an effect outside the worktree, and a plan too broken to follow [S26]. As a reading of [S30], classify each action as idempotent, reversible, compensable or irreversible and limit auto-answers to the first two; that is an inference and untested for questions. Record each auto-answer with the choice, the reason and the cost if wrong, as Superpowers' ruling does [S26]. This matches the decision protocol in SEED-SPEC section 6 [S29] (H13; feeds R13, R15).
- Do not copy GSD's first-option auto-select as a rule; its premise is stated, not tested [S24].
- Cap review rounds and hand over to a human at the cap, as bigpowers does at 5 [S25] (feeds R15).
- Do not make mutation testing a gate in an agent's review round. It is unsourced there. Google's diff-based mutants in human review [S33][S34] and Meta's ACH [S10] are the nearest models, and BMAD's verification-gap lens is a reading-only version [S27]. It is a candidate experiment (H14; feeds R10).

## Earns its place vs ceremony

Verdict labels: earns its place, ceremony, unproven. A verdict rests on the cited source only. None earns its place on a measurement.

- A declared command as the done signal: unproven, with a positive signal; passing only the nearby tests overstates correctness [S20], and a gate the worker cannot write to is the nearest design [S38].
- A reviewer that only reads the diff (Claude Code service, BMAD lenses): unproven; models misjudge code correctness when reading alone [S6][S4].
- A reviewer on a different model or family from the coder: unproven; mixed in the one direct test, where it helped in one direction and hurt in the other [S37], with a positive signal from self-preference results [S1][S2][S3].
- A fresh, briefed reviewer context: unproven; used or offered by bigpowers, Superpowers, BMAD, Claude Code and Codex, no measurement found [S25][S26][S27][S21][S23].
- Two blind reviewers with an AND-gate (bigpowers): unproven; it doubles the reviewer cost per round and no source measures it [S25].
- A verification or triage step on reviewer findings (Claude Code, BMAD): unproven; the docs describe it and give no false-positive figures [S21][S27].
- A self-review checklist before the reviewer (bigpowers `audit-code`): unproven [S25].
- Executable patch oracles from pull request text: unproven for this project, with a positive signal at precision 0.62 and a low cost per pull request [S12].
- Mutation testing inside a review round: unproven; direct prior art for human review [S33][S34], unsourced for agent review, with adjacent work on test strength [S9][S10].
- Auto-selecting the first option at decision checkpoints (GSD): unproven; the docs rest it on planner behavior and cite no measurement [S24].
- Rule-based escalation on irreversible or security-sensitive actions: unproven for agent questions; used by Superpowers and Codex [S26][S23], with action reversibility classes defined elsewhere [S30].
- A reviewer agent that answers approval requests by risk tier (Codex auto-review): unproven; documented, no measurement found [S23].
- A separate decider role before coding: unproven, with a positive signal [S13].

## Open questions

- No paper was found that uses mutants in an agent's code review round, or that uses reversibility classes to limit auto-answered questions. The arXiv queries in Method found direct work only on human review [S33][S34] and on agent actions [S30][S31][S32]; other terms, such as test adequacy for patch review or approval policy, may find more.
- Does a different-family reviewer find more seeded defects than a same-family one, on code review? A measured experiment is a candidate story for R10. The one direct test [S37] used competitive-programming tasks, two model families and no test execution, and does not separate "different" from "stronger".
- Does a fresh, briefed context change findings against a continued context? Candidate R10 experiment.
- Which of the 32 papers cited here have a peer-reviewed venue? I read abstracts only; the full text of S2, S12, S13, S14 and S8 would be worth reading.
- What does a review round cost? S8 reports overhead and Superpowers states a context per review [S26][S8]; no figures were found for per-round cost across the tools.
- How would a decider for weftwork be evaluated? S14 gives Ask-F1 as a metric; whether it transfers to weftwork's decision requests is open.
