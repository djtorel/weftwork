## Method

## Skill listing cost

Result, for the same ten skills, measured as the difference in input tokens on the first request. Method: usage from each host's own output, a run with the skills minus a run without, same model (`claude-haiku-5-5`), same prompt.

| Host and version | Without skills | With ten skills | Added by ten skills | Per skill |
| --- | --- | --- | --- | --- |
| Claude Code 2.1.321 | 32,161 tokens | 32,501 tokens | 340 tokens | 34 tokens |
| pi 1.5.0 | 2,456 tokens | 4,089 tokens | 1,633 tokens | 163 tokens |

- Claude Code 2.1.321: a second baseline run (the `.agents/skills` run below, which loaded no scratch skill) gave 32,159 tokens, 2 below the first, so the two baselines differ by 2 tokens on a total of 32,000. They ran in different directories, so this is not a repeat: repeat noise for Claude Code was not measured, and the 340-token figure comes from a single run with skills. That second baseline is the same run used below to show `.agents/skills` was not read, so the independent evidence for "not read" is the init skill list, not this token total. The added 340 tokens against the 1,029 characters of names and descriptions is 3.0 characters per token; I did not capture the listing text, so how much of the 340 is format rather than text is not measured.
- pi 1.5.0: the baseline was 2,456 tokens in both runs, and the run with ten skills gave 4,089 tokens in both runs, so the figure repeated. With pi's default model `claude-opus-4-8` the same pair gave 2,458 and 4,091, the same 1,633 added. The skill section of pi's system prompt was 3,690 characters, and 1,630 of those are the `<location>` lines, one absolute path per skill. Each `<location>` line is 163 characters counting its newline, four-space indent and tags; the scratch path inside it is 137 characters because the scratchpad is deep, so the 163 tokens per skill is high for a shorter project path. The match between 163 tokens per skill (1,633 divided by ten) and 163 characters per line (1,630 divided by ten) is a coincidence of two separate totals. Without the path lines the section is 2,060 characters. I did not rerun with a shorter path, so how much of the gap is the path is not measured.
- The two hosts differ by 4.8 times on this set (1,633 against 340 tokens). The docs agree on the mechanism: pi "adds each skill's name, description, and path to the system prompt" [S1], and Claude Code loads "a listing of skill names and descriptions" and says every listed skill "adds to your context on every turn" [S2]. Claude Code also caps the listing at a character budget of 1% of the model's context window and drops descriptions, not names, when it overflows [S2]. I found no such cap in pi's skills page [S1].
- Limits of this measurement: one set of ten skills, so I have no slope. An extrapolation to 80 skills at Claude Code's 34 tokens each is about 2,700 tokens; that is an estimate, not a measurement. Claude Code's listing budget is 1% of the model's context window [S2]; I did not look up the window of the model used, the 20 built-in skills count against the budget too, and I did not read the debug log for the overflow warning [S2], so I do not know at what catalog size descriptions start to be dropped. The skills here have 100-character descriptions; real ones are longer.

## Verdicts

- H8: refined - R5's refinement stands and gains a measured half. The file format is portable: `SKILL.md` is read by every host R5 checked [S8], BMAD v7 installs the full BMad Method as skills through `npx skills add` and also offers a plugin marketplace route [S3], and pi reads `.agents/skills` [S1]. The location is not: in this brief's own run (one headless run, Claude Code 2.1.321, `--setting-sources project`, a directory outside a git repository) Claude Code did not read a skill under `.agents/skills`. The docs are silent on that path rather than saying it is unread [S2][S8], so this is a result of the run, not of the docs. Another study finds that when similar skills are co-installed, install location decides which one runs and listing order barely matters [S14]; that concerns conflicts between skills a host does read, not whether a host reads a path, so it is an analogy here, not support. R5's finding on the other half of H8, that beyond skills and instruction files each host has its own schema, is unchanged by R16 [S8]. A corpus of 138,133 public SKILL.md files finds that 91.8 percent have at least one defect, among them weak routing metadata, and that AI-marked skills show more safety and portability problems [S11]. The AGENTS.md half stays unsettled (these three studies are about whether context files help, not about portability, so they do not move the verdict): one study finds context files do not generally raise task success and add over 20 percent cost [S6], another finds lower median runtime and fewer output tokens [S7], and a controlled ablation of 288 runs finds context strategy does not measurably move correctness, bounded to 10 to 15 percentage points [S13]; all three are abstract-only and on different tasks.
- H10: refined - R3's refinement stands (small cores are common, one entry command is not) and gains two separate points. First, why keep a catalog small: one paper reports that pass rate falls by up to 21 percent when a library grows from a small helpful set to 202 skills, and that wrong skill selection, not the larger context, is the main cause; its context-overhead effect is "small and indistinguishable from zero" [S5]. A corpus study finds weak routing metadata is among the dominant defects and that skills with valid routing metadata are retrieved more reliably from startup descriptions [S11]. A study of co-installed similar skills in coding agents finds that nearly one in four installed skills is co-installed with one that does the same job, that the model picks between them by name and description alone, and that a similar skill takes one run in five from the installed skill [S14]. I read both abstracts only, and do not know whether S5's tasks are coding tasks. Second, what the listing costs: it is paid on every turn on both hosts [S1][S2], and for the same ten skills it was 340 tokens in Claude Code and 1,633 in pi, so the price differs by host and is small at ten skills. A deployment report says operational cost grows with library size and that progressive disclosure improves retrieval quality at a small latency cost [S10]. A benchmark of 31 web-development skills reports that injecting a target skill lowers mean Pass@2 by 1.3 to 4.2 percent and raises token cost by 72 to 394 percent (abstract only; that is injected skill content, not the listing) [S12]. S5 found no context-overhead effect on pass rate, and S12 found length effects for injected content (some models are "length-distracted"); neither tests a startup listing, so whether listing tokens affect quality is unmeasured, and the money and latency point is my inference from S10 and S12. For BMAD, v7 keeps `bmad-build` as its entry and replaces `bmad-help` with the `bmad` hub [S3]. I measured no catalog of 40 or 80 skills, so the slope is unknown.

## Implications for weftwork

- Ship skills as `SKILL.md` directories, and place them where each host reads them: `.agents/skills` for pi, and `.claude/skills` for Claude Code, since in this one-run test `.agents/skills` was not read there (provisional until repeated). Whether a symlink works is untested [S1][S2]. R5 reports that pi loads project `.agents/skills` only after the project is trusted [S8]. When similar skills are co-installed, install location decides which one runs, so check the catalog for near-duplicates [S14].
- Keep the catalog small and write each description as routing metadata: wrong skill selection, not the enlarged context, drives the pass-rate loss as a library grows [S5] (S5 does not test the listing itself), and weak routing metadata is among the dominant defects [S11]. The listing's token cost is real but a separate point: every listed skill costs tokens on every turn, and Claude Code drops descriptions past its budget, which hurts matching [S1][S2].
- Use the usage-difference method above to check a catalog's cost on each host before release; Claude Code also has `/doctor` and `/skill-doctor` for its own estimate [S2].
- Do not plan around BMAD v7 yet: it is a preview with a changing install path, and re-checking after release costs one page read [S3][S4].

## Earns its place vs ceremony

- A `SKILL.md` catalog: earns its place, because the format is shared and the listing cost measured here is small at ten skills; the catalog size is the part that needs a limit, for selection quality more than for tokens [S1][S2][S5].
- A second install location for Claude Code: earns its place, because in this one-run test (provisional) a skill kept only under `.agents/skills` was not loaded, and a symlink is untested; see the section on Claude Code and `.agents/skills`.
- Tracking BMAD v7 before release: ceremony. The release has not happened and the install path is stated to change [S3][S4].
- A listing-cost gate in this repository's own CI: not earned yet; one measurement of ten skills gives no threshold.
