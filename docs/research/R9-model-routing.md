# R9 Model routing and cost efficiency

Research story R9, wave 3. Assigned hypotheses: H15, H17, H18, H19, H20.

Question: how to size a task before dispatch (a planner model against deterministic signals), how model size and reasoning effort differ, whether to escalate on failure or pick the tier up front, which default tier fits each role, how to save tokens (cache hits, context per dispatch, per-subsystem dispatch, tool-definition cost with code-based tool access), what local models can do as a tier, and how budgets work. Scope: literature and host documentation only, by owner decision (2026-11-09). No measurement was run; every claim that needs one is labelled unproven and listed as a candidate story for R10 (e04s01).

## Task sizing

- A planner model can size a task before dispatch, or deterministic signals can. I found no study that compares a planner model's size estimate with deterministic signals for coding agents; this is unsourced beyond the studies below, and the queries are in Method.
- Deterministic static features predict how hard an issue-resolution task is: on CoderForge-Preview trajectories, a model using features of the task patch, the repository and the prompt predicted task outcome with AUC 0.863, driven mainly by patch fragmentation and repository scale, with prompt wording visible in the mid-band [S7]. The patch features come from the finished fix, which weftwork does not have before dispatch, so only the repository and prompt features are usable up front (an inference from the abstract) [S7].
- Code health is a proposed routing signal: Triage assigns each task to a light, standard or heavy tier from code health metrics, and derives two conditions for it to pay (the light-tier pass rate on healthy code must exceed the cost ratio between tiers, and code health must separate the tiers at p-hat 0.56 or more); its abstract reports no measured routing result [S1].
- Routing on a difficulty prediction pays only when two conditions hold. In document extraction, routing helped only when the cheaper model failed often enough and the failures were predictable from visible features, and a small labelled pilot predicted whether routing would work in the two cases where it was run first; this is not a coding task [S20].
- A model's own estimate of its cost is weak: eight frontier models asked to predict their token use before a task reached correlations of at most 0.39 and underestimated it, and difficulty rated by human experts aligned only weakly with real token cost [S8]. This is about tokens, not about success, and it does not test a planner that has read the repository (inference).
- Cost is noisy even for a fixed task: runs of the same task differed by up to 30 times in total tokens [S8], so any size estimate is a rough guide to cost.
- Existing size units can be mapped to tokens: ACEM maps use case, story and function points to token consumption, with its constants left symbolic and no data [S28]. weftwork already records BCPs and effort hours per story in `specs/execution-status.yaml`; whether BCPs predict token cost or failure is unmeasured and unsourced (a repository record, not a published source).

## Model size and reasoning effort

- Vendors treat reasoning effort as a setting apart from model size. Claude Code says effort controls adaptive reasoning, that a lower level is faster and cheaper, and that the scale is calibrated per model so one level name is not the same value across models; the five levels are low, medium, high, xhigh and max, and the default is medium on Opus 5.5, Sonnet 5.5 and Haiku 5.5 [S42]. The API page names medium as the default for Opus 5.5 and Haiku 5.5 and high for most other models, so the two pages give different defaults for Sonnet 5.5 [S49][S42].
- Hosts expose both knobs per dispatch. Codex subagents take a `model` and a `model_reasoning_effort`, and inherit the parent's when neither is set [S50]; pi has a thinking level and `thinkingBudgets` [S52]; opencode model variants carry `reasoningEffort` [S51]. The field table per host is R5's [S57].
- On reasoning tasks, the best use of test-time compute varies with prompt difficulty, so effort is a knob separate from model size (only as recorded in R4; not a coding task) [S38]. On software tasks, a trained 32B model with test-time scaling reached a 46% resolution rate on SWE-bench Verified, above much larger models, and models spent more tokens on harder problems [S39]; this is one trained system, not a choice between API tiers.
- The one coding task study I found is observational: 90 runs built the same application from one specification; capability tier dominated (frontier models near the ceiling, a low-cost local model at 24 to 37 of 42 points), and raising reasoning effort from high to xhigh lifted first-try perfect runs from 28% to 89% and cut corrective prompts about fivefold, for 9 to 29% more cost [S2]. It is one task, one author and not a controlled comparison.
- A counterfactual study of effort levels on proprietary and open-weight models finds that higher effort often fails on tasks lower effort solved, that on easy tasks every level solves the highest level costs up to 42 times the lowest, and that at higher effort agents verify and search more, which lengthens trajectories without necessarily changing the outcome [S3]. The abstract does not name its four benchmarks, so whether any of them is a coding task is unsourced until the full text is read.
- Choosing effort per step can save tokens: Ares predicts the lowest adequate level for each step and cut reasoning tokens by up to 52.7% against fixed high effort with minimal loss in success, on tool-use, deep-research and web tasks; none is a coding task [S23].
- Token efficiency differs between models on the same work: on SWE-bench Verified tasks, Kimi-K2 and Claude-Sonnet-4.5 used on average over 1.5 million more tokens than GPT-5, and more tokens did not mean higher accuracy [S8]. A price per token is therefore not a cost per task, and one study found a crossover where the highest-priced model cost less than the next tier on long tool-heavy sessions [S6].
- List prices on 2026-11-09, per million tokens, input and output: Opus 5.5 $4 and $20, Sonnet 5.5 $2 and $10, Haiku 5.5 $0.10 and $0.50 for prompts up to 100,000 tokens [S48]. These are dated examples, not a recommendation.
- Other settings can matter more than size: in a study of a coding agent on four scientific tasks, the information given to the agent had a larger effect than the time budget or the model size, and extra time helped only when the agent had enough information or a capable model [S22].
- No paper I found holds a repository-level coding task set fixed and compares model tiers and effort levels on pass rate and cost per accepted task; the closest are [S2] (one task) and [S3] (benchmarks not named in the abstract). This is a candidate story for R10.

## Routing and escalation

- Up-front routing results cited first are on general benchmarks: a router between a strong and a weak model cut cost over 2 times in some cases at similar quality, and cascades cut cost by up to 98% while matching the best single model, both as recorded in R4 and neither a coding task [S36][S37].
- A cascade for code exists but predates agents: with self-generated tests and a threshold for when to call a larger model, costs fell by 26% on average and up to 70% across model families and datasets; the abstract says accuracy was kept or improved "in natural language generation tasks", so it is unclear from the abstract that the accuracy claim covers code [S19].
- Difficulty-aware choice of model, prompt and decoding settings improved results in one study: under a matched search budget on LiveCodeBench, pass@1 rose from 45.9% to 52.8% while cost fell from $36.57 to $4.92, and on SWE-bench 76.0% of tasks were resolved against 70.0% for the best baseline; it is the authors' own method, and the abstract reports a similar gain on repository-level SWE-bench, against a different baseline [S16].
- Tier routing on code health is a proposal with two stated conditions and no measured result in its abstract [S1].
- Escalating only after a verified failure is the closest test of H19, and it varies effort, not tier: starting at the lowest effort and escalating after a verified failure matched or beat fixed top effort across all models and benchmarks, at lower cost for most proprietary models [S3]. The benchmarks are not named in the abstract.
- Cheap-first escalation on coding tasks has a small 2026 literature, which my first query missed (see Method). SWE-Router lets a cheap model run a few turns, reads the partial trajectory, then continues cheaply or escalates; on SWE tasks it greatly improved cost efficiency and kept the majority of the stronger model's performance [S62]. ARIA learns when to consult a stronger model at workflow points and, on SWE-bench Verified among other tasks, recovers 44 to 81% of the executor-advisor success gap at less than half the advisor model's cost, ahead of routing and cascading baselines [S63]. Bayesian self-escalation derives an escalation threshold and checks it on a 1.5B to 7B code cascade (MBPP, 257 tasks), confirming two of three pre-registered predictions [S64]. A handoff study with Claude and GPT pairs on coding agents finds full-trajectory escalation recovers less than half of the low-to-high quality gap at a substantial cost premium, and downshifting offers a favorable cost-quality point [S66]. InflationAgent reports that forwarding a failed reasoning chain to a stronger model cut accuracy by up to 34.8 points on GSM8K, which supports a fresh attempt over the failed chain; it is not coding [S65]. AgentCollab escalates on self-reflection signals across agent benchmarks; its abstract names no coding benchmark [S67]. One paper on recovery routing was withdrawn and I do not use it [S15].
- An escalation is an upward model switch, and switching has a price. Each model has its own cache, so a switch recomputes the whole request [S47]. In a routing study on spreadsheet tasks, a downward switch recovered its cache cost within two calls and an upward switch did not break even under the conditions tested [S4]. The same spreadsheet study found history-aware routing within one point of always using the expensive model at a matched offload rate, and the cheaper model's per-task cost advantage narrowed from 6.8 times to 3.2 times on longer sessions [S4] (not coding). A fresh dispatch at the higher tier avoids the cache rebuild, but it pays full input price for whatever context it is given, so it saves only when that context is smaller than the session history (inference from [S4][S47]).
- Delegating to a cheaper model can cost more: across 600 public coding-agent trajectories, 98.6% of input tokens came from a prefix cache, a closed-form break-even condition for delegation was derived and checked, and delegation raised cost in half of the settings, near the predicted boundary; turn count explained 84% of the variance in log cost [S5].
- A router can sit in the harness: one design routes at session start, in side lanes and at subagent launch, and moves work only where no running conversation has to rebuild its cache; in an emulated enterprise of 10,000 seats it recovered 13 to 21% of model spend at list prices of 2026-09-21, a simulation using the authors' own classifier [S6]. Step-level routing under time and cost budgets (ProgRouter) cut operating cost against baselines on HumanEval Plus, MBPP, MATH-500 and ASQA [S18].
- A failure signal can come before the failure: a small open-weight draft model scores the agent's trajectory, and a veto gate on two software engineering agents cut execution errors by 6 to 8 points and token cost by 14 to 19% [S17]. Such a score could trigger an escalation (inference).
- The agent should not choose how to spend extra effort: in a controlled study of failed coding agents, three of four frontier models picked feedback in 95 to 100% of cases and gained less than a uniformly random pick [S35]. An escalation trigger from the harness, such as a failed declared command, avoids relying on the model's preference (inference).
- Picking a model per role can be searched empirically: at matched accuracy, the cost gap between the best and worst model combinations for pipeline roles reached 13 to 32 times, and a bandit search recovered near-optimal accuracy with 62 to 76% less evaluation budget [S27]. The four benchmarks are not named as coding in the abstract.
- How many failures before escalating (H15): none of the sources I read gives a failure count above one for coding agents; [S3] escalates at the first verified failure. N above 1 is unsourced.

## Token efficiency

- Prompt caching saves a lot, and placement matters: on a web-research agent benchmark (not coding) with 10,000-token system prompts, caching cut API cost by 41 to 80% and time to first token by 13 to 31% across three providers, and dynamic content at the end of the system prompt with dynamic tool results excluded gave more consistent benefits than naive full-context caching, which could raise latency [S9]. In 600 public coding-agent trajectories, 98.6% of input tokens were served from a prefix cache, so flat input pricing overestimated loop cost by roughly 7 times on average under near-ideal caching [S5]. Cache hits cost 0.025 times base input on Fable 5.1 and Mythos 5.1, 0.05 times on Opus 5.5 and Sonnet 5.5, and 0.1 times on the other models, including Haiku 5.5 [S48].
- Cache mistakes are silent: a study of 120 caching pull requests in 10 open-source agent systems found most mis-integrations fail without any visible error, and its linter identified 32 mis-integrations in 571 agent projects at 0.86 precision [S10]. An engine should record cache-read tokens per dispatch to see this (inference).
- Switching models breaks the cache: each model has its own cache, and a skill or command whose frontmatter names another model counts as a switch [S47]. Claude Code's cost view shows the cache share and misses for the main conversation only, not for subagents [S44].
- Context per dispatch is a cost: Claude Code starts its Explore and Plan subagents without the CLAUDE.md files and the git status snapshot to keep them fast and cheap [S43]; verbose work in a subagent stays out of the main context, but the subagent's own requests still draw usage [S44]. Each dispatch starts cold, and token cost scales with the number of teammates [S59]. Context files were associated with a 28.64% lower median runtime and 16.58% fewer output tokens in an observational study of 124 pull requests [S29], but raised inference cost by over 20% on average in another [S60]; the two disagree.
- Per-subsystem dispatch (one agent per subsystem against one per task) is unsourced: R6 found no measurement [S59], and I ran no query aimed at it.
- Turns, not observation size, drive cost in one study: turn count explained 84% of the variance in log trajectory cost and mean observation size 4%, though the authors do not show that turns can be removed with success held fixed [S5]. Methods that shrink observations still report savings: 33.0% fewer tokens on SWE-bench Verified [S30], and 19% fewer tokens with 15% fewer rounds from a retrieval agent [S34]. Agentic coding tasks use about 1000 times the tokens of code chat, input tokens drive the bill, and runs of one task vary up to 30 times [S8].
- The tool-definition cost claim is a vendor claim and stays unproven for weftwork: Anthropic reports 150,000 tokens falling to 2,000 (98.7%) by loading tool definitions from a filesystem on demand and calling MCP tools through code, for one example workflow [S41]. A tool proxy paper reports R@5 of 0.816 on a 49-query benchmark the authors built, and a measured top-5 discovery exchange of 475 tokens against 42,450 under its stated full-catalog accounting, over 374 tools in 22 servers [S33]. A code-execution MCP study found lower token use and latency but a much larger attack surface (sixteen attack classes) [S32], and a measurement study found that system prompts, MCP tool definitions and context histories inflate token use [S31]. All of these are unproven here: no source in this brief counted tool-definition tokens in Claude Code or pi.
- Hosts already defer tool definitions: Claude Code's tool search is on by default and loads only tool names and server instructions at session start [S46]; pi has `codemode` (a script tool with a 3,000-token inline budget for tool declarations) and `tool_search`, both registered inactive and enabled through `defaultTools` [S52].

## Local models

- Parallel requests on one local server are set by memory. Ollama processes one request per loaded model at a time by default (`OLLAMA_NUM_PARALLEL` is 1), the RAM needed scales with that setting times the context length, it loads up to 3 models at once by default (3 times the GPU count on GPU), and it queues up to 512 requests before answering 503 [S53]. llama.cpp's server splits its memory into slots (`--parallel`, default automatic) with continuous batching on by default [S54].
- pi connects to a llama.cpp router directly and to Ollama, LM Studio, vLLM and SGLang through an endpoint entry in `models.json` [S52]; R5 lists the other hosts' fields [S57].
- Capability falls behind the frontier unless trained for the job: a low-cost local model scored 24 to 37 of 42 where frontier models clustered near the ceiling [S2]; a lightly post-trained 7B model reached 42.4% pass@1 on SWE-bench Verified by asking a strong expert for help about 4 times per task, which used 11% of the tokens [S13].
- The harness changes the result as much as the model: for the same lightweight model, resolution rates differed by up to 44 points across six open-source harnesses on 100 SWE-bench Verified tasks, and charged tokens per resolved task varied more than 20 times [S12].
- A local model can cut cloud tokens as a triage layer: local routing plus prompt compression saved 45 to 79% of cloud tokens on edit-heavy and explanation-heavy coding workloads, and the best set of tactics depended on the workload [S11]. For finding files, a semantic search tool with small trained models under two billion parameters cut tokens 29.1% and trajectory latency 44.1% on CPU against grep-based agents using the same models [S40].
- Parallel agents need a scheduler: against a shared rate-limited API, uncoordinated agents failed at 72 to 100% rates under contention across seven scenarios, a five-primitive proxy (admission control, rate limits, backpressure, token budgets, priority queuing) cut that to 0 to 18%, and transparent retry was the most critical part [S26], and it was checked against Ollama with under 3 ms of overhead per request [S26]. For a local server the limit is memory, as above [S53].
- The owner said the project began on local LLMs [S61]; which hardware weftwork would run on is unsourced, so the number of parallel local agents it can afford is unsourced too.

## Budgets

- Host ceilings exist but are partial. Claude Code's `--max-budget-usd` stops a run once its client-side estimate reaches the amount (print mode only, subagent spend counts, spend can pass the cap) and `--max-turns` limits turns (print mode only, no limit by default) [S45]. opencode's `steps` caps agentic iterations and then forces a text answer, and its docs present it as a cost control [S51]. I found no spend ceiling in the Codex subagents page, whose config reference returned 404, and none in the pi settings and usage pages, which show accumulated cost and `thinkingBudgets` [S50][S52]; both are unsourced for a spend ceiling.
- A ceiling has to act on measured use, not a forecast: models predicted their own token use with correlations of at most 0.39 and underestimated it, and runs of the same task varied up to 30 times [S8].
- Budget shape changes the best strategy: under a fixed budget on 216 Codeforces problems, repeated independent sampling beat agentic reasoning on accuracy per dollar, and a cost-optimal solver minimizes log failure likelihood per dollar; these are self-contained algorithmic tasks, which may not carry over to repository work [S21]. In a credit-budgeted arena, frontier single agents and swarms did not balance accuracy against the budget well [S25].
- A scheduler can hold a token budget: token budget management is one of five primitives in a proxy that also does admission control, rate-limit tracking, backpressure and priority queuing [S26].
- Whether a per-story ceiling should be counted in dollars or in tokens is unsourced; the local-triage study counts cloud tokens saved [S11], and Claude Code's cap is a dollar estimate [S45].
- Logging each escalation: none of the host pages I read documents an escalation log; Claude Code reports usage per model and attributes it to skills, subagents and MCP servers [S44], so an engine would have to write the escalation log itself (inference).
- A position paper names recurring failure modes of token allocation (over-routing, over-delegation, under-verification, cache misuse) but is a position paper whose abstract shows no data [S24]. Stop conditions that are not about cost belong to R15 (e03s08); this brief does not cover them and cites nothing for them.

## Verdicts

- H15: refined - tiers rather than model names is supported by how hosts work: Claude Code resolves `opus`, `sonnet` and `haiku` aliases to the newest model, GSD maps agents through profiles, and Codex names models in config [S42][S55][S50]. Escalating at the first verified failure has a test on the effort axis only [S3]; none of the sources I read gives a failure count above one, and the new coding-agent papers decide escalation from a trajectory or learned signal, not from a fixed count, so the count stays unsourced above one [S62][S63][S64]. Budget ceilings exist as Claude Code's dollar cap and turn cap in print mode and as opencode's step cap, with overshoot noted [S45][S51]; the Claude Code costs page documents no escalation log, and I did not check the other hosts' pages for one [S44]. Refined: tiers hold, the "after N failures" count is unsourced above one, and ceilings are partial.
- H17: refined - routing helps only when the cheaper tier fails often enough and its failures can be predicted [S20], and the coding evidence is thin and split: a code cascade cut cost by 26% on average with an unclear accuracy claim [S19], difficulty-aware configuration cut cost and raised pass@1 on LiveCodeBench in the authors' own search [S16], while delegation raised cost in half of the settings in 600 coding trajectories [S5] and the top-priced model cost less than the next tier on long tool-heavy sessions, a crossover that repricing about 10,000 real sessions confirmed [S6]. No source measures pass rate against cost per accepted task across tiers on repository work. The claim that cheaper models keep pass rate while cutting cost is unproven for coding agents. The closest result, a spreadsheet study, keeps pass rate within one point of always using the expensive model with history-aware routing [S4], and SWE-Router keeps only the majority of the stronger model's performance, a weaker claim [S62].
- H18: refined - effort is a separate setting that hosts expose beside the model [S42][S50][S51][S52] and that matters: xhigh over high lifted first-try perfect runs from 28% to 89% on one coding task [S2]. It is not monotone: higher effort often failed on tasks lower effort solved and cost up to 42 times more on easy ones [S3], and one level name is not one value across models [S42]. Useful, but only when matched to the task, and no repository-level coding measurement exists.
- H19: refined - starting at the lowest effort and escalating after a verified failure matched or beat fixed top effort across all models and benchmarks at lower cost for most proprietary models [S3], so the claim holds on the effort axis against fixed top effort, not an informed up-front choice, with benchmarks the abstract does not name. For tier escalation, a code cascade supports it before agents [S19], and an upward switch costs a cache rebuild [S4][S47]. For coding agents, SWE-Router reports that a cheap model starting the run greatly improves cost efficiency on SWE tasks while keeping most of the stronger model's performance; the abstract names no baseline [S62], and ARIA reports a better success-cost trade-off than cascading baselines [S63]. None of the abstracts measures an up-front tier choice against escalation, and the handoff study finds full-trajectory escalation carries a substantial cost premium [S66]. Refined, not confirmed.
- H20: refined - static features predicted task difficulty with AUC 0.863, but one of its two main drivers, patch fragmentation, comes from the finished patch and so is not available before dispatch (inference); the authors conclude that difficulty is "encoded in its structure" and that this "enables static, pre-hoc difficulty estimation" [S7]; models predicted their own token use with correlations of at most 0.39 and human difficulty ratings aligned weakly with token cost [S8]; routing worked only where failures were predictable from visible features [S20]; Triage's conditions are untested [S1]. Deterministic signals are promising and cheap but not shown reliable enough to route on for weftwork.

## Implications for weftwork

- Name tiers (light, standard, heavy) and an effort level per role in the engine, and resolve them to a host alias or model id in each adapter, because the five hosts R5 read can set a model per dispatch (a field in four, a package in pi) and an effort level in all but Gemini CLI, which may have only a settings override [S57][S42][S50][S51][S52].
- Start from the Default tier per role table, and treat every cell as unmeasured until R10 tests it. Decide implementer and reviewer cells by a small evaluation on weftwork stories, since the cost gap between model assignments at matched accuracy reached 13 to 32 times [S27].
- Escalate on a verified failure signal from the harness (a failed declared command), at the first failure, first by effort and then by tier (on Opus 5.5, Sonnet 5.5 and Haiku 5.5 changing effort keeps the prompt cache, while a model switch does not [S47]), and start the higher tier as a fresh dispatch rather than a mid-session switch (inference: no source tests a fresh start directly; S47 gives the cache cost of a switch, and a fresh dispatch saves only when its context is smaller than the session history). The related evidence is partial: forwarding a failed chain cut accuracy on GSM8K, which is not coding [S65], and full trajectories carry a cost premium [S66]. Write each escalation to a log the engine owns. The Claude Code costs page documents no escalation log [S44], and I did not check every host's pages for one, so "no host has one" is inference.
- Do not build a learned router or a planner-model sizing step for v1: learned routers need training data and, in one study, retraining per dataset [S20]; the coding-agent learned controllers report gains on benchmarks with trajectory data, which weftwork does not have yet (inference: neither abstract states this) [S62][S63], and a model's own cost estimates were weak [S8]. Keep BCPs, which weftwork already records, and measure whether they predict cost before routing on them.
- Set a per-story ceiling in tokens or dollars measured while the run goes, plus a turn cap, using the host flags where they exist [S45][S51] and an engine count where they do not; count the cost of subagents [S45]. Do not rely on a forecast [S8].
- Record cache-read tokens per dispatch, and keep model switches out of long sessions, so cache mistakes show up [S10][S47].
- Keep tool definitions out of the always-loaded context with the hosts' deferred-tool features before building anything of our own [S46][S52], and count the tokens before quoting the 98.7% figure as ours [S41].
- Treat the local tier as optional: its limits are memory and the harness pairing, and the owner's hardware is unknown [S53][S54][S12][S61].

## Earns its place vs ceremony

- Tier names plus effort per role in the engine, with adapters resolving them: earns its place, as a cheap indirection that the hosts R5 read mostly support; the table's cells are unmeasured [S57][S42][S50].
- Escalation at the first verified failure: likely earns its place; measured on the effort axis [S3], for model tiers, coding-agent evidence now exists [S62][S63][S66], but none measures it against an up-front tier choice.
- Per-story spend and turn ceilings: earn their place as a safety stop, with overshoot and print-mode limits to design around [S45][S51].
- A learned or classifier router: ceremony until a measurement shows it beats the fixed table on weftwork tasks [S20].
- A planner-model step to size tasks: ceremony until it beats BCPs or a deterministic signal; models estimate their own cost badly [S8].
- Mid-session model switching: ceremony, and possibly harmful, until the cache break-even is checked on our hosts [S4][S5][S47].
- Code-based tool access and tool search: earns its place if tool definitions are large; the 98.7% figure is a vendor example and unproven here, and hosts already defer definitions [S41][S46][S52].
- Observation compression or retrieval agents: unproven for weftwork; their savings are reported but turn count may dominate cost [S30][S34][S5].
- Per-subsystem dispatch as a cost saver: unproven; no measurement [S59].
- Local models as a tier: unproven for weftwork; depends on hardware and harness [S12][S53].
- A separate reviewer tier or model from the implementer: unproven; the one direct test was mixed [S58].
