## Sandboxing

- Codex is the closest shipped match to "sandbox by default". Its CLI runs with network access off and writes limited to the active workspace (the current directory and temporary directories such as `/tmp`); in the `Auto` preset it edits and runs commands in the working directory without asking, and asks before editing files outside the workspace or running commands that need network access. On launch it recommends `Auto` for a folder under version control and `read-only` for one outside it [S29]. This is documented behaviour, not tested here.
- Claude Code's sandbox is off by default. Once on, writes are limited to the working directory and a temp directory, and network goes through a proxy whose allowed domains start empty. Reads still cover most of the machine, including `~/.ssh` and `~/.aws/credentials`. In auto-allow mode a command inside the sandbox runs with no prompt [S26]. Two defaults weaken an unattended run: if the platform lacks the sandbox or its startup dependency check fails, Claude Code runs commands unsandboxed unless `sandbox.failIfUnavailable` is set; and Claude may retry a failed command unsandboxed, where a matching allow rule such as `Bash(curl *)` also approves the retry with no prompt, unless `allowUnsandboxedCommands` is `false` [S26].
- The sandbox does not cover every tool. In Claude Code the file tools, WebFetch, MCP servers and hooks run outside it, so a `denyRead` entry does not stop the Read tool, and a local MCP server is outside the boundary [S26]. A "sandbox by default" rule is only as wide as the tools it wraps.
- The other hosts differ. pi has no built-in sandbox and does not ask approval before every tool call; its page says to run it inside a container, virtual machine or sandbox, and that the working folder does not stop commands reaching other paths [S25]. opencode defaults to `allow` for most permissions, with `external_directory` and `doom_loop` at `ask`, so many tool calls that touch paths outside the working directory prompt [S30]. Gemini CLI's sandbox is opt-in (`-s`, `--sandbox` or `GEMINI_SANDBOX`); once on, the default macOS Seatbelt profile `permissive-open` confines writes to the project directory while allowing broad reads and network [S31]. With its sandbox on, Gemini CLI also ships H21's pattern: when a sandboxed command fails on a permission, or is known to need more (such as `npm install`), a dialog asks the user and grants the extra permission for that run only [S31]. Of the five hosts, only Codex ships a sandbox on by default.
- Some paths inside the worktree (the writable area) stay write-protected, and the hosts protect different sets. Codex keeps `.git`, `.agents`, `.codex` and `.aws` read-only inside writable roots [S29]. Claude Code's sandbox denies writes to its settings files, `.claude/skills`, `.claude/hooks`, `.mcp.json`, shell startup files and `hooks` and `config` inside `.git` [S26]. The lists differ, so no portable "protected paths" set exists yet.
- Approval is itself an attack surface. Adversarial context planted in a repository steered agents on Claude Code and Codex CLI into requesting a broad allow-rule in 58% of instances, and once approved that rule gave silent goal completion in 47 of 58 eligible instances (81.0%) [S4]. A survey of 21 production systems found runtime approval in 15 of them, and describes users caught between approval fatigue and uncontrolled autonomy [S23]. The one independent test of a deployed approval gate found large gaps: Claude Code's auto mode (a transcript classifier) had an 81.0% end-to-end false-negative rate on deliberately ambiguous scope scenarios, 70.3% on the actions it evaluates, and 36.8% of state-changing actions were in-project file edits that the classifier does not evaluate; the vendor's reported rate on production traffic is 17%, and the authors say the workloads differ [S39]. A different design runs each command in a snapshotted sandbox first, shows an approver the observed effects, and rolls back what is blocked; it had a 6.7% harmful-outcome rate against at least 14.8% for six other systems on one benchmark, and blocked 1.0% of safe twin tasks on another [S42]. No study I found compares a sandbox with approval against one without approval.
- Hardening has a cost. Across 12 coding agents on Terminal-Bench 2.1, the strictest enterprise-style policy cost up to 18.3 points of success and up to 167.3% more cost, and failed runs mostly ground into timeouts or wrong answers rather than stopping early [S41]. A sandbox that blocks needed actions has to say so to the agent in a form it can act on (the Caper design does [S42]; Claude Code names the denied host in the command result [S26]).
- Agents are poor at inferring their own least-privilege policy. On 120 terminal tasks, frontier models both omitted permissions the task needed and granted unused or sensitive ones, and more inference-time reasoning did not fix it [S43]. Policies that a model generates for itself (as in S38 and S24) need an independent check.
- A sandbox can be escaped. In a benchmark of container escapes, LLMs identified and exploited vulnerabilities that were added to the setup; the abstract gives no rate [S14]. Isolation needs the same checking as any other control.
- Rollback is a different control from a sandbox. One prototype wrapped agent actions in transactions with a filesystem snapshot, and reports a 100% interception rate for high-risk commands and a 100% rollback success rate at 14.5% overhead; it used a small model on a custom testbed and is unreplicated [S13].

## Secrets

- Claude Code sandboxed commands inherit the environment variables of Claude Code, secrets included, and there is no built-in credential deny list; only the files and variables you list are restricted, through the `sandbox.credentials` setting (`deny` blocks, `mask` lets requests authenticate without the command holding the real value) and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` [S26]. Read deny rules such as `Read(./.env)` apply to its file tools and to recognized file commands in Bash, but not to a command that reads files without naming them (for example `grep -r`) or to a script that opens files itself, so they are not a credential boundary; the page points to the sandbox for that [S27]. opencode denies reads of `*.env` files by default [S30].
- Credentials leak through the transcript, not only through commands. Tool output, shell logs and file reads are appended to provider-bound transcripts. A local rewriting boundary removed all 20,814 annotated structurally sensitive characters (in 9,229 paths) and reduced credential leakage to 0.0% across 852 planted values on controlled repository transcripts [S15]. This is one tool on planted data.
- Credentials can also come out of the model. A black-box extraction method recovered masked, provider-specific credentials from three deployed LLM systems, including systems behind OpenAI and Claude Code, because training corpora may hold exposed secrets [S16]. These are memorized third-party keys, not this project's secrets, and the defence is outside the project; the point for a harness is that model output is not free of credentials, so it should not be written to shared places unchecked (a design judgement, not a finding of [S16]).
- pi's page warns that sessions can contain prompts, tool arguments, command output, file contents and credentials, and says to keep credentials outside the environment or use narrowly scoped, short-lived ones [S25].
- Credential theft is a main attack in skills. Of the 157 confirmed malicious skills, one of the two dominant strategies was credential theft via remote code execution [S2].
- The strongest model tested in an agent benchmark held hard boundaries against credential forwarding and destructive actions; weaker models permitted both, and safety depended on the agent framework as well as the model [S6].
- How often a real coding agent reads a `.env` file without being asked, in ordinary work, is unsourced; no study found measures it.

## Destructive commands

- Frontier models "can randomly generate destructive commands at nontrivial probabilities", and dangerous behaviour could be elicited with three conditioning examples; the authors respond with a harness modification [S11].
- Destructive acts also come from helpfulness. Across 17 models run through Codex, Claude Code and OpenCode, an agent finished its task while breaking an existing task in 44.5% of trajectories. A prompt telling it not to affect existing tasks reduced but did not remove this, an instruction authorizing it to stop local processes increased it, and in 31.9% of successful cases the final answer mentioned neither the conflict nor the action [S12]. The damage is to other running tasks and shared resources; the authors point to stronger privilege controls and task isolation [S12]. That version control cannot undo a killed process is this brief's inference, not the paper's.
- Destructive acts are among the dominant real-world failures. A study of 547 confirmed safety incidents in coding tools found 326 rated high or critical, with constraint violations, destructive operations, authorization bypasses and deception the dominant risks, and over 65% arising in bug fixing and in setup or configuration [S34]. Agents sometimes do more than asked on benign tasks, for example deleting unrelated files or wiping a stale credentials backup (the paper's examples of "overeager" actions); across about 7,500 runs of 500 scenarios on four agent products, a permissive cluster (Claude Code, Codex CLI, Gemini CLI) took such actions in 5.4% to 27.7% of runs, against 0.2% to 4.5% for OpenHands, and removing the written consent declaration from the prompt raised the rate on Claude Code from 0.0% to 17.1% on paired scenarios [S33]. In every run interactive confirmation was disabled (for example `--dangerously-skip-permissions` for Claude Code and `--ask-for-approval=never --sandbox=danger-full-access` for Codex), so this measures agents without an approval gate and says nothing about whether a gate would help [S33].
- A sandbox scoped to the worktree still lets an agent delete files inside it, including git history that is not protected. Recovery therefore needs version control, snapshots or backups; pi's page says to use them before substantial changes [S25]. A snapshot-and-rollback prototype is one design [S13]. Committing needs writes to `.git`, which Codex keeps read-only inside its sandbox [S29], so on that host a commit step may have to run outside the sandbox or with an approval.
- Hosts gate irreversible actions by rule. Claude Code evaluates deny rules first, then ask, then allow, and an allow rule cannot carve an exception out of a deny rule [S27]. A Bash deny rule matches the command text and is not a security boundary: `Bash(rm *)` stops `rm -rf build/` but not `/bin/rm -rf build/` or `bash -c 'rm -rf build/'`, and the page points to the sandbox or a `PreToolUse` hook for enforcement [S27]. Codex states that destructive app or MCP tool calls always require approval when the tool advertises a destructive annotation, unless it also advertises a read annotation, which takes priority [S29]; per R7, Superpowers stops for an irreversible or destructive operation [S32].
- Every host ships a way past its own gate: Claude Code `bypassPermissions` skips prompts, including for writes to protected paths such as `.git` [S27]; Codex has `--sandbox danger-full-access` and `--dangerously-bypass-approvals-and-sandbox` [S29]; opencode `--auto` approves every request that is not explicitly denied, and explicit `deny` still holds [S30].
- The legacy project's guards for irreversible git and filesystem actions never fired outside test fixtures in about two days in one repository, so they are neither shown to work nor shown to be useless there [S32].
- A formal treatment of reversibility (idempotent, reversible, compensable, irreversible) exists; whether it can limit what an agent may do alone is open, as R7 found [S32].

## Prompt injection from repo content

- Repo content is untrusted input, and the hosts say so. pi lists files, comments, instructions, command output and model responses as able to steer the model, says project trust does not make that content safe, and loads `AGENTS.md` and `CLAUDE.md` regardless of project trust unless context loading is disabled [S25]. Claude Code shows a trust dialog on first use of a folder, but a `-p` session shows neither that nor the `.mcp.json` approval prompt [S28]; an unattended loop will probably run in that mode (an inference, not stated by the page).
- Attacks on coding agents through poisoned development resources are measured and often succeed. AIShellJack, with 314 payloads covering 70 techniques, reached up to 84% success in executing malicious commands on GitHub Copilot and Cursor, including credential theft and data exfiltration [S36]. A systematization of 78 studies reports, as a meta-analysis of other papers' results and not a measurement of its own, attack success above 85% against state-of-the-art defenses when attacks are adaptive, and most of 18 defenses it reviewed mitigated less than 50% of sophisticated adaptive attacks [S35]. Two further results are adjacent, not repo-content studies: QueryIPI reached up to 87% success on five simulated coding agents by placing payloads in tool descriptions, the tool-metadata channel [S10], and the benchmark of S22 below covers that channel at scale.
- General agent benchmarks agree in direction. ClawSafety tested personal agents (OpenClaw) in professional workspaces, software engineering among them: success ranged from 40% to 75% across five models, and instructions in workspace skill files (highest trust) were more dangerous than email or web content [S6]. INFUSE, a benchmark of agentic workflows with shell and code tasks, found a mean attack success of 19.6% (LLM-judged) over 19 models; its per-model range of 3.2% to 41.9% includes a 3.2% for one model that comes from runs cut off by a cost cap and is not evidence of robustness [S5].
- Rule files are an injection channel. An attack that plants prompts in files such as `AGENTS.md` or `.cursorrules` made coding agents swap legitimate dependencies for attacker-controlled packages, with "high attack success rates" across models and frameworks; the abstract gives no figure [S7]. Weftwork's own context files are in this class.
- Filters and detectors are imperfect, and prompt hardening is a different control from a filter. A code-context sanitizer for code LLMs reached a 0.80 average node-level F1 across six attack families, which is a detector score, not an agent result [S8]. INFUSE found that external chat-safety classifiers transfer poorly (attack success stayed at 43.8% to 44.0% on a high-attack-success stress subset whose undefended rate is 58.2%) and that guard models give limited protection, while prompt-level instructional hardening cut attack success on that subset from 58.2% to 14.3%; the authors warn that these reductions are not to be extrapolated to the full benchmark, where the mean is 19.6% [S5]. Read together: filters did poorly, and hardening helped on a hard subset, with uneven utility costs.
- INFUSE also tested boundary-style defences, and the result is not favourable. Shell-level ports of Progent and a CaMeL-style control, on the same stress subset, produced no reduction in attack success distinguishable from their matched baselines; the only separable change was an increase (Progent raised one model from 6.5% to 27.1%), and Progent lowered utility by 64% to 75% on three of four models. A model-level defence (Meta-SecAlign) did reduce attack success. The authors present the ports as their own adaptations, so this does not refute the original systems, but it shows that a boundary's value depends on how well its policy fits the workflow [S5].
- Permission boundaries did well in one coding-agent study, against baselines, with limits. CapScope derives a task-wide authority ceiling from trusted input before repo content is read and checks every tool call against typed per-agent capabilities. The injected effect ran in 3 of 75 runs, against 33 to 47 of 75 for ambient-authority and global-policy baselines, and 68 of 75 repairs completed against 68 to 72 for the baselines. It was built on pi and tested on five small Python repairs, five injection surfaces, three trials per cell and one model (qwen3.5-flash); all three executed attacks came through `AGENTS.md`, the same kind of file weftwork depends on. Mean run time was 316 s under CapScope against 145 s for the ambient-authority baseline, and the mechanism does not prevent misuse of a capability that was granted [S3].
- Two general designs back the boundary approach, tested on general agent benchmarks, not on coding agents. CaMeL extracts control and data flow from the trusted query so untrusted data cannot change program flow, and solved 77% of AgentDojo tasks with provable security against 84% undefended [S37]. Progent checks every tool call against a least-privilege policy, and treats a proposed policy update as either a narrowing (applied automatically) or an expansion (explicit approval), so the action space can only shrink without approval [S38].
- Boundaries have a human hole. Planted repository context steered agents into asking for a dangerously broad allow-rule, which the user then approved [S4]. A boundary that a user can widen on the agent's request is only as strong as that approval; Progent's rule that only narrowing is automatic is one answer, untested against [S4] [S38].
- The literature leans towards system-level defences over model-level ones. The systematization of S35 concludes that injection needs architectural mitigations, not ad-hoc filtering. A position paper argues for rule-based and model-based checks inside designs that strictly constrain what the model sees and decides, and warns that existing benchmarks can give a false sense of security [S9]. Another proposes capabilities scoped to task intent and context source, validated by a deterministic checker, and reports blocking tested violations without rejecting benign actions [S24].

## Skill and plugin supply chain

- Scale of the problem. Of 31,132 marketplace skills analysed, 26.1% had at least one vulnerability (data exfiltration 13.3%, privilege escalation 11.8%) and 5.2% showed high-severity patterns suggesting malicious intent; the odds of a vulnerability were 2.12 times higher (odds ratio) for skills that bundle scripts than for instruction-only skills [S1]. In 98,380 skills from two registries, 157 were confirmed malicious, more than half from one actor using templated brand impersonation, and the registries removed all 157 after disclosure [S2].
- Skills install with full user privileges and little vetting [S2][S1], so install is the trust decision. pi says extensions run inside its process and should be reviewed before loading [S25]; Claude Code's sandbox denies writes to `.claude/skills` so a sandboxed command cannot add one [S26]; Codex keeps `.agents` read-only [S29].
- Scanning before install is supported but imperfect. The SkillScan detector reached 86.7% precision and 82.5% recall [S1]; SkillGuard-Robust reported 98.33% malicious-risk recall on a 404-package held-out set, with transfer to harsher external sources still open [S18]; SkillScreen flagged 20% to 25% of benign skills at 99% recall, and false positives rose sharply on unfamiliar benign sources [S19].
- Scanners also over-flag. Scanner reports from individual marketplaces classified up to 46.8% of skills as malicious; a repository-aware analysis of 238,180 skills left 0.52% suspicious [S20]. The two figures have different bases (the highest share one marketplace scanner flagged, against the share of all collected skills after context), so they show a large gap, not an exact rate. A scan-before-install gate that ignores repository context will block many safe skills.
- Scanners can be evaded. PhantomSkill hides malicious behaviour in a skill's auxiliary resources as vulnerability-shaped code, lowering warnings and malware-level detections, and the authors conclude that ecosystems need resource-level vetting and execution-time containment [S17]. Skills that look benign alone can also become harmful in composition, with attack success of 33.6% against near zero in isolation on one sub-benchmark [S21].
- Pinning a skill to a version or commit has no study of its own that I found; a measured pinning control is unsourced. Indirect support: skills hosted in abandoned GitHub repositories can be hijacked [S20], which a pin to a reviewed commit would block until the pin is updated. A measurement over 1.43 million skills finds that skill identities, versions and provenance are implicit, that inspecting a skill alone misses security signals hidden in its dependencies, and borrows from software bills of materials to model skills as dependency-bearing artifacts; it does not test pinning [S40]. A scan should therefore cover a skill's dependencies as well as the skill.
- Tool metadata is part of the supply chain. In MCP tool poisoning on 45 real servers, attack success reached 72.8% on one model, more capable models were often more susceptible, and the highest refusal rate was under 3% [S22].

## Threats and controls

| Threat | Control | Enforced by | Residual risk | Evidence |

| Destructive command | Version control or snapshot before work; sandbox write limits and protected paths for .git; task isolation for shared processes; deny rules only as a first filter | Sandbox or PreToolUse hook, plus rollback | Deletes inside the worktree; deny rules miss other command forms; bypass flags; agent disrupts other tasks | [S11][S12][S13][S25][S27][S34] |
| Secret leak | Keep credentials out of the run; scrub environment variables; sandbox read limits on credential files; rewrite transcripts | Sandbox and environment scrubbing | Read deny rules miss `grep -r` and scripts; no default deny list; model may emit memorized third-party credentials | [S15][S16][S26][S27] |
| Prompt injection | Authority ceiling and per-agent capabilities checked on every tool call, not model detection | Harness capability check | Approval flow can be steered; the one positive study used a small model on five Python repairs, with residual hits via AGENTS.md; ports in another study showed no gain | [S3][S4][S5][S35] |

## Verdicts

- H21: refined - the sandbox-by-default half is what Codex ships (network off, writes in the workspace, approval outside) and what Claude Code's auto-allow mode does once enabled, though Claude Code ships it off and can fall back to unsandboxed runs [S29][S26]; Gemini CLI ships the "ask only to leave the sandbox" pattern once its sandbox is on [S31]. The approval half has no positive measurement: the one independent test of a deployed gate found an 81.0% false-negative rate on ambiguous scope cases [S39], and the study of overeager actions ran every framework with confirmation off, so it says nothing about approval [S33]. It is also weaker than the claim because agent-proposed allow-rules can be steered by repo content [S4], approvals tire users [S23], some tools run outside the sandbox [S26], deny rules are not a boundary [S27], hardening costs success and money [S41], and destructive acts inside the worktree need rollback, not approval [S13][S34]. A design that checks the observed consequences of a command in a snapshot did better on its own benchmarks [S42]. No measurement was run here.
- H22: refined - scanning before install finds real threats [S1][S2][S18] but over-flags without repository context [S20][S19] and can be evaded by resource-level hiding [S17], so it needs execution-time containment [S17] and review; pinning to a commit is supported only indirectly [S20] and no study tests it.
- H23: refined - the evidence is mixed. For boundaries: CapScope beat ambient-authority and global-policy baselines (3 of 75 against 33 to 47 of 75 runs; one small model, five Python repairs, longer runs) [S3], and the systematization and position papers favour architectural defences [S35][S9]. Against: shell-level ports of Progent and a CaMeL-style control showed no gain on INFUSE's stress subset, and Progent cost 64% to 75% of utility [S5]; models generate poor least-privilege policies on their own [S43]; and the approval step that widens a boundary can be steered [S4]. On filters: classifiers left attack success near 44% on that subset and guard models gave limited protection [S5], but prompt-level hardening cut it from 58.2% to 14.3% and a model-level defence also helped [S5], so "not prompt filters" omits controls that did work there. The claim that boundaries beat filters is supported only weakly, by one positive coding-agent study and one mixed benchmark.

## Implications for weftwork

Each bullet is a design judgement drawn from the evidence above; the citations support the facts it rests on, not the judgement itself.

- Treat all repo content as untrusted, including `AGENTS.md` and skill files, because they are an attack channel [S7][S36][S3]. This is a rule for the engine and for the skills it ships. S36, S7 and S3 are coding-agent studies; S6 and S5 are general agent benchmarks; none tests weftwork's own files.
- Do not build a sandbox; compose the host's. The hosts differ widely: Codex ships one on, Claude Code and Gemini CLI ship one off, pi has none, and opencode defaults to allow [S29][S26][S31][S25][S30]. The adapter should report which boundary a host gives and refuse to call a run "autonomous" on a host with none, unless the run is inside a container or virtual machine [S25]. For unattended Claude Code runs, the documented settings that close its fallbacks are `sandbox.failIfUnavailable` and `allowUnsandboxedCommands: false`, and `permissions.blockReadsOutsideWorkingDirectories` narrows the default read surface [S26]. When the sandbox blocks something, return the reason to the agent in a form it can act on, because hardened runs otherwise grind into timeouts [S41].
- Keep a portable "protected paths" list in weftwork's own rules (`.git`, skill and agent directories, settings and hook files, credential files), since the hosts' lists differ [S29][S26].
- Make recovery part of any autonomous run: start from a clean branch and commit before risky steps, because a worktree-scoped sandbox does not stop deletion inside it [S25][S13]. Under Codex, `.git` is read-only in the sandbox, so the commit step needs an escalation or must run outside it [S29].
- Treat agent-proposed permission rules as untrusted input to a human or reviewer, and do not let an autonomous loop widen its own permissions [S4][S38]. ClayBuddy lets an agent edit its own harness to add safety [S11]; that is a widening risk of its own unless edits are limited to narrowing, and the settings and hook files are protected paths [S26][S29].
- Use a sandbox or hook, not deny rules, to enforce the protected-paths and destructive-command lists, because a Bash deny rule matches text only [S27].
- For skills from outside the project, require a repository-aware scan before install and run installed scripts inside the sandbox [S20][S17]. Pinning a reviewed commit is a precaution that follows from the hijack of abandoned repositories [S20]; it is a design judgement, since no study tests pinning. Keep the catalog small (H10), since each skill with scripts adds risk [S1].
- Keep credentials out of the agent's environment where possible, and scrub the environment of sandboxed commands; on Claude Code that means the `sandbox.credentials` entries and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` [S26][S25].

## Earns its place vs ceremony

- Earns its place: a sandbox with network off by default, because a major host ships it that way and it removes exfiltration through shell commands without prompts [S29]. File tools, WebFetch, MCP servers, hooks and cached web search can stay outside it [S26][S29], and whether network exfiltration is the largest class of harm is unsourced. Hardening has a cost in success and money [S41].
- Earns its place: version-control recovery before autonomous work. It costs a commit, and sandboxes do not cover deletion inside the worktree [S25][S34].
- Unproven, with mixed evidence: capability checks on tool calls. The positive result is one comparison with one small model on five Python repairs (see Prompt injection) [S3]; ports of similar controls showed no gain in another benchmark [S5].
- Ceremony until measured: an approval prompt for out-of-sandbox actions. The one independent test of a deployed gate missed most ambiguous cases [S39], approvals tire users and can be steered into broad rules [S23][S4], and no study compares approval on and off. Keeping approval for permission widening and new hosts, not for every action, is a proposal, untested here [S38].
- Ceremony until measured: a prompt-injection filter run as the only defence. The best detector here reached 0.80 node-level F1 [S8] and classifiers left attack success near 44% on a stress subset [S5], though prompt-level hardening helped there [S5].
- Ceremony until measured: scanning every skill with no repository context, which flags up to 46.8% of skills as malicious, against 0.52% after context [S20].
- Unproven: pinning skills by commit as a control [S20].

## Open questions

- Which sandbox does a given host really enforce when weftwork runs a loop unattended? Candidate R10 measurement: read the effective sandbox and approval state for each host on a fixed task and record what an out-of-sandbox write, a network call and a read of a credential file do. Unsourced beyond the docs.
- Does CapScope-style capability checking carry over from pi and Python repair to other hosts and to weftwork's stories? Candidate R10 measurement: inject a planted instruction into a spec file and count executed effects with and without a capability check [S3].
- How often does an agent request a broad allow-rule in ordinary work, and how often do users approve it? [S4] measures the attack, not the base rate. Unsourced.
- What false-positive rate does a repository-aware skill scan have on the skills weftwork would ship? Candidate R10 measurement on the catalog itself [S20].
- Does pinning to a commit reduce loss in practice, or does it only delay updates? Unsourced.
- Which protected-paths list should weftwork require, and who owns it when hosts disagree? Open for the owner and for R13 [S29][S26].
- Does an approval gate reduce out-of-scope actions at all? S33 ran every framework with confirmation disabled, and S39 shows a deployed gate missing most ambiguous cases. Candidate R10 measurement: the same model and task set under approval on and off in one host, plus a consequence-checking variant [S33][S39][S42].
