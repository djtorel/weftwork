# R6 — Multi-agent work in one codebase

Research story R6, wave 3. Hypotheses H11 and H12.

Question: when several agents work in one codebase, how do they share
state, hand off work, isolate their edits, scope the files each may touch,
avoid or resolve merge conflicts, and integrate the result?

## Failure modes

What goes wrong when agents share a codebase. Figures come from abstracts, and each paper uses its own benchmark.

- Textual merge conflicts are common when agents work at once. The authors replayed three-way merges on 747 pairs of concurrent agent-authored pull requests, one pair per repository. Textual conflicts hit 41.7% of cross-agent pairs and 19.8% of same-agent pairs. Of the conflicted files, 84.4% were source files, and nearly 42% of the conflicts were structural (modify/delete or add/add) [S18]. These are pull requests agents opened on GitHub, not the output of one planned decomposition, so the rates show how often overlap happens without coordination. Only 0.5% of the co-active pairs were cross-agent (in 122 of 2,807 repositories), so 19.8% is the more representative rate [S18].
- Two agents on one file overwrite each other, and the vendors say so. Claude Code's agent teams page: "Two teammates editing the same file leads to overwrites" [S2]. Codex's subagent page: parallel agents editing code at once "can create conflicts and increase coordination overhead" [S4].
- Semantic conflicts survive conflict-free convergence. CodeCRDT (agents on a shared CRDT state, not a git merge) reached 100% convergence with zero merge failures and still measured semantic conflict rates of 5-10% [S14]. Its speed results were mixed: up to 21.1% faster on some tasks and up to 39.4% slower on others [S14]. This is one preprint on one stack, read by abstract.
- Features that can be built independently still collide. CooperBench gives two agents different features on real repositories, each implementable alone but liable to conflict. Agents succeeded on average 30% less often together than alone [S13]. The authors trace this to vague or late messages, broken commitments and wrong beliefs about the other agent's plan [S13].
- Multi-agent failures are not only about files. MAST built a taxonomy of 14 failure modes from 150 annotated traces, and released a dataset of 1600+ traces across 7 multi-agent frameworks [S20]. I read only the abstract, so I cannot say which modes apply to concurrent code edits.
- Workspace isolation may only move the conflict. STORM argues that one worktree per agent defers conflict handling to a merge step where recovery is costly, and reports +18.7 on Commit0-Lite against a worktree baseline, but only +1.4 on PaperBench [S15]. CAID reports the opposite reading of the same primitives: branch-and-merge with test-based integration beat a single agent by 25.6 points on PaperBench and 14.7 on Commit0 [S16]. The two compare against different baselines, so they do not settle which is better.
- Isolation leaks. Claude Code's worktree checks read the target path, the working directory and the command text, but "None of them tracks which files a shell command writes", so `cp` or a redirect into the main checkout is not refused [S1]. In weftwork's own use, the gates of a new worktree evaluated the primary checkout because the gitignored `scripts/` link was missing, so a green result described the wrong tree (BUG-002) [S7].
- Parallel paths may postpone commit-time checks. GSD tells parallel executors to commit with `--no-verify` to avoid pre-commit hook contention, and moves the hooks to one post-wave run by the orchestrator. If that run fails, GSD reports it and asks "Fix hook issues now?" or "Continue to next wave?", so the check comes after the commits and is advisory [S5].
- Shared state files are written from many worktrees. In GSD each parallel executor updates STATE.md and ROADMAP.md [S5]. I did not find how GSD reconciles those writes, so whether they conflict is an inference, not a finding.
- Git allows a branch in one checkout only. Codex notes that a branch checked out in a worktree cannot be checked out locally at the same time [S3]. An engine that creates worktrees must pick branch names so that handoff does not collide.
- Coordination costs tokens and time. Claude Code states that token cost scales linearly with teammates and that more teammates mean more coordination and potential conflicts [S2]. Co-Coder's starting point is that adding agents adds communication overhead that "can sometimes offset the efficiency gains" [S17].

## Dispatch granularity

The unit of dispatch decides how often an agent starts cold. The sources use six units.

- **Per task, one at a time.** Superpowers sends a fresh implementer subagent per task with a review after each, and says what that costs: "a fresh context per task and per review", where an inline run costs one context plus one final reviewer [S8]. It also forbids parallel implementers: "Never dispatch multiple implementation subagents in parallel (conflicts)" [S8].
- **Per independent problem domain.** Superpowers' parallel skill dispatches "one agent per independent problem domain", for example different test files or subsystems, and only when there is no shared state [S8]. It is written for investigating separate failures, not for building a feature.
- **Per plan with declared files.** GSD's unit is a plan whose frontmatter lists `files_modified`, grouped into waves at plan time; each executor loads the full execute-plan context [S5].
- **Per story, one branch.** bigpowers takes a lock and makes one branch or worktree per story [S6]. That is a unit of isolation: it does not split one story among agents.
- **Per set of files.** Claude Code's agent teams advise that each teammate owns a different set of files. They suggest 3-5 teammates to start, and tasks with clear boundaries that do not write code, because parallel implementation brings the coordination problems [S2].
- **Per dependency community.** Co-Coder builds a dependency graph by static analysis, sets structural hub files apart, and partitions the rest by community detection. Its gains were largest on the most dependency-dense projects, with up to 2.10x speedup and up to 35% lower API cost than its baselines [S17]. CAID uses a central manager that builds a dependency-aware task plan and runs subtasks in isolated workspaces [S16]. Co-Coder's units are file communities found by a tool, not human-named subsystems, and the abstract frames the gain as a communication-versus-computation trade-off [S17].

Three points bear on the choice of unit.

- **Read-heavy work parallelizes more safely than writing.** Codex recommends parallel agents for exploration, tests, triage and summarization, and care with parallel write-heavy work [S4]. Claude Code's agent teams page gives the same advice for newcomers [S2].
- **A cold start is paid per dispatch.** bigpowers says each agent starts cold, that brief size controls token cost and hallucination risk, and that each agent should get only the decisions relevant to its task [S6].
- **What I did not find.** None of these sources measures what re-learning the codebase costs, or compares one agent per subsystem with one agent per task on the same work [S5][S8][S17].

## Verdicts

- H11: refined - grouping parallel work by how tightly the code is coupled is supported, but the stated reason (avoid re-learning the codebase) is not measured and the supported unit is a dependency community, not a subsystem. Co-Coder partitions by static dependency graph and, against sequential, file-parallel and Claude Code Agent Teams baselines, lifts pass rate by up to 14.0%, speeds up to 2.10x and cuts API cost by up to 35%, with the largest gains on dependency-dense projects [S17]; CAID's manager builds dependency-aware task plans [S16]; Claude Code advises one set of files per teammate [S2]. Against it, Superpowers deliberately uses a fresh agent per task and accepts the cold-start cost [S8], and bigpowers briefs each agent cold to limit tokens [S6]. Co-Coder frames cross-agent dependencies as costly context transfer, which is close to the re-learning idea, so its cost result is indirect evidence for the reason [S17]; still, no source measures re-learning cost directly or compares subsystem dispatch with task dispatch on equal work [S5][S8][S17], and the paper evidence is preprint abstracts.
- H12: refined - the two halves fare differently. Half one, disjoint file scopes checked before dispatch: it is the common mechanism (GSD `files_modified`, bigpowers `in_scope` and `out_of_bounds`, Claude Code's advice) [S5][S6][S2], but in the tools read the check is a planner convention or a manual step, not a mechanical one [S5][S6], and no source read tests disjoint file scopes directly: CodeCRDT measured 5-10% semantic conflicts on shared state after clean convergence and CooperBench found 30% lower success on features described as implementable independently, so a clean merge or an independent task does not rule out a semantic conflict, and whether disjoint scopes do is an inference [S14][S13]. Pre-write admission control is proposed by ATM, within one governance domain and without a claim of superiority [S19]. Half two, an integrator that re-verifies the merged result: only CAID is shown to verify at integration, since it consolidates progress with executable test-based verification and beats single agents [S16]. bigpowers' parent runs the verify commands on each result and checks diffs, then merges accepted results and resolves conflicts by hand, so its verification comes before the merge [S6]; GSD verifies `must_haves` after all plans and I found no explicit per-plan merge step, so neither re-checks a merged tree [S5]. Half two therefore rests on one preprint abstract plus practice that verifies near integration, not after it, and no source measures the step on its own. A scope check is necessary but, on this evidence, not shown to be sufficient.

## Implications for weftwork

These are recommendations for e04s02, not decisions.

- Make the overlap check mechanical. Give each parallel task a declared file list, as GSD and bigpowers do, and have the engine refuse to dispatch two parallel tasks whose lists overlap; add a coupling check (shared imports or types) where the stack allows it, because tasks that look independent can still conflict semantically, although no source read tests disjoint files directly [S5][S6][S14][S13][S17].
- Integrate by re-running the declared verify commands on the merged tree, not by trusting each worktree's own result. bigpowers verifies each result before merging, so this is an addition to it, and the support is CAID's abstract [S16][S6]. Point every gate at the checkout being judged, since BUG-002 showed gates silently judging the primary checkout [S7].
- Let the engine create worktrees and pick branch names that cannot collide, because hosts differ and Git allows a branch in one checkout only [S10][S3].
- Default to sequential writing and parallelize read-heavy work first (review, exploration, test runs), which Claude Code and Codex advise and Superpowers instructs for implementers [S8][S4][S2].
- Do not let a gate become advisory in the parallel path. GSD already moves its hooks to one post-wave run, but lets the user continue past a failure [S5]; make the integrator's gate blocking.
- Keep shared state files to one writer. The orchestrator should write the state file; parallel agents should return results. beads' claim step is one way to do it, GSD's executors each editing STATE.md is the case to avoid, and this is an inference, not a tested result [S9][S5].
- Do not adopt a coordination database yet. beads adds a Dolt database [S9]; plain files with a single-writer rule are the smaller option, and R0 listed where state lives as an open topic [S21].

## Earns its place vs ceremony

- Earns its place: a mechanical file-overlap check before parallel dispatch. It is cheap and deterministic, and concurrent agent-authored pull requests conflicted textually in 19.8% to 41.7% of replayed merges [S18][S5][S6].
- Earns its place: re-running verify commands on the merged result. CAID integrates with test-based verification; bigpowers verifies before it merges and GSD after all plans without a per-plan merge step, and none measures the step on its own [S16][S6][S5].
- Earns its place: engine-created worktrees with gates aimed at them, from weftwork's own failure [S7][S10].
- Ceremony until proven: a fresh subagent plus a two-part review for every task. Superpowers' own docs list the cost, and I found no measurement of the benefit [S8].
- Ceremony until proven: typed message envelopes between agents (`task_brief`, `checkpoint`, `result`, `circuit_open`). No source tests them [S6].
- Ceremony until proven: agent teams that message each other. CooperBench traces coordination failures to jammed or inaccurate messages, and Claude Code marks the feature experimental [S13][S2].
- Ceremony until proven: a lock file for stories, such as `specs/agent-locks.yaml`. It lives in `specs/`, so each worktree carries its own copy until merged, which is my inference, and I found no evidence it prevents a real conflict [S6].
- Ceremony until proven: a database tracker for coordination [S9].
