## Compaction

- Hosts own the compaction trigger, and pi and Claude Code compact close to a full window; opencode's docs give no trigger point, only `auto`, `prune` and a `reserved` buffer. pi compacts when `contextTokens > contextWindow - reserveTokens` (default reserve 16,384 tokens, 20,000 recent tokens kept, `/compact` for manual runs) [S23]. opencode has `compaction.auto` (default on), `prune` (default off, removes old tool outputs) and a `reserved` token buffer [S24]. Claude Code compacts at the model's limit by default, at about 967K tokens for models with a native 1M-token window, at the 200K boundary for some models, `/autocompact` with a token count moves the point earlier, and the `idleCompaction` setting also compacts a conversation left idle [S22]. Codex has a manual `/compact` that summarizes the visible chat and has a `model_auto_compact_token_limit` setting (a token threshold for automatic compaction that uses model defaults when unset, with a `_scope` key choosing whether the full active context counts) and a `model_post_turn_compact_threshold_percent` setting that compacts after a final response at a percentage of the usable window [S25]. In the passages I read, none of these pages gives a basis for its default (unsourced).
- One preprint says agent frameworks commonly summarize when context crosses 70 to 90 percent of the window, citing four works I did not open, so I treat it as a claim and not a measurement (the pi and Claude Code defaults above sit later in the window than that range); its own design keeps the active context under a fixed 80,000-token ceiling, about 30 percent of the models' windows [S1].
- No universal threshold is supported. In a code-audit workflow one model passed 8 of 10 runs in a 10,991-character context and 3 of 10 in a 299,140-character context, with the same drop when the extra text was irrelevant (p = 0.0698, which the authors call trend-level); a second task passed every run, and the authors say the evidence does not support a universal context-length threshold [S8]. This is one model and two tasks.
- On frontier models in a coding-agent scaffold, the threshold mattered little in one study. With the OpenCode scaffold fixed, five compaction strategies and three frontier models on three long-horizon agentic benchmarks (PaperBench, ProgramBench and PostTrainBench), the threshold did not measurably affect performance for the two 1M-context models, while the smallest-window model did worse at lower thresholds on one benchmark and, less clearly, on another; no method beat default self-summarization, and methods that discard more content cost some models up to 20 points [S39]. The authors' reading is that benchmarks are compaction-friendly, because the objective is fixed and progress stays on disk, so most of what compaction discards can be recovered, except constraints that exist nowhere else [S39].
- Compaction designs for coding agents report gains, all from their own authors. A deterministic method for pi keeps user and assistant prose verbatim and flags what was stripped; against pi's default model-written summary and a deterministic baseline it matched or outperformed both on commitments and fact recall across four models (emphasis on a 27-billion-parameter local model), with a smaller advantage for a frontier model [S47]. A trained policy that learns when to compact and what to keep improved pass rates by an absolute 9.2 and 5.0 percent on SWE-bench Verified and SWE-PolyBench Verified [S49]. An autocompaction method that only truncates or drops content, never rephrases it, and never compacts a compaction, reports up to 50 percent lower cost on Terminal-Bench at maintained or better performance, with an API proxy usable with Claude Code and Codex [S50]. Pruning file context to the current goal is another lever (23 to 54 percent token reduction on agent tasks such as SWE-bench Verified with unchanged or better success, as claimed by its authors) [S55].
- Timing matters for small models. A small-model runtime reports that on 100 SWE-bench Verified tasks run by a 27B reasoning model on a 49K-token window (556 graded sessions), compaction raised the resolve rate on long sessions from 41 to 53 percent (+12.3 points, 95 percent CI +1.6 to +23.0, McNemar p = 0.043); the gain vanished under a 45-minute session budget because each summary took a median of 161 s, and in a threshold study it appeared only when compaction triggered early enough to leave room [S70].
- Compaction can launder untrusted text into trusted memory (R11). In five harnesses that flatten the conversation into one string with text role labels (pi, opencode, Cline, Aider and OpenHands), a forged user turn survived compaction as a genuine instruction 87 to 100 percent of the time; in four harnesses that keep role-typed messages (Codex, Gemini CLI, Qwen Code and Continue) the same attack succeeded 0 percent; a code-level provenance check caught 77 percent while demoting 2 percent of legitimate content [S48]. Any re-injection weftwork adds must keep message roles.
- What compaction keeps is a safety question. Across 1,323 episodes and seven model families, a policy that agents never violated in full context was violated in 30 percent of episodes after one compaction step (59 percent for some models), and in 38 percent when the summary dropped it; a mitigation that pins the constraint outside the summary restored 0 percent violations [S4]. The main experiment used a simulated sandbox with tool calls parsed and never executed, one-turn trigger requests and constraints that could be quoted as rules; on a three-model panel the authors found that violation tracked the summarizing model, not the acting model, and of four compaction strategies only one that keeps the oldest turn preserved the policy [S4]. They also report the effect in framework context managers (a LangGraph summarization node, 65 percent on one model; the LangMem summarization node, 95 and 70 percent on two models; AutoGen's recency eviction, 100 percent; 20 episodes each), compounding over repeated compaction (0 to 78 percent across four rounds), and limits: pinning needs a rule that can be quoted, an operator-impersonation notice in the recent context raised violations under naive pinning from 0 to 17 percent (10 percent with a pin hardened with provenance), and messages that a framework keeps immutable are a separate, safer channel [S4]. Two other studies agree on the direction: the first compaction summary dropped about one third of a task's anticheating rules on average and the share grew with each compaction, and instructions about how to work were dropped about six times as often as specifications of what to build in real sessions [S39]; across 14 summarizer models stable damage reached 5 to 64 percent of 22 full-history successes, and LLM summaries kept at most 16.0 percent of recurring details against 79.1 percent for mechanical extraction [S40].
- Keeping the rule in the summary is necessary but not sufficient. In ARCBench, built on the pi harness, most violations after compaction occurred while the rule was still in the compacted history, with the agent treating a later request as permission or ignoring the rule; how a rule is delivered decides whether the agent would break it even without compaction, the strongest compactor-targeted attack more than doubled violations, and the strongest defense restored the rule in most summaries but still violated [S58]. CONPACT found that compactors kept 17 percent of injected side constraints on average, that an inbox agent deleted emails without approval in 30 of 100 sessions after compaction and in none before, and that a separate extractor keeping constraints apart from the summary reached over 90 percent retention [S59]. In an analysis of one structured compressor, 83 percent of failed runs traced to an action carrying out a summary entry that, in most cases, no environment output supported (AppWorld and OfficeBench, not coding tasks) [S65].
- Claude Code's own compaction prompt was measured on rule retention. On 20 production agent configurations, `/compact` on Sonnet 4.6 preserved 53 percent of safety rules after one round and 10 percent after five; the authors' type-aware retention preserved 2 to 4 times more safety rules than the strongest single-shot LLM compactor (their own framework) [S71]. The abstract does not say whether files Claude Code re-injects from disk were included, so how re-injection interacts with this result is untested.
- What survives a compaction depends on where it lives. Claude Code re-injects CLAUDE.md, auto memory and the plan-mode plan from disk, re-reads up to five recently touched files, caps re-injected skill bodies at 5,000 tokens each and 25,000 in total, reloads path-scoped rules and nested CLAUDE.md files only when their trigger file is touched again, and summarizes context that hooks added earlier with the rest of the conversation; a `SessionStart` hook matching the `compact` source, a `PreCompact` hook and a `PostCompact` hook let a project re-inject or shape what is kept [S22]; Codex's config reference lists `PreCompact`, `PostCompact` and `SessionStart` among its hook events [S25]. pi's `session_before_compact` event can cancel a compaction or supply its own summary [S23]. Anthropic's guidance is to tune the compaction prompt on real traces, to maximize recall first, and it names tool-result clearing as one of the safest, lightest forms of compaction [S21].
- Summarizing is not the only lever, and its advantage is not shown. In SWE-agent on SWE-bench Verified across five model configurations, masking old tool outputs cut cost by more than half in most configurations (one configuration, Qwen3-32B with thinking, had much shorter trajectories, which the authors say explain its small saving and could not themselves explain, and summarization was the cheaper strategy in one Qwen3-32B configuration) and matched, and sometimes slightly exceeded, the solve rate of LLM summarization; summarization lengthened trajectories in the two configurations the authors plotted for it; a masking window tuned for SWE-agent degraded sharply in OpenHands until retuned on a 50-instance slice; and the authors name their domain, with its long, verbose tool outputs, as a condition that favors masking, and both strategies use fixed turn-based triggers; a hybrid of the two cut cost a further 7 and 11 percent against masking and summarization alone [S3]. A controlled comparison on coding tasks (176 matched settings, four models, SWE-Bench Verified and Terminal-Bench 2.1, five context-management strategies, four window budgets) found that context management matters more as the budget tightens, mostly by preventing overflow failures, that staging rule-based elision before LLM summarization gave the strongest overall efficiency, and that making elided content recoverable added machinery models rarely used with no accuracy gain [S72]. Other designs (a deterministic eviction policy over agent-annotated episodes, a hierarchical summary DAG with pointers to every original, structurally lossless trimming that cut tokens by a mean of 20 percent in a single-user case study of 76 sessions) are reported by their own authors; the eviction paper is a first release whose accuracy differences from fresh sessions are within run-to-run variance, its baseline never faced context pressure, and R0 had flagged it as a lead [S1][S6][S7][S34].
- Warning the agent, not only the user, exists in GSD and, for some models, on the model platform, and its effect is unmeasured. GSD's context-monitor hook injects a warning into the agent's context when 35 percent or less remains and a critical one at 25 percent or less, waits five tool uses between warnings and lets a rise in severity bypass that wait; at the critical level, when GSD state exists, it tells the agent not to write handoff files and to ask the user to pause [S28]. R1 left the thresholds to R12 [S32]. The Claude Developer Platform gives Sonnet 5, Sonnet 4.6, Sonnet 4.5 and Haiku 4.5 an update after each tool call (`<system_warning>Token usage: 35000/200000; 165000 remaining</system_warning>`), and says newer models, including Sonnet 5.5, Haiku 5.5 and Opus 4.7 and later, do not receive these tags, and gives them an explicit budget through task budgets, which are in beta [S43]. OpenDev reports event-driven system reminders against instruction fade-out, which remind the agent of instructions, not of context use [S2]. In the Claude Code, pi, opencode and Codex pages I searched, I found no default warning to the agent about context use; Claude Code gives the user a live `/context` breakdown, and Claude Code hooks and pi extension events are places to build one [S22][S23]. I found no study of whether an agent warning changes outcomes (unsourced).
- Compaction can loop or fail, which matters for stop conditions (R15). Claude Code stops auto-compacting after a few attempts when one file or tool output refills the window [S22]; pi allows one compact-and-retry recovery attempt after a provider overflow error [S23].
- Compression can change behavior after the boundary. In a preliminary study, recurrent compression weakened the influence of recent interactions, increasing blocked actions, repeated exploration and instability across runs; the authors then propose a verifier-guided prompt optimizer, whose initial results are on AppWorld, which is not a coding benchmark [S45].
- Theory is thin: a formal study says compaction has received essentially no formal analysis and relates the budget for summary-style compaction to one-way communication complexity, which gives no practical threshold in the abstract (my inference) [S5]. A survey of over 1,400 papers places context management inside context engineering and gives a taxonomy, not a test [S19]; a 2026 survey of agent memory formalizes a write-manage-read loop with five mechanism families, including context-resident compression and policy-learned management [S56].

## Durable state and handoffs

- A new session starts with no memory, and hosts resume by transcript. Claude Code writes each session to a plaintext JSONL file, lets a user resume or fork it, and says each new session starts with a fresh window, with CLAUDE.md and auto memory as the cross-session channel [S22]. pi stores a session as a tree of entries with `--continue`, `--resume` and branch summaries [S23]. A handoff note is the workflow's own file, not a host feature.
- Anthropic's long-running harness uses files, not the transcript, to bridge sessions: an initializer session writes `init.sh`, a `claude-progress.txt` log and an initial git commit; every later session reads the progress file and `git log`, works on one feature, commits and updates the log [S20]. It reports two failures it fixed this way (trying to do too much and leaving a half-built feature undocumented, and a later session declaring the job done) and uses a JSON feature list in which agents may only flip a `passes` field, "as the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files" [S20]. That is the authors' experience, not a measured comparison, and it comes from a vendor [S20]. The same vendor recommends structured note-taking outside the context window (a NOTES.md or a to-do list) for iterative work with clear milestones [S21], and its platform docs link a memory-tool pattern for multi-session software development [S43].
- GSD's handoff is two files and a validation step. `pause-work` writes `.planning/HANDOFF.json` (position, completed and remaining tasks, blockers, pending human actions, decisions, uncommitted files, next action, context notes) and a `.continue-here.md`; `resume-project` reads STATE.md, prefers HANDOFF.json, checks its `uncommitted_files` against `git status` and flags divergence, and deletes HANDOFF.json after a successful resume so it is one-shot [S28]. R1 did not read how STATE.md carries across sessions; this answers part of that [S32].
- The study that compares handoff views head to head favors the raw trace on events. Handoff Debt interrupts a coding agent at set points in SWE-bench Verified tasks (75 source tasks, 181 handoff-point tasks, 724 takeover runs per successor model; predecessors from one model; successors Qwen, Gemma and Devstral, all 24 to 31 billion parameters) and compares four views: repository only, raw trace, summary notes and structured notes [S36]. Against repository-only takeover, the raw trace cut median agent events by 57 to 59 percent and the two note views by 20 to 46 percent, with prompt-token reductions of 42 to 63 percent across context-bearing views; solved-rate effects were smaller and model-dependent, the raw trace often gave the strongest solved-rate gains, and no single ranking of the views held across successors [S36]. The raw trace's first prompt had a median of 87k characters against 9.8k for summary notes and 10.0k for structured notes, and the authors call compact artifacts a practical middle ground [S36]. For the third successor the raw trace was ahead on every metric: 73 median events against 123 and 125, 1.66M prompt tokens against 2.30M, and a solved-rate gain of 14.9 points against 9.4 and 10.5 [S36]. Limits: tasks of 15 minutes to 4 hours, open models served locally, and a raw trace pasted into the first prompt, which is close to but not the same as resuming a live transcript [S36].
- Two further studies bear on raw history against compressed state. MemDev-Bench (555 base tasks, 4,869 historical tasks) is indirect, since it reuses earlier tasks' history from the same repository and measures steps, not an interrupted-task handoff: memory systems mainly improved localization and editing, memory also caused failures on otherwise solvable tasks through reuse without reassessing applicability, and directly providing raw historical trajectories reduced agent steps substantially more than memory systems did, which the authors attribute to process information that compressed memories omit [S57]. HSC-Bench (1,039 tasks, six receiving models; 300 repository tasks scored by line-F1 evidence recovery and 739 synthetic tasks on conversational state, tool use and reported file work) is the closest comparison to a transcript: it paired a recent transcript with structured state at the same visible token count, and structured state raised repository-evidence recovery for every receiver (line-F1 gains of 0.114 to 0.162 over recent transcripts, with intervals above zero) and overall continuation score for five of six receivers; on one receiver (GPT-5.4) it also beat narrative summaries by 5.42 points; the transcript there is a recent window of matching length, not a full trace, and the continuation track's full-history arm scored above structured state for every receiver (GPT-5.4: mean score 94.51 against 92.76 and completion 57.9 against 52.1 percent) [S60].
- Handoffs can erode constraints. Compression, plan assimilation, ownership deferral and similar handoff forms weakened blockers an upstream agent had established (76.7 percent deactivation for ownership deferral, 97.2 percent for multihop compression), while direct-state controls preserved every blocker; restoring the full blocker description raised recognition from 6.2 to 99.2 percent and cut forbidden action from 85.2 to 0.0 percent in fixed-artifact replays [S61]. A multi-agent privacy testbed found that summaries kept operational facts near ceiling while a 25-word budget cut boundary-marker survival from about 0.80 to about 0.57, and that explicit constraints reduced leakage below 15 percent [S62]. Neither tested a coding agent.
- A memory that follows the repository was tested on re-finding a root cause across sessions by one design paper. In Stratum's multi-session experiment on eight real bugs, a fresh agent that inherited a prior session's memory, written by a different model, identified the root-cause file in 21 of 24 trials against 6 of 24 for a retrieval-only baseline (Fisher p < 10^-4) at 4.5x lower median token cost [S37]. The authors sketch the system, the comparison is with retrieval and not with a transcript, and I read the abstract only [S37].
- Self-written handoff summaries can state policy the record does not support. In synthetic tool-use tasks with a ground-truth permission ledger, two AI readers confirmed unsupported restrictions in 1.2 and 2.4 percent of the readable summaries of two open-weight models and unsupported authorizations in 0.1 and 1.3 percent; for restrictions, a pre-specified replay test was not significant (p = 0.58) and a follow-up planned after it found a fragile effect (p = 0.027); replacing false approvals with neutral filler cut unauthorized actions from 24 to 7 of 120 held-out runs (post hoc; 17 to 11 of 48 on a later set); and a pre-specified prompt change cut unsupported restrictions from 5.0 to 1.8 percent of development summaries [S54]. The tasks are synthetic and the models open-weight. That a note should say where each permission comes from is my inference.
- Append-only, typed plain-text records recur as a design, and rewriting erodes detail. PROJECTMEM records issues, attempts, fixes and decisions as an append-only plain-text event log projected deterministically; its evidence is an author-run six-month self-study (3,228 events, 27 projects) that the authors say shows feasibility and not that warnings prevented failures [S51]. ACE reports that iterative rewriting of a context erodes details ("context collapse") and uses structured incremental updates instead, on agent and finance benchmarks, not coding tasks [S52]. Resilient Write adds six layers (pre-flight risk scoring, transactional atomic writes, resume-safe chunking, typed errors, scratchpad storage and task-continuity handoff envelopes) to an MCP file-write surface and reports a 5x reduction in recovery time against baselines; it addresses failed writes, not YAML style [S53].
- Practitioner and filesystem-memory reports add operating detail. One months-long Claude Code effort on a 633,000-line codebase reports a memory harness with decision and dead-end stores and conventions engineered to survive compaction, and 85 recorded failures in 78,933 hook invocations, none silent; it is a single project's account [S66]. A study of markdown-file memory found that organized stores roughly halve retrieval cost where material is large, while in its growth study organization eroded for all but the strongest management agent [S67]. One project reports a repository-resident constitution of conventions, 34 on-demand specification documents and 19 domain agents built over a 108,000-line C# system, with metrics over 283 sessions and four observational case studies of codified context carrying across sessions; it is observational and the abstract names no control arm [S68].
- External memory beat none in a multi-session coding benchmark. In DreamBench-SWE, where later tasks depend on non-inferable evidence from earlier sessions, no external memory passed 21 of 180 work units, deterministic verbatim event memory 82 of 180, a typed-plus-raw reference probe 83 of 180, and one hosted Mem0 configuration 97 of 180, and all three comparisons against no memory rejected after Holm correction; the comparison of literal storage with verbatim memory was nonconfirmatory, and the original fold's primary contrast was null [S69].
- Prose notes can keep a conclusion without the state that supported it. EA-Graph anchors each verification claim to the content that established it; on generated repositories with known ground truth (42 sessions, seven worlds), the anchored memory outscored prose notes and no persistent memory in all seven worlds with the smaller model (exact paired Wilcoxon p = 0.0156 each), while with the larger model it was perfect but frequent control ceilings left the preregistered contrasts non-significant [S44]. The task there is to classify prior claims after drift, not to resume work, and the authors call the result a bounded claim [S44].
- Resuming after other work costs resolution. Switch-SWE (200 focus tasks from 19 Python repositories, 400 matched session specifications) finds that interleaving other unfinished tasks from the same repository lowers focus-task resolution by 11.5 points on average across seven coding agents (6.0 to 15.0), with cross-task requirement confusion and loss of task state as recurring behaviors; the authors' plug-in module that selects task-relevant history and keeps concise task-state summaries improved completion by 5.5 to 15.5 points on OpenCode across the evaluated models [S46].
- Delivery may matter more than storage. In a controlled evaluation on one coding task, an agent with a pre-seeded memory store made 0 memory operations in 114 turns; ten facts held only in conversation were absent from 106 of 108 compactions, while the same facts injected by the harness arrived intact through all 138 compact-resumes; and 39 percent of intra-session re-reads bought again content paid for before a compaction boundary [S38]. The authors argue the harness, not the agent, should own memory delivery; I read the abstract only [S38].
- A shared event log is the design that crosses agents. ESAA-Conversational captures visible turns into an append-only `activity.jsonl` and projects `handoff.md`, `state.md`, `decisions.md` and `tasks.json` deterministically, so a different agent can take over; its evidence is a self-referential case study of 570 events [S9]. ESAA lets agents emit only structured intentions that a deterministic orchestrator validates and persists, with replay verification by hash, shown on two case studies, and the abstract names no baseline [S10]. Version-controlled session state appears as snapshots, branches and trimming in a DAG [S7] and as COMMIT, BRANCH and MERGE operations over a versioned file system, where the authors claim over 13 percent relative improvement on SWE-bench Verified against long-context baselines; I report it as the authors' claim and did not open their code [S13].
- Keeping the raw transcript and searching it is competitive for strong models on one chat benchmark. On one conversation (419 turns, 152 questions) with one run per cell, one designed memory system (Mem0) beat full context only with the weakest model, and with the strongest model a coding agent (pi) scored 99 percent for less than half the cost of full context [S11]. Part of that lead came from photo captions that only the agents could read (the memory methods were given the turn text only); on the 88 questions whose evidence has no photo, pi and full context differ by one answer [S11]. This is a chat-memory test, not a coding task, and it says nothing about resuming a long coding session.
- A format-preserving writer is a requirement with first-hand evidence here. `bp-timing.sh` rewrote `specs/state.yaml` with a YAML dumper that dropped the document start, comments and line wrapping and turned Preflight red (BUG-001), and `record-cycle-time.sh` removed the `---` line from `specs/execution-status.yaml` (BUG-004) [S35]. They are two different tools that each wrote one file in a style the repository's lint rejects: they show the need for a format-preserving writer, not that several writers caused the fault. R2 drew the same conclusion from BUG-001: write the state file with a format-preserving writer or from one tool only [S33]. The single-writer half has design precedent: ESAA routes every write through one orchestrator [S10], ESAA-Conversational adds a write-path lockfile [S9], beads' default embedded mode is single writer [S26], and Backlog.md asks users to prefer its commands over hand-editing task files so field types and metadata stay consistent [S27].
- Persisted state goes stale and is trusted. An audit of coding-agent trajectories identified candidate failure chains in which invalid stored records are reused as premises, and a framework that diagnoses and repairs them reached 93.3 percent correctness against 38.7 percent for the baseline on 150 cases under corrupted state; the number belongs to the full pipeline (find the decision-critical records, verify them, ground the evidence, persist the repair, replan, check the action), removing its resolution or persistent-repair component cost 78.7 and 76.7 points, and the corruption was built by the authors [S14]. GSD's check of `uncommitted_files` against `git status` is the same idea in a shipped workflow [S28]. A single case report documents Claude Code compaction summaries recording partial output from timed-out commands (exit code 143) as confirmed results that later sessions inherited without re-verification [S73].
- Durable files are an attack surface (R11). Project memory files load at session start as trusted guidance; in one small study (36 tasks, three agent and model setups), crafted malicious memory files changed the rate of secure completions by -8 to +6 percentage points with no consistent pattern, agents differed in whether they told the developer about the file, and flagging the file as an attack did not reliably protect the code [S17].
- Plan files kept in a repository are rare in the wild: a screen of 36,710 repositories found 85 Markdown plan files in 10 of them [S18]. That describes tool-specific plan directories, not workflow state files.

## Git-backed tracker or plain files

- R5's verdict on H8 is the starting point: `SKILL.md` and a conditionally read `AGENTS.md` are portable, while subagent, hook and plugin formats differ per host [S29]. The hosts keep their own memory in plain files, such as Claude Code's CLAUDE.md and Markdown auto memory with a `type` frontmatter field [S22]. Claude Code also has a built-in task list (`TaskCreate`, `TaskGet`, `TaskList` and `TaskUpdate`, the last of which updates status, dependencies and details, plus `TaskCreated` and `TaskCompleted` hooks), provided by default only on Opus 4.7, Sonnet 4.6, Haiku 4.5 and earlier models; a list can be shared across sessions by setting `CLAUDE_CODE_TASK_LIST_ID`, which names a directory under `~/.claude/tasks/`, outside the repository [S22]. I found no equivalent in the pi, opencode or Codex pages I searched. R0 raised this comparison as candidate 5 [S34]. This section compares the storage format only. Where state lives when two hosts share a repo belongs to R13.
- beads is git-backed in transport, not in format. It calls itself a persistent, structured memory that "replaces messy markdown plans with a dependency-aware graph"; the data live in a Dolt database under `.beads/`, sync goes through `bd dolt push` and `pull` against `refs/dolt/data` on the git remote, and `.beads/issues.jsonl` is an export [S26]. So the primary store is not a text file that a commit diffs line by line (my inference from the README's description of the layout).
- beads has the heaviest schema of the designs I read. Its README describes a schema version check at open time, a `bd migrate schema` step, and an example error "database is at v45, binary knows up to v42", plus a semantic "memory decay" that summarizes old closed tasks [S26]. That is a database engine in place of text files, plus a bespoke versioned schema with migrations, which H8 rules out.
- Backlog.md keeps every task as a plain `.md` file in the repository, with no server or account, and leaves completed tasks in git as a record; it frames one task as one context window and one pull request [S27]. The README I read does not give the file schema (fields and frontmatter), so how bespoke that schema is stays unsourced beyond the README's claims of milestones and dependencies [S27].
- Plain files still carry a schema. The harness feature list fixes a `passes` field [S20], GSD fixes a HANDOFF.json shape [S28], and ESAA fixes event types [S10]. "No bespoke schema" cannot mean no field names; the evidence supports no bespoke storage engine and a small, documented set of fields in Markdown, YAML or JSON (my inference from S20, S26, S27 and S28).
- Both trackers are vendor READMEs and no source compares them, or either against plain files, on agent outcomes; the nearest study tests memory systems, not trackers, and finds 11 of 12 solver and system pairings no better than no memory on resolution, although all four systems cut one solver's tokens and steps markedly [S12]. Both also support use without committing to the repository (a stealth mode in beads, a no-git init in Backlog.md) [S26][S27].

## Avoiding re-investigation

- Earlier verdicts stand and are not redone here. R8 refined H3: stale instructions are followed, and the check itself is untested [S31]. R6 refined H11: the supported unit is a dependency community, and re-learning cost has not been measured directly [S30].
- A context file has not been shown to reduce effort. In the controlled study that separates LLM-generated from developer-provided files, context files did not significantly change task success; LLM-generated files raised cost by 20 and 23 percent on average in its two benchmark settings, developer-provided files improved performance by 2.4 percent on average (p = 21 percent, not significant) and beat the LLM-generated ones, at up to 19 percent more cost; instructions were followed and repository overviews were not helpful; and the number of steps before the agent first touched a file in the final patch was generally lower without context files [S16]. Two later studies measure different things: on 10 repositories and 124 pull requests, an AGENTS.md was associated with a 28.64 percent lower median runtime and 16.58 percent fewer output tokens at comparable completion [S41], while a 288-run ablation on 17 tasks from 3 repositories with Claude Code and Codex found no measurable change in correctness (bounded to 10 to 15 points), with failures traced to implementation skill and not to missing repository knowledge, and its abstract reports no effort measure [S42]. Hosts budget these files: Claude Code advises under 200 lines per CLAUDE.md and Codex stops concatenating AGENTS.md at 32 KiB by default [S22][S25]. This is consistent with R8 [S31].
- Context files also rot. An existing README and wiki checker, applied unchanged to 612 AI configuration files in 356 repositories, found stale code-element references in 23.0 percent of the repositories; in a manual check of 50 flagged elements, 32 (64 percent) were genuine and the rest were false positives or ambiguous, and one author inspected the sample, the authors name two opposing biases in the 23.0 percent figure, and they read it as a feasibility signal, not a prevalence; per element, 230 of 18,048 verified references (1.27 percent) had gone stale [S15]. R8 covers four further studies of stale and mis-configured instruction files [S31].
- Retrieval at run time is the vendor-recommended alternative to up-front context. Anthropic recommends lightweight identifiers such as file paths with `glob` and `grep` for just-in-time loading, and sub-agents that keep search detail in their own window [S21]; Claude Code does the same with subagent research [S22]. Those are design advice, not a measured saving.
- The avoidable cost may exist, but the evidence is directional and memory systems did not deliver it in resolution. In VibeMemBench (111 targets from 90 repositories), each target was kept only because injected history experience improved its outcome in a reference setting; injecting that verified experience raised resolution on four of five held-out solvers by 1.1 to 4.5 percentage points and lowered steps on all five, but the authors say the intervals cross zero, so the gains are directional, and the solver pool omits proprietary frontier models [S12]. With four existing memory systems (Mem0, SimpleMem, MemoryOS and A-MEM, each injecting one top-ranked record before the solver started), 11 of 12 solver and system pairings did not beat a no-memory baseline in resolution, although all four cut one solver's tokens and steps markedly [S12]. What helped was verified, task-specific experience, not a general memory.
- What is passed forward matters more than whether it is retrieved. On SWE-ContextBench Lite, injecting the same experience as a summary or a raw trajectory, even when oracle-retrieved, did not help, while a phase-structured document injected at the start, with the costlier implementation record withheld until a gate detected the agent struggling, improved resolution from 24.9 to 27.6 percent at 17 percent lower cost (the authors' own framework) [S63].
- Losing context causes re-exploration that traces show. In the eviction paper's own runs, a budget of about 50,000 tokens cut inference cost by up to 3x but forced eviction of still-relevant exploratory content, and the agent re-explored the same codebase regions, raising wall-clock time per task by up to 2x while accuracy was kept; this is a trace observation in a first-release preprint [S1].
- Codebase maps: I found no study of repository maps for coding agents that I could use. Query 13 returned a code-index serving system (arXiv:2607.25431) and a repository-improvement paper that I did not open, S16 found repository overviews in context files not helpful, one study found that better documentation did not beat the issue alone for resolving real issues across two model families and ten repositories when the source was present [S64], and the Backlog.md README advertises an architecture-map integration (Groma.md) that is kept up to date automatically, which is a product claim without evidence [S27] (unsourced beyond that).
- Dispatch per subsystem (R6) is one way to limit re-learning, and no source here compares it with passing verified experience forward. Across sessions, two abstracts measure rediscovery, Handoff Debt and Stratum's root-cause experiment, and one reports that 39 percent of intra-session re-reads bought content again after a compaction boundary [S36][S37][S38]. I found no study that measures re-investigation across a long task sequence in one repository with a state file as the memory (unsourced).

## Mechanisms compared

| Mechanism | Problem it solves | Where state lives | Triggered by | Evidence |
| --- | --- | --- | --- | --- |
| Compaction | A session outgrows the context window | A summary replaces older messages in the session | Harness at a token threshold or after idle time, or the user | [S22][S23][S24][S3][S4] |
| Context eviction | The same, without a model call | Episode graph in the harness; evicted content leaves the context | Harness policy when a budget is exceeded | [S1] |
| Observation masking | Old tool outputs dominate the history | Placeholders replace old observations in the history | Harness, after a fixed window of turns | [S3] |
| Handoff note | The next session has no memory | A file in the repository (GSD uses two; this repository uses a state.yaml block) | The user or agent at a pause; read at resume | [S28][S20][S35][S36] |
| State file | Position, decisions and next step must outlive a session | A plain file in the repository | An agent or a tool, at milestones | [S20][S28][S35] |
| Git-backed tracker | Dependency-aware tasks shared across agents | A Dolt database under .beads with a JSONL export, synced over a git remote ref | The agent, through the tracker's command-line tool | [S26] |
| Host task list | Planning and tracking multi-step work in a session | A named directory under ~/.claude/tasks, outside the repository, when a list ID is set | The model, through the task tools | [S22] |
| Context file | Project conventions every session | AGENTS.md or CLAUDE.md in the repository | The harness loads it at session start | [S22][S25][S16] |
| Event-sourced log | Handoff between different agents | Append-only activity.jsonl with projected handoff.md and state.md | Hooks and watchers capture; a CLI projects | [S9][S10] |

## Verdicts

- H3: refined - R8's verdict stands (stale instructions are followed, the resolution check itself is untested) and four further studies of stale and mis-configured instruction files are covered in R8 [S31]. R12 adds three adjacent results, none a test of a command-resolution lint: an existing consistency checker run unchanged on 612 AI configuration files found stale references in 23.0 percent of 356 repositories, with 64 percent of 50 inspected flags genuine [S15]; a pipeline that diagnoses and repairs stored records reached 93.3 percent against 38.7 percent on the authors' own 150 constructed cases [S14]; and GSD already validates a handoff's `uncommitted_files` against `git status` [S28]. Context files raised cost without a significant gain in the study that separates LLM-generated from developer-provided files (developer-provided files helped by 2.4 percent, not significant, at up to 19 percent more cost) [S16], while a smaller study found a lower runtime with an AGENTS.md [S41] and another found no change in correctness [S42].
- H8: refined - R5's two-part verdict stands [S29]. On storage, the hosts keep their own memory in plain files, and Claude Code has a host-native, dependency-aware task list stored outside the repository [S22]; the git-backed tracker keeps its primary store in a Dolt database with a versioned schema and migrations [S26], while the plain-file designs are Markdown, JSON or JSONL [S27][S20][S9]. Every plain-file design still defines fields, so the supported reading is plain-text files with a small documented field set, not a database engine and not no schema (my inference); no source compares either bet on agent outcomes [S12].
- H11: refined - R6's verdict stands [S30]. New evidence: injecting verified experience from repository history lowered steps on all five held-out solvers and raised resolution on four, with intervals crossing zero [S12]; in the same study four existing memory systems did not beat no memory on resolution in 11 of 12 pairings, though they cut one solver's tokens and steps [S12]; context-file overviews did not help [S16]; strong coding agents searching raw history held their own on one conversation with one run per cell, where part of their lead came from photo captions [S11]; and a fresh agent that inherited a prior session's memory found a root-cause file in 21 of 24 trials against 6 of 24 for retrieval-only (abstract only, the authors' own system) [S37]. The lever looks like what is passed forward (verified, task-specific experience), not the unit of dispatch, a second benchmark found raw trajectories cut steps more than memory systems and that memory reused without a check caused failures [S57], a framework that injects a phase-structured document at the start and withholds the costlier implementation record until the agent struggles improved resolution where plain summaries and raw trajectories did not [S63], and no source compares subsystem dispatch with task dispatch, so the evidence here is indirect and leaves R6's verdict unchanged.
- H24: refined - the files half is documented practice: a progress file with git history and a JSON feature list bridge sessions [S20], hosts re-inject disk files after compaction while summarizing conversation content away [S22], and event-sourced projections carry state across agents [S9][S10]. One coding-task evaluation found that facts held only in conversation were absent from 106 of 108 compactions while harness-injected facts arrived in all 138 resumes, and that voluntary memory use was near zero (abstract only) [S38]. The format-preserving half is shown to be needed by BUG-001 and BUG-004, and the single-writer half rests on design precedent, not on a measured fault [S35][S33][S10][S26][S27]. In a multi-session coding benchmark, verbatim event memory passed 82 of 180 units against 21 of 180 with no memory, level with a typed-plus-raw probe (83 of 180), although the highest arm was a hosted Mem0 configuration (97 of 180), so the result does not favor files over a service [S69], and one observational project reports repository-resident conventions and specifications carrying across sessions [S68]. No study shows that files beat the transcript, raw-history search is competitive for strong models on one chat benchmark [S11], and a raw trace beat notes on effort in the one handoff study [S36].
- H25: refined - the first half holds in practice: pi, Claude Code and Codex each expose a compaction trigger that a user can move (Codex both a token and a percent trigger, Claude Code also an idle trigger), while opencode exposes an on/off switch and a reserve buffer and no documented threshold [S23][S22][S25][S24]. The second half, warning the agent, exists in one workflow with fixed 35 and 25 percent remaining thresholds [S28] and, on the model platform, as per-tool-call token-usage updates for some models and not for newer ones [S43]; OpenDev's reminders concern instructions, not context use [S2]. No host page I searched warns by default, no study measures the effect, and the threshold evidence is mixed: one study found no universal context-length threshold, another found the threshold did not measurably matter for two 1M-context models but did for the smallest window, and a small-model runtime found its gain only when compaction triggered early enough to leave room [S8][S39][S70]. What compaction keeps matters more than when it fires: violations of a policy agents obeyed in full context rose from 0 to 30 percent after compaction and fell back to 0 with pinning in one benchmark, and later studies found constraints dropped in agentic and repair tasks [S4][S39][S40]; preliminary work adds that compression can increase repeated exploration [S45], designs that learn when to compact or compact deterministically report gains from their own authors [S47][S49][S50], compaction can launder untrusted text into trusted memory where roles are flattened [S48], and keeping a rule in the summary does not by itself stop violations [S58][S59].
- H26: refined, not refuted - the claim as stated, that a note beats resuming a transcript, is not supported, and the evidence runs the other way on effort. In Handoff Debt the raw trace cut median agent events by 57 to 59 percent against 20 to 46 percent for summary and structured notes, and it was ahead on events for all three successors and on prompt tokens for the Devstral successor (1.66M against 2.30M), roughly tied for Gemma (300k against 319k and 317k) and behind for Qwen (811k against 602k and 660k); the paper reports no single ranking of the views across successors, and I found no pairwise test of raw trace against notes in the passages I read [S36]. The notes' advantage is first-prompt size (about 10k characters against 87k) [S36]. MemDev-Bench is indirect (reuse of earlier tasks' history, measured in steps) and points the same way for raw trajectories against memory systems [S57]. I do not call it refuted because both tests compare a note or memory with a trace pasted into the prompt, not a live transcript, because they use short tasks and small or varied models (24 to 31 billion parameters in S36; notes written by one model at temperature 0 with a 1,600-token cap, note-writing cost excluded), and because the evidence depends on size: at equal token count a structured note beat a recent transcript window in HSC-Bench (on repository evidence recovery for all six receivers, and on 739 synthetic continuation tasks for five of six), but the full record beat the note in both tests that used it (the full raw trace in S36 on events, and the full-history arm in S60, GPT-5.4 mean score 94.51 against 92.76) [S36][S57][S60]. REM, in a different setting (a related past task, resolution not steps), found that injecting a raw trajectory did not raise resolution [S63]. Handoff notes remain the practice in Anthropic's harness, GSD and ESAA-Conversational, and in this repository [S20][S28][S9][S35]. Self-written summaries can add unsupported policy, drop constraints and go stale [S54][S4][S14], and handoffs can weaken established blockers unless the state is carried directly [S61], so a note should be checked against the repository at resume, as GSD does [S28], and anchored to repository state [S44]; concise task-state summaries helped resumption after task switching (the authors' own module) [S46]. What survives is a narrower claim: a bounded-size, verified note is a reasonable trade against a raw trace, not better than one.

## Implications for weftwork

- Do not build compaction. Configure the host's trigger and use the host hook points to re-inject what must survive: the `SessionStart` hook for the `compact` source in Claude Code, the `session_before_compact` event in pi, and the compaction hook events Codex lists [S22][S23][S25]. Governance rules and the current handoff are the first things to keep out of the lossy path [S4], and re-injected text should keep its message role so that untrusted content is not laundered into instructions [S48].
- Keep durable state in plain repository files written by one format-preserving tool, and treat that tool as a requirement for R13 and the v1 spec [S33][S35]. Keep the field set small and documented.
- Write the handoff for a session with no memory, verify it against the repository at resume (branch, `git status`, files named) before acting, as GSD does, and expect it to trade some rediscovery effort for size against a raw trace [S28][S14][S36].
- Do not adopt a database-backed tracker for the first release without a failure that plain files cause; R13 decides where state lives for two hosts [S26][S27] (proposal for the synthesis).
- Warn the agent about context use with a small hook, with host- and model-specific thresholds and no fixed global number; the model platform already does a version of this for some models and offers task budgets for newer ones [S28][S8][S43]. The hook costs little and its effect is unmeasured, so R10 should test it.
- Keep context files short and about non-standard practice, as R8 concluded [S31] and S16 supports; the evidence on effort is mixed [S16][S41], and S42 found no change in correctness.

## Earns its place vs ceremony

- Constraint pinning (keeping rules out of the summary): earns its place provisionally. The mechanism is shown by a deletion ablation, the effect reproduces in framework context managers and the fix is cheap, but the main grid is 9 tasks times 3 repetitions in a simulated sandbox, pinning needs a rule that can be quoted, an operator-impersonation notice in the recent context still broke it, Claude Code already re-injects the root CLAUDE.md from disk [S4][S22], retaining a rule did not stop violations in a pi-based benchmark [S58], and type-aware retention beat a single-shot compactor on rule preservation [S71].
- A format-preserving state writer: earns its place. It answers two failures that happened in this repository; the single-writer half rests on precedent, not on a measured fault [S35][S10][S27].
- A context-monitor hook warning the agent: unproven, cheap to try. Keep it only if R10 shows an effect [S28].
- A handoff verified against the repository at resume: earns its place, because stored state goes stale [S14][S28].
- A handoff note in place of a raw trace: earns its place for size only; the raw trace cut effort more in the one direct test, and MemDev-Bench is indirect [S36][S57]; HSC-Bench favors structured state over a recent transcript window of equal length but scored its full-history arm higher [S60].
- Two handoff files for one handoff (HANDOFF.json plus .continue-here.md): ceremony until a failure shows one file is not enough [S28].
- A database-backed tracker: ceremony for the first release, for want of evidence that plain files fail [S26][S27].
- LLM summarization as the default compaction: unproven. Simple masking matched it on one domain that favors masking, and another study found no method beat default self-summarization, so do not assume either is needed [S3][S39].
- Repository overviews in context files: ceremony; they did not help in the one controlled study [S16].
- A fixed numeric compaction threshold set by weftwork: ceremony; hosts own it, and no number is supported [S8][S22].
