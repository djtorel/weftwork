## Completion detection

How a loop decides it is done. R4 and R7 refined H1 first; this section adds loop-level evidence and the two built-in checks I could read. Each bullet is a documented or reported behaviour; none was tested here.

- The model's own claim of done is not dependable evidence. In tau2-bench, 45 to 48 percent of failures in the single-control domains were false successes (the agent asserted completion while the state showed otherwise); in AppWorld, which the paper calls coding agents, 1,425 of the 1,879 failed trajectories that carried an explicit status claim claimed success (75.8 percent; two agent architectures, released outputs of GPT-4o, GPT-4-Turbo, LLaMA-3 and DeepSeekCoder, and 3,120 trajectories with no status excluded). LLM judges did no better than 0.65 AUROC on tau2-bench and 0.54 on AppWorld API traces [S7].
- In long coding runs, voluntary early exit is a minority of the labelled failures. In SWE-Marathon, premature termination was 7.6 percent and poor self-verification 4.0 percent of 526 agent-attributable failures, with Codex on GPT-5.5 at the highest premature-stop share (15 percent) and Claude Code on Claude Opus 4.7 at the highest poor-self-verification share (20 percent); the labels were assigned by GPT-5.5 reading the trajectories, and 79 trials were excluded as unclassifiable [S11].
- The model's termination judgment can be pushed around. Injected text made eight agents (ReAct-style, simulated tools, 60 GAIA tasks) run 2.33 times the steps on average with static prompts and 3.57 times with the adaptive attack, peaking at 25 times; verifiable tasks resisted better (one attack scored 3.58 on a technology task and 1.68 on a maths task). The proposed defence, an independent check of the agent's progress against objective completion criteria, is untested [S6].
- Judgments are not decisions. Seven agents called a failing source's results useless 97 to 100 percent of the time, yet unaided Qwen3-8B answered after five such judgments on 1 of 292 questions and the others on at most 7 percent; this is retrieval question answering with simulated failures, not coding [S16].
- Ralph's dual exit check: the loop exits only when `completion_indicators` is at least 2 (a heuristic over natural-language patterns in the model's output) and the model writes an explicit exit signal (`EXIT_SIGNAL: true`); with the signal false or missing it continues. Other exits are all `fix_plan.md` items checked, two consecutive done signals and three test-only loops. Both parts of the check come from the model or from pattern-matching its text; neither is a command the harness watched exit 0 (my reading of the README). The README reports no outcome data and I did not read the code [S17]. R0 recorded the same design with no outcome data (R0) [S24].
- No study varies ralph's dual exit check. A ralph-style loop appears in one paper as the baseline: it ended only when an external evaluator judged the design valid and the agent was confident it could not improve it, within 30 steps; the paper compares design quality across three architectures and does not vary the exit rule [S12].
- Claude Code's `/goal` moves the check to a separate small fast model that reads the conversation and returns met, not yet met or impossible; the evaluator does not call tools, so it judges only what the agent has surfaced in the transcript. A Stop hook can instead run a script for a deterministic check [S20][S19].
- Bounded Loops is the design that keeps the claim out of the decision: no node reaches done without a verdict from a gate the worker cannot write to, and the worker's own claim appears in no guard (proved from control flow; the claim is recorded and never read). R13 read the same paper for the gate verdict before done (R13) [S3][S29]. The paper reports 47 gates with vacuity defects in its authors' own 69-loop catalogue (as R13 read it), so a gate is only as good as its test [S3].
- A survey lists six convergence criteria used by code-generation systems (test-gated, security, performance, score-based, consensus and implicit) and calls implicit convergence, a fixed number of stages or iterations with no objective quality criterion, the most prevalent pattern and the most significant gap; this is the survey's reading of the literature, not a measurement [S4].
- A hand-coded count of 50 catalogued loops found 74 percent naming terminal states and 70 percent verifying in the autonomous zone (deterministic or rule checks); the author calls it a descriptive coding of one public catalogue, not a random sample, with no causal conclusion [S1].
- R4 and R7 qualify H1: a passing declared command is only as good as its scope, and R7 records that 7.8 percent of SWE-bench patches count as correct while failing the developer suite (R4, R7) [S25][S26].

## Budget, rate and context ceilings

What stops a run by cost, count, time or window size. R9's H15 verdict is the baseline; R12 and R13 supply the context and enforcement inputs.

- R9 recorded Claude Code's dollar cap and turn cap in print mode, opencode's step cap and Codex's experimental rollout token budget, and found no documented escalation log (R9) [S27].
- Claude Code 2.1.321: `--max-budget-usd` stops the run once estimated spend reaches the cap (print mode only); the check uses a client-side estimate, spend can pass the cap, and subagent spend counts toward it. `--max-turns` limits agentic turns (print mode only, no limit by default). The installed `claude --help` lists `--max-budget-usd` but not `--max-turns`; I ran neither [S18].
- A turn or time bound on a Claude Code goal is a clause in the goal text (the docs give "or stop after 20 turns"); the evaluator model judges it from the conversation. It is a model-judged bound, not a counter. The status view shows turn count and token spend [S20].
- Codex 0.167.0: `goals.max_goal_token_budget` sets the default and the largest token budget a goal can request, and without it goals have no configured limit; `features.goals` is on by default. A separate `features.rollout_budget` is experimental and off by default, tracks a token limit and sends reminders at remaining-token thresholds; the page does not say what happens at the limit. The two help screens list no turn, iteration or budget flag (R9 recorded the rollout budget) [S21][S27].
- opencode v1.19.5: `steps` caps an agent's agentic iterations; at the limit the agent gets a system prompt to reply with text only, summarizing its work and the remaining tasks. Unset, it iterates until the model stops or the user interrupts [S22].
- pi 1.5.0 (docs at commit 5c37d3be1c3c): the settings and usage pages list thinking-token budgets, compaction settings and agent-level retry (3 attempts by default for transient failures), and no step, turn or spend cap; I read only those two pages, and Escape stops the current task [S23].
- Context ceiling. R12 recorded that Claude Code stops auto-compacting after a few attempts when one file or tool output refills the window, and that pi allows one compact-and-retry recovery after a provider overflow error (R12) [S28]. Codex has `model_auto_compact_token_limit` and pi `compaction.reserveTokens` (16,384 by default) as compaction triggers; these start compaction and are not stop conditions [S21][S23].
- Rate limit. Ralph has an hourly call limit (100 by default) and a token-per-hour limit, both reset hourly, and waits or exits on the provider's 5-hour limit; Claude Code fires its StopFailure event on a rate-limit error and `/goal` pauses on one and resumes when the limit resets. A rate limit slows a loop and does not end it, and I found no study of rate limits as a stop condition (unsourced) [S17][S19][S20].
- Wall-clock ceilings do end failed runs. In SWE-Marathon, timeouts (the agent ran the full wall-clock budget without a clean submission, including reasoning loops, stuck states and hangs) were 31.4 percent of the 526 agent-attributable failures; the labels are model-assigned [S11].
- A ceiling can be a licence to spin. In a production incident study, a verifier agent made the same call 54 times over 11 minutes, every call successful, and stopped only when a human killed the run; the step budget, sized from the workload, "bought a proportionally large licence to spin" [S14].
- A ceiling has to cover the whole feedback path. A static analysis of 6,549 Python agent repositories (at least one star) reported 74 findings, of which manual review confirmed 68 across 47 projects (91.9 percent precision): a feedback path that can reach costly operations with no effective bound. The paper notes that a model-controlled exit "is not a deterministic bound", that an inner cap does not cover an outer cycle, and that it found 7 false negatives; these are missing-bound patterns confirmed by code review, not observed runaway runs [S5].
- Bounded Loops enforces its ceiling inside an attempt: the worker turn is clamped to the remaining budget and a reserve is partitioned out of it so a hard stop leaves a written handoff. The implementation declares nine bounds and a kill switch; on one catalogue loop the predicted bound use matched the observed use in 9 of 9 cases against a ceiling of 10 attempts. R13 recorded this ceiling as one of two enforced stop conditions (R13) [S3][S29].
- Budget awareness. A Budget Tracker that shows the agent its remaining tool-call budget each turn helped web-search agents (the process stops when any budget is exhausted); the paper found that raising the budget alone did not improve performance. It is not a coding study [S13]. In BAGEN, five frontier models' own estimates of the remaining budget were over-optimistic, and Qwen-7B estimators trained with SFT and RL on Sokoban reached 47 percent interval coverage at best, so nearly half the intervals still missed the true remaining budget [S15].
- A stated budget moved the 7 to 8 billion-parameter models' stops to the deadline without making them stop on evidence, and a larger model that stopped earlier with a stated budget made 46 percent more tool calls for no gain when the budget doubled [S16].

## Circuit breakers and no-progress detection

What stops a loop that runs but gets nowhere. The one coding-loop design with a breaker is ralph's; the evidence on breakers is one incident study, one retrieval study and mixed early-stop results.

- Ralph's circuit breaker opens after 3 loops with no file changes, 5 loops with the same error, or an output decline above 70 percent; it waits 30 minutes, then half-opens. R0 recorded the breaker with no outcome data, and the README reports none; the thresholds are defaults and I found no study of them (unsourced beyond the README) (R0) [S17][S24].
- An observational study of one production platform (147 incidents, 81 runs, diagnosed by the team that built it) found that the dominant failure was "a sequence of individually successful actions that stops changing the outcome", which an error-rate breaker cannot see. The platform now runs progress-based breakers at five nested scopes, among them four byte-identical tool calls and four session turns with no new grounding or mutation [S14].
- The same study found that a progress signal can be wrong by construction: a stall detector hashed the failing check's name, which stays the same whether the agent has fixed four defects or none, so it tripped on the third repair round regardless of progress and one run fell from six of six components to three. Twelve incidents had the enforcement layer blocking correct work, the costliest taking 107 agent turns with no accepted write. The authors say the primitives' effectiveness is unmeasured [S14].
- A harness-enforced no-progress stop worked in a retrieval setting: finishing after five consecutive results the agent judged useless raised success on a failing source for every model tested and held the stopping point when the budget doubled; the threshold was chosen for sources that recover after at most three failures, and it can give up just before a later recovery. The environment is simulated retrieval, with mostly open models [S16].
- AgentLoop stops tool-augmented agents when stability and low-gain signals over neighbouring rounds say further rounds add nothing: total token cost fell "by up to 88.44 percent" and average depth "by up to 76.85 percent" (the abstract says service invocations) against high-cost baselines, on two backbones and three tool-use datasets (ToolBench, Open-Agent-Trace and GAIA), none of them a coding benchmark. Its stability test counts a paraphrase as a change, and disabling its slot-control path raised depth from about 3.4 to 7.43 and cut accuracy from 0.938 to 0.612 on ToolBench [S10].
- Bounded Loops has a no-progress window beside the attempt limit, and the paper proves the window can only tighten the bound [S3].
- A survey describes two stagnation rules in code-generation systems: PairCoder switches to the next plan when the same buggy code or feedback recurs, and ChatDev stops when two consecutive rounds produce identical code or after 10 rounds; these are the survey's descriptions, not readings of the systems [S4].
- Claude Code gives its own Stop-hook loop a breaker: after eight consecutive continuations from stop hooks it overrides the next block and ends the turn, resetting the count when Claude calls a tool. `/goal` stops its loop with a warning when Claude answers the evaluator with no tool use for several turns in a row, and it pauses after three automatic retries [S19][S20].
- Learned early stopping is mixed. A study of 147,002 coding-agent traces found within-task discrimination near chance (AUC about 0.50) at 5k to 20k tokens, and uninterrupted continuation had higher solve rates at lower mean token cost than both restart policies in all four settings at a 75k-token cap and in 216 of 224 budget-threshold configurations overall; its policy tests were restarts, not abort-only stops, in four open-weight settings [S8]. StopLoss, an abort-only monitor trained on outcomes, cut cost per retained solve against full execution by 4.5 percent on SWE-bench Verified with one executor (GPT-5.6 Luna) while keeping 99.0 percent of successful runs, and by 24.2 percent (72.2 percent kept, Luna) and 30.6 percent (91.6 percent kept, Claude Sonnet 4.6) on a three-repository Pro subset; it was trained on GPT trajectories [S9]. In BAGEN, stopping when the model predicts the task infeasible saved 28 to 64 percent of tokens on failed runs for 1.6 to 4.2 points of overall success, most on SWE-bench and Warehouse and near zero on Search-R1 [S15]. The three use different signals, policies and baselines, so none refutes another.
- I found no study that compares thresholds for a coding-loop breaker, and none that tests ralph's design (unsourced).

## Host stop controls

What each host gives a loop to stop it, read from the docs at the versions named in Method. R5 compared hooks and permissions per host and has no stop or budget row; R9 and R13 recorded part of what follows [S30][S27][S29].

- Claude Code 2.1.321 Stop hook: it runs when the main agent finishes responding; exit code 2 sends Claude back to keep working; `stop_hook_active` is true when it is already continuing because of a stop hook. Claude Code ends the turn after eight consecutive continuations, resets the count when Claude calls a tool, and `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises the cap. R9 and R13 do not mention the cap [S19].
- A Stop hook that cannot start does not hold the agent: the `onFailure` field has no effect on Stop, and a Stop hook that exits 2 with only "No such file or directory" on stderr is treated as a non-blocking error, so (my reading) the turn ends with the gate not run. R13 read this as a Stop gate that cannot start not stopping a loop (R13) [S19][S29].
- Claude Code `/goal` is a wrapper around a session-scoped prompt-based Stop hook: the goal clears when a model confirms the condition, when it judges it impossible, or when a turn fails on an error the user must fix; evaluation is by the small fast model and costs are described as typically negligible next to main-turn spend [S20].
- Claude Code print mode adds `--max-budget-usd` and `--max-turns`; the installed `--help` shows only the first [S18].
- Codex 0.167.0 has persisted goals with automatic continuation on by default, an optional goal token budget and an experimental rollout budget with reminders. I found no page that says what ends a Codex goal (the docs index has no goals page), so its completion rule is unread (unsourced) [S21].
- pi 1.5.0: Escape stops the current task and the two pages read list no cap; whether pi has an event like Stop was not re-read here, and R5 and R13 cover its hooks and extensions [S23][S30][S29].
- opencode 1.19.5: a per-agent `steps` cap ends in a text-only summary reply, and without it the agent runs until the model stops or the user interrupts [S22].
- Counting differs by control. The caps I read that a harness counts are `--max-budget-usd`, `--max-turns`, the Stop-hook continuation cap of eight, opencode's `steps` and Codex's goal token budget; the done verdict and the turn clause of `/goal` are model-judged [S18][S19][S22][S21][S20].

## Stop conditions compared

Each row is a stop condition, what enforces it, what it stops, how it fails, and the evidence. Evidence is the sources above; "unsourced" marks a cell I could not source. Every cell describes a documented or reported behaviour and none was tested here.

| --- | --- | --- | --- | --- |
| Model done claim | model | Nothing by itself; the run ends when the model says done | False success (45 to 48 percent of failures in the single-control tau2-bench domains, 75.8 percent of failed AppWorld runs with a status claim) and termination poisoning (2.33 to 3.57 times the steps) | [S7][S6] |
| Verified completion gate | engine, or a harness hook that runs a script | A run that ends as done without a passing check | A vacuous gate passes anything (47 vacuity defects in the authors' own catalogue); a Stop hook that cannot start fails open and Claude Code overrides a block after eight continuations | [S3][S19] |
| Dual exit check | model | A premature exit on one loose signal | Both signals come from the model or its text; no outcome data in the README | [S17][S24] |

## Verdicts

- H1: refined - R4 and R7 refined it: external evidence beats self-report, and a passing declared command is only as good as its scope and its oracle [S25][S26]. R15 adds loop-level evidence. In favour: self-reported completion is measurably unreliable (false success is 45 to 48 percent of failures in the single-control tau2-bench domains and 75.8 percent of failed AppWorld runs that carried a status claim; injected text can push the agent's own termination judgment to 2.33 to 3.57 times the steps; agents rarely stop on evidence they judge useless unless the harness enforces the stop), and the design that makes the point keeps the worker's claim out of every guard [S7][S6][S16][S3]. Qualifying: those rates come from non-coding or older-model benchmarks and simulated tools, not from coding runs on current models; the SWE-Marathon labels put premature termination and weak self-verification at 7.6 and 4.0 percent of failures against 31.4 percent for timeouts [S11]; the two built-in completion checks I read (ralph's dual exit check and Claude Code's /goal) are model-judged and neither runs a command [S17][S20]; a gate is only as good as its test (47 vacuity defects in the authors' own catalogue) [S3]; and no source I read tests the clause "after the last edit" (unsourced). Refined: self-report is unreliable in direction, the rule needs a harness-run check whose gate has been tried against a failing case, and the size of the effect on coding runs is unmeasured.
- H15: refined - R9 refined it: tiers hold, the count N is unsourced above one, and ceilings are partial [S27]. R15 adds that a configured ceiling is documented on Claude Code, opencode and Codex and not on the two pi pages read, and each is partial: Claude Code's dollar and turn caps are print-mode only and spend can pass the cap, opencode's step cap ends in a text-only reply, and Codex's goal budget has no default [S18][S22][S21][S23]. Ceilings do end runs (timeouts are 31.4 percent of agent-attributable failures in SWE-Marathon, model-labelled), but a ceiling alone is a licence to spin when sized from the workload (54 identical successful calls) or when it does not cover the whole feedback path (68 confirmed missing-bound cases in 47 projects, by code review and not observed runs) [S11][S14][S5]. Models do not stop on their own budget or evidence judgment (a stated budget moves stops to the deadline; results judged useless rarely end the run), and a model-judged bound, the /goal turn clause, is not a ceiling [S16][S20]. N is unsourced above one: the thresholds found are defaults (3 and 5 in ralph, 8 for Claude Code's Stop-hook continuations, 3 retries in /goal and in pi) with no outcome data [S17][S19][S20][S23]; learned early-stop evidence is mixed [S8][S9][S15]; and R9 found no host page documenting an escalation log, and none I read adds one [S27]. Refined: ceilings stop runs only when the harness or engine counts them and they cover the loop; N stays unsourced; a progress-based breaker is a design option backed by one production incident study and no controlled test [S14].

## Implications for weftwork

These are proposals for the synthesis (e04s02), each with its evidence and none tested. "Engine" means the provisional engine of docs/SEED-SPEC.md.

- Name the terminal states and write the rule that an error or an exhausted budget never counts as done: done (verified), blocked, stalled, exhausted and killed, each logged with its counters [S1][S3].
- Let a run end as done only on a verdict from a check the engine runs and the worker cannot write to, and try each gate against a held-out failing case before trusting it (a gate that cannot fail is a vacuous gate) [S3][S7][S29].
- Count the ceilings in the engine, not in the prompt, cover the whole loop (the outer cycle as well as each attempt), and keep a reserve so a hard stop leaves a written handoff. Do not rely on a host cap that exists only in print mode or on a goal clause the model judges [S3][S5][S18][S20].
- Key any no-progress breaker to evidence that can move (a change in the tree, a count of failing tests), never to an identifier that stays constant, and show it can trip and can stay quiet before shipping it; treat a trip as the `stalled` terminal state with a handover note, since breakers block correct work too [S14].
- Start thresholds as tunable defaults (ralph's 3 no-progress loops and 5 repeated errors are the only coding-loop figures found) and measure them in R10; do not present them as findings [S17][S16].
- Do not build a learned early-stop predictor for v1: three studies disagree and each used a different signal [S8][S9][S15].
- Do not make a Stop-hook gate the only guard in Claude Code: it fails open when it cannot start and the host overrides it after eight continuations, so the engine has to hold the done verdict itself [S19][S29].
- Treat a rate limit as a pause that is logged, not as a stop, and treat a full context as a handover or a stop state, not an endless compaction loop (R12) [S17][S20][S28].
- Cap review rounds and hand over to a human at the cap, as R7 recorded for bigpowers at 5 (R7) [S26].
- Keep adapters thin: the hosts differ in which caps they have and who counts them, so the engine owns the counters and each adapter only passes the stop through [S18][S21][S22][S23].

## Earns its place vs ceremony

- Ending a run as done only on a verified gate verdict: earns its place. The evidence on model claims is the strongest in this brief, provided the gate has been tested against a failing case [S7][S6][S16][S3].
- Ralph's dual exit check (two model-derived signals): unproven as a completion test and fine as a guard against premature exit; the README gives no outcome data [S17].
- A harness-counted ceiling on spend or turns that covers the whole loop: earns its place. Timeouts end many failed runs, and a missing or inner-only bound leaves the loop open [S11][S5][S14].
- A model-judged bound such as the /goal turn clause: ceremony as enforcement; it is a request the evaluator reads from the transcript [S20].
- A budget-awareness signal (a tracker or reminders): unproven for coding loops; one web-search study helped, and models given a budget stopped at the deadline, not on evidence [S13][S16][S21].
- A progress-based circuit breaker keyed to evidence that can move: earns its place in form, with the thresholds unproven and a false-trip risk shown in one incident study [S14][S16].
- An error-rate circuit breaker for an agent loop: ceremony; it was blind to a loop of successful calls [S14].
- A learned early-stop predictor: unproven; results differ by signal, policy and baseline [S8][S9][S15].
- A rate limit as a stop condition: unproven; it is cost control in a README and a pause in Claude Code [S17][S20].
- A context ceiling as a stop state: unproven; nothing measured, and the hosts treat it as a compaction trigger [S28][S21][S23].
- Named terminal states: cheap, and earns its place; the support is descriptive (one catalogue, one coder) [S1].
- A Stop-hook gate as the only holder of the loop in Claude Code: partial; it fails open and is overridden after eight continuations [S19].
