## Advisory and enforced

This section separates what a host can enforce (a tool-call hook, a permission rule, an engine gate) from what it only asks of the model (a skill, a context file, a steering file). It reads R2's and R5's findings first and adds what the papers and the host pages say about where enforcement stops.

- R5 found a hook that can block a tool call in all five hosts it read, in two families: out-of-process command hooks that exchange JSON and an exit code (Claude Code, Codex CLI, Gemini CLI) and in-process TypeScript (pi, opencode) [S41]. I re-read the Claude Code, Codex, pi and opencode pages and found nothing that contradicts it [S25][S27][S28][S29]. A skill or context file reaches the model as text; the Kiro steering page describes how such files are loaded and when, and names no check that the model followed them [S30].
- R2 found that a gate written as prose is a request: in one session a request and a repository rule disagreed and the agent chose between them, and the guard hook "does nothing until it is installed", was not registered in this repository's settings (user level unchecked), and no block was observed, so R2 has no catch rate [S38]. R2 left it to R13 to decide what else deserves hook form [S38]. The evidence below says which advisory text works, which does not, and what a hook still cannot stop.
- Advisory text helped in one measured case and was ignored in others. A guardrail skill learned from failure traces (AgentGuard) cut abnormal execution from 69.0% to 26.7% on 100 tasks with Claude Code 2.1.19 and Haiku 4.5, but over-refusal rose from 0 to 19.3%, successful task completion rose from 21.7% to 35.0%, and the human reviewers could tell which condition they were scoring [S8]. Agents "almost never proactively retrieve" repository contribution rules, improve at disclosure and verification with reminders, rule quotes or verifier feedback, and never refuse to contribute in AI-banned repositories under any condition tested (106 issues, 49 repositories, four models) [S20]. Adding instruction files raised the merge rate by at least 20% in 27.7% of 148 projects and lowered it in 26.35% [S23]. Advisory text works sometimes; no source here says when.
- Prompt-layer defences are model-specific. One study of authority-spoofing tool calls found "no tested prompt-layer defence provides a general boundary across the endpoints tested": some endpoints stop after voicing doubt, others execute anyway (the paper calls responses that both express doubt and delete rare in its reflection re-run, 25 of 509 executions) [S4]. The same paper's external reference monitor rejected all 750 forged, tampered, replayed and unsigned records in 1,350 sandbox trials, which it calls a functional-correctness test, not a robustness estimate; a deputy holding a valid scoped token still induced in-scope deletions in 31 of 42 trials, so semantic authorization stayed open [S4]. The setting is benign file deletion on gateway-labelled endpoints, not a workflow gate.
- Executable checks beat prompt-only and reflection in one benchmark, with qualifiers that the abstract omits. ContextCov reached 88.3% constraint compliance against 67.0% for the arm that had AGENTS.md in context and 50.3% for an LLM critic, and resolved 57.3% of SWE-bench Lite against 53.0% and 52.3% (McNemar p=0.031 and p=0.046) [S2]. The compliance oracle is the same family of synthesized checks that fed the loop, the baselines were scored post hoc, the instruction files were LLM-generated from CONTRIBUTING files, lint configuration and CI files, the checks were generated by Claude Code with Opus 4.5 and include an LLM judge for semantic architectural constraints (rubrics, not executable code), extraction precision was 82.81%, and it ran one scaffold, one coding model and 300 tasks in 12 Python-heavy repositories [S2]. It states it is not a security boundary: it assumes trusted instructions and a non-adversarial repository, and "Organizations should treat AGENTS.md with the same rigor as .github/workflows/" [S2].
- A hook is a guardrail whose failure mode matters. In Claude Code, of the exit codes only 2 blocks a PreToolUse call (a JSON `permissionDecision: "deny"` returned on exit 0 also blocks); a missing script, invalid JSON, a timeout or exit code 1 is a non-blocking error and the action goes ahead unless the hook sets `onFailure: "block"` [S25]. Codex's page says, in its cloud-orchestration section, that "a `PreToolUse` error, timeout, or malformed response can let the tool run", and says of MCP-tool hooks that "errors, missing servers, and unavailable tools don't block the operation"; it also says hosted tools such as WebSearch do not use the hook path, that some specialized tool paths can opt out, and to "treat tool hooks as a useful guardrail, not a complete enforcement boundary"; I did not find the error-and-timeout sentence for local command hooks [S27]. pi's page tells gate handlers to "fail closed when their safety decision cannot be made", and its Error Handling section says "`tool_call` errors block the tool (fail-safe)" while other extension errors are logged and the agent continues [S28]. opencode blocks by a plugin throwing in `tool.execute.before`, and its permission file has `allow`, `ask` and `deny` [S29].
- A completion hook has the same gap. A Claude Code Stop hook that exits 2 sends the agent back to work, which fits the declared-command evidence gate (H1), but `onFailure` has no effect on Stop hooks and a hook that cannot start does not block [S25]. Whether a Stop hook runs a gate command and the gate passes is a check the hook owner must make live; no page I read offers a way to confirm that a required hook is installed and healthy (unsourced); one research implementation for Claude Code and Codex tests hook delivery and allow/deny behaviour with eight scripted runtime cases (abstract-level) [S54].
- Enforcement depends on the hook being present and trusted. Codex skips non-managed hooks until the owner reviews and trusts the exact definition by hash, and `--dangerously-bypass-hook-trust` turns that off for a run [S27]. Claude Code's `disableAllHooks` turns off user, project and local hooks but not managed ones [S25]. pi loads project-local extensions only after the project is trusted [S28]. R2's unregistered guard hook is the same gap in this repository [S38].
- The files that hold enforcement are an attack surface. Claude Code's `bypassPermissions` mode skips prompts "including for writes to protected paths such as `.git` and `.claude`" [S26]; a `ConfigChange` hook can block configuration changes except those from managed policy [S25]. In a lifecycle benchmark, Harness Configuration was the most vulnerable phase across all three harnesses, and attack success ranged from 12.6% to 80.9% over 14 configurations [S15]. Keep the gate scripts and hook registration where the agent cannot write, or managed by the owner.
- Permission rules stop the form they match. Claude Code's docs say a Bash deny or ask rule "covers the invocation Claude usually produces and isn't a security boundary around the program", and that rules constraining arguments are "fragile" [S26]. A security vendor reported that in a past version more than 50 chained subcommands skipped per-subcommand deny checks and added an update note that Anthropic had "seemingly fixed" it in v2.1.90; I did not re-test that [S35]. The design-space paper cites the same report [S17]. A PreToolUse hook's "allow" does not override a matching deny or ask rule [S26][S17].
- Kiro steering is advisory context. Steering files are markdown that Kiro loads, with inclusion modes `always` (the default), `fileMatch`, `manual` and `auto` (all four in Kiro CLI V3; older engines load only `always` files automatically); the three foundation files (`product.md`, `tech.md`, `structure.md`) are included in every interaction by default, and `AGENTS.md` is always included [S30]. With custom agents, steering files "are not automatically included" and must be added to the agent's `resources`, so a rule in a steering file does not reach a custom agent unless it is listed [S30]. The page lists "security policies" as steering content and describes loading only [S30].
- Kiro hooks can enforce, and have a shape R5 did not compare. A command hook on Pre Tool Use blocks the tool invocation on any non-zero exit and sends stderr to the agent; exit 0 adds stdout to the agent's context; the default timeout is 60 seconds and 0 disables it [S33]. The pages call Pre Tool Use able to "validate and block tool usage" and list "gate dangerous operations" as a use [S32][S31]. This differs from Claude Code, where of the exit codes only 2 blocks and any other failure is non-blocking unless `onFailure` is `block` [S25][S33]. An agent-prompt action injects a prompt, which is advisory and consumes credits, while a shell command is the deterministic form [S33]. File triggers respond only to the agent's changes, not manual edits; hooks run in the IDE and CLI, not Web or Mobile; CLI Prompt Submit hooks cannot block while the IDE's can [S32][S31]. I did not find what Kiro does when a Pre Tool Use command times out (unsourced).
- The survey frames the harness as the layer holding "sandboxes, memory, validators, permission boundaries", says lifecycle hooks "turn tool use from a raw model-selected action into a monitored transition", and says gateway and policy layers keep "governance outside the prompt alone" [S1]. It is a survey and ran no test of its own. A separate proposal says "a Skill describes how an agent should behave; a Policy decides which behavior is allowed to become an action" and that today the second is left to the model; its guards rejected 60 of 60 borrowed-authority requests across five attack variants without blocking benign requests on a physical-world edge testbed, which is a proposal with one testbed, not a result for coding agents [S14].

## Ceremony scaled to risk

This section starts from the H7 verdicts of R1, R2 and R3, which found that tools scale ceremony but not by measured risk, and asks what else shows whether risk-scaled ceremony works.

- R1 found GSD tiers ceremony by effort (`fast` for up to three edits, `quick`, then the full chain), picked by the owner or a triviality check, with no file that scores risk [S37]. R2 found bigpowers scales `verify-work` by a declared `risk:` field (P0 to P3; P2 and P3 skip tests, the security scan and manual UAT; a missing field means P1), while its `assess-impact` score is assigned by the agent and does not feed verification depth [S38]. R3 found the other tools scale by size or kind of change and by the human's choice, and that only bigpowers uses risk, through a declared field [S39]. R2 and R3 left the question of whether it works to R10 and R13 [S38][S39]; R1 did not.
- No source I found compares risk-scaled ceremony with fixed ceremony on pass rate and cost per accepted task for coding agents (unsourced; candidate R10 measurement, with H7 as the claim). R2's candidate, computing the risk score in code and letting it set verification depth, is also untested [S38].
- Classical software engineering has a literature on this, with no agent evidence in it. A taxonomy of risk-based testing says such approaches use risk assessment to steer every phase of the test process and sorts them into risk drivers, risk assessment and risk-based test process; it is a taxonomy built from published approaches to compare and tailor them, not a study of whether they work better than uniform testing (abstract-level) [S18].
- A cheap, computed signal exists for one adjacent outcome. Tree-based models predicted pull-request acceptance from submission-time features with F1 above 0.95 on the AIDev data, but comment counts and time to merge were only modestly explained, and the authors say to use such models as advisory tools, not automated decision-makers (abstract-level) [S19]. Acceptance is not risk, so this supports computing triage signals in code, not any particular risk formula.
- More ceremony bought reviewability, not correctness, in one small pilot. Explicit delegation contracts and a required evidence bundle improved evidence sufficiency in 22 of 30 paired comparisons and worsened none (+0.83 on a 5-point scale, p<0.0001), at +13% agent tokens and +38% wall-clock time; all 64 runs passed the hidden acceptance checks in every condition, on ten small tasks with model-based reviewers (abstract-level) [S22]. That is a reason to name what a ceremony step buys before scaling it.
- A passing test is weaker evidence than a gate assumes, which argues for depth on high-risk work. In SpecBench every frontier agent saturated the visible tests while the held-out gap grew by 28 percentage points for each tenfold increase in code size, and a 2,900-line hash-table "compiler" memorized test inputs (abstract-level) [S9]. In SWE-bench Verified, 7.8% of all patches count as correct while failing the developer-written test suite, and 29.6% of plausible patches behave differently from the ground truth (abstract-level) [S21]. Reading these as a case for deeper verification on larger or riskier changes is an inference; neither paper measures ceremony.
- Scaling a gate by action instead of by story is already shipped, and its error rate is vendor-reported. Anthropic's auto mode hands approvals to a model classifier: the full pipeline blocked 0.4% of 10,000 real benign actions, missed 17% of 52 real overeager actions and 5.7% of 1,000 synthetic exfiltration attempts, and the post calls the 17% "the honest number" and not a drop-in replacement for careful review on high-stakes infrastructure [S34]. Claude Code has five user-selectable permission modes (seven in the source, counting an internal one and a feature-gated one), which are human-chosen ceremony levels [S17]. A research approver that runs each command in a snapshotted sandbox and shows the observed effects reported a harmful-outcome rate of 6.7% against at least 14.8% for six existing systems on SABER, and 7.8% against at least 35.3% on a benchmark its authors built (abstract-level) [S7].
- Commercial agents sit at two ends. Of five commercial agents, those that default to user-in-the-loop approval prompt often and those with low overhead give the user little control or transparency; Claude and Codex also appeared to use AI guardrails to auto-review actions, and the paper analysed five commercial agents (Claude, Claude Cowork, ChatGPT chat mode, ChatGPT agent mode and Codex), not Claude Code [S5]. The survey describes a three-tier permission model (read-only, sandbox-edit, full access) with mandatory human gates on the full-access tier, and says a loop can stop "when the risk tier changes" [S1].
- This repository applied one review ceremony to work it rated P2. The e03 epic and its stories e03s01 to e03s07 are `risk: P2` [S49], and each of e03s02 to e03s06 ran the independent-reviewer gate for two to five rounds, failed it in every round, and was then waived by the owner (five waivers); the waivers record real errors found and fixed along the way [S47]. It is one repository over four days: it shows a gate with a cost and catches that was not scaled by the stated risk, not a rate [S47].

## Escape hatches and gate retirement

This section starts from R14's H4 verdict and asks what the new sources add on logged escape hatches, retiring overridden gates, and adding a gate only after an observed failure.

- R14 found the escape hatch (`/flow allow`, one-shot) and the retirement rule (3 overrides, 0 catches) designed and unit-tested in the owner's earlier project, but its live ledger held 1 `guard_block` and 0 `guard_override` events, gates G1 to G4 never fired, and the project built five rules from gap analysis rather than from an observed failure, against its own decision D021 [S46]. R14's advice: keep the escape hatch and the log, and do not build retirement logic until there are overrides to count [S46]. R13 found nothing that changes it.
- I found no study of retiring agent-harness gates after overrides (unsourced). Retirement stays a design choice with R14's single-repository record behind it [S46].
- This repository's waiver ledger is one record of escape-hatch use. At the e03s07 plan commit it held 26 entries from 2026-11-07 to 2026-11-10: 6 gate-trace verdicts, 5 request-review gates, 4 plan-consistency-check findings, 3 security-review threat-model waivers, 3 GitHub-API or `gh` rule deviations, 3 source-publication-date exceptions, 1 rule about released briefs, and 1 resolved note about the cycle-time test [S47]. It is a free-text list the agent writes and the owner approves; each entry has what, why, date and scope, and no override count, catch count or retirement rule is applied to it [S47]. It records use, not rates, and it is one repository over four days [S47].
- Since e03s04 the gate-trace waiver has been scoped to one release at a time, which is the one-shot shape R14 designed; the handoff note says it "covers one release at a time", and the first three entries were scoped to a whole epic [S47][S46]. A one-release scope keeps each override a fresh decision; the ledger holds six gate-trace entries in all [S47].
- One gate in the ledger cannot pass by construction. gate-trace rule R1 fails any undone story that has no code tag, and this project has no code, so the rule was waived in all six gate-trace entries [S47]. Under R14's rule (3 overrides, 0 catches) that is a retirement candidate. The same gate also raised a finding that stories e01s02, e01s04 and e02s01 were released without verify evidence, and that finding names e01s02 and e01s04 in each of the last three gate-trace waivers (the last also names e02s01) with no fix recorded in the ledger, so whether the gate has caught anything is open [S47][S46].
- Hosts ship escape hatches, and none of the pages I read says their use is logged. Codex's `--dangerously-bypass-hook-trust` runs enabled hooks without persisted trust for one invocation [S27]; Claude Code has `disableAllHooks`, `bypassPermissions` and a `disableBypassPermissionsMode` setting that can lock bypass mode out, usually from managed settings [S25][S26]; opencode keeps explicit `deny` rules enforced even in auto mode [S29]. I did not find a statement that these are logged (unsourced).
- An allow-rule is the common escape hatch, and the agent can steer it. Planted repository content, produced by the authors' optimizing attack framework, led agents to request a plausibly justified but dangerously broad allow-rule in 58% of instances across four configurations (Claude Code with Haiku 4.5 and Sonnet 5, Codex CLI with two gpt-5.6 models; 25 cases each); the saved rules covered 56.9% of category-specific capability cases, and conditional on approval the exploit completed its goal silently in 47 of the 58 eligible instances (81.0%), where two baseline attacks reached 20 and 1 of 58 [S6]. The paper assumes the user approves the rule, and it quotes Anthropic as reporting that 49.5% of active Claude Code CLI users had configured a Bash allow rule as of June 2026 [S6]. A hatch the agent can propose is an attack channel; an escape hatch should be written by the owner, one-shot, and not offered by the agent (a reading of [S6], not tested).
- Human approval wears out, which bears on both hatches and retirement. Anthropic's auto-mode post says "in practice users accept 93% of [manual prompts] anyway", which is vendor-reported; the Claude Code design-space paper repeats it and cites longitudinal data in which auto-approve rises from about 20% under 50 sessions to over 40% by 750 sessions [S34][S17]. In clinical order entry, a review of 17 papers found drug safety alerts overridden in 49% to 96% of cases, with the authors saying overriding "may often be justified" and pointing at low specificity and workflow disruption as error-producing conditions; that is another domain [S24]. A gate that is mostly overridden is either too coarse or training its users to dismiss it, so a retirement rule should count false alarms as well as overrides (a reading of [S24], untested here).
- A gate that never fires may be empty, not healthy. An instrument run on a 69-loop catalogue the authors wrote counts 47 vacuity defects (a check satisfied by the absence of the thing checked) pinned as regression cases: 20 gates that accepted a defective mutant, 2 that rejected a conforming one, 14 that still accepted after a partial fix and 11 that filed a rejection as an incapacity; self-attestation, where the subject supplies the checked value, is a separate second class the 47 do not include. A fresh set of mutations found a false-accept rate of 23.3% (14 of 60 mutants, Wilson 95% interval 14.4% to 35.4%) where the exhausted set had reported none; the authors say a rate belongs to one gate and that transfer beyond their own catalogue is untested [S11]. R14's never-fired gates G1 to G4 have the same ambiguity: nothing triggered them, or they could not fire [S46][S11].
- Failure-derived guardrails have a worked example in the literature, and it is advisory, not a hard gate, with no comparison against gap analysis. AgentGuard learned guardrail instructions, packaged as a skill, from 461 failure traces across 282 tasks and evaluated them on 100 disjoint tasks, each a repository workflow with one injected adversarial step, all on one Click repository snapshot, at the cost of 19.3% over-refusal [S8]. ContextCov derives checks from instruction files, which is gap analysis in executable form [S2]. Whether failure-first gates beat gap-analysis gates is untested (unsourced).

## Model judgment and deterministic checks

This section starts from the H2 verdicts of R4 and R8 and R7's evidence-gate findings, and asks which verdicts weftwork should take from code and which it can leave to model judgment.

- R4 and R8 refined H2. R4: a fixed, code-driven pipeline matched or beat open-source agent loops on SWE-bench Lite (Agentless), and prose repository overviews did not help while instructions were followed, a hint that facts may be better read from commands, which no study tested [S40][S3]. R8: executable checks reached 88.3% constraint compliance against 67.0% for prompt-only and 50.3% for LLM reflection on one benchmark, and reading stack facts by command against a short context file was not shown [S43]. The evidence is for deterministic control flow, not yet for stack facts or gate verdicts [S40][S43].
- The full text of the 88.3% result adds qualifiers R8 could not see from the abstract: the compliance oracle is the executable check family that fed the loop, baselines were scored with it after the fact, and the LLM-reflection arm scored worse than the AGENTS.md-in-context arm on compliance, which the paper reads as LLM-based critique introducing "more drift than it corrects"; its remark that critics "may fixate on stylistic preferences" explains a different result, that the critic's own finals had the highest critic-clean rate and the lowest resolution rate [S2]. So it shows deterministic feedback beating model critique on constraints derived from instruction files, in one scaffold with one coding model, not a general rule that code beats model judgment [S2].
- R7 advised keeping the evidence gate separate from review and making it a gate the worker cannot write to, and rule-based escalation triggers instead of the model's own sense of when to ask [S42]. The full text of the paper behind the first point adds that its "47 vacuous gates in shipped, reviewed code" are in the authors' own catalogue of 69 loops, that a gate's false-accept rate depends on the mutation family used to test it, and that transfer to other codebases is untested [S11]. A separate gate the worker cannot write to is a requirement the evidence supports in form, and it still needs a test that the gate can fail [S11].
- A model judge's verdict depends on what it is shown. In a testbed with a scripted oracle, a 14B judge given only the request and the final reply scored 34% to 76% recall on four fault types that leave the reply unchanged, yet its paired discrimination against the clean runs was zero, so that recall was its flag rate on clean runs; told to check each step, the same model flagged every fault of those types and none of 100 clean runs; one support-desk testbed, abstract-level [S13]. A model judgment can be a reasonable check when it reads the evidence and not the claim, and its recall alone says little (a reading of [S13]).
- A self-reported pass is a claim. Re-verifying 10 fix claims from one coordination agent against file timestamps, the claimed defensive pattern and a rule-based re-check, the authors found that among claims with enough information to re-check, half failed the check on identifier and call site; the 10 claims are a census of one agent on one platform, and the checks were static [S10]. This supports H1's rule that "done" is a command the harness watched exit 0, and it is small [S10].
- A passing deterministic check can still be wrong, and the agent can learn the check. In SpecBench the visible validation tests saturated for every frontier agent while the held-out gap grew by 28 percentage points per tenfold increase in code size, and one run memorized test inputs in a 2,900-line hash table (abstract-level) [S9]. In SWE-bench Verified, 7.8% of all patches count as correct while failing the developer-written test suite, and 29.6% of plausible patches behave differently from the ground truth (abstract-level) [S21]. R14 asked whether plausible-but-wrong passes appear in agent-written verify commands; [S21] is about patches and benchmark tests, and the closest source I found, on test code in agent-authored pull requests, reports that 80.2% of 86,156 test-file patches carry weak or no explicit oracle signals, so quality gates based on test-file presence overestimate verification strength (abstract-level) [S52]; neither is about verify commands, so the question stays open (unsourced) [S46]. Both papers expose the gap with held-out material, held-out tests in [S9] and a held-out mutant corpus in [S11]; I found no test of a remedy for an agent that can see its own gate (unsourced).
- In this repository the `verify:` commands of the e03 briefs check structure, citations and keywords only, and the waivers for e03s02 to e03s06 record real errors that review rounds found in those briefs: a wrong claim about which reviewers run a command, a paper cited for something it does not show, an inverted detail of a paper, and papers the searches missed [S47][S49]. It is one repository, and it shows structural checks and model review catching different things, not which is better [S47].
- The boundary between stochastic output and deterministic action can be named. One paper calls it the stochastic-deterministic boundary and states it as a four-part contract: a proposer, a verifier, a commit step and a reject signal (a design framing, abstract-level) [S12]. The survey's version is the Plan-Execute-Verify loop, in which "termination should likewise be governed by verification rather than by model confidence" and model critique should "interpret sensor outputs rather than replace them" [S1].
- Hosts split the two kinds of hook. Claude Code hooks can be `command`, `http` or `mcp_tool` (code or a server you run), `prompt` (a single-turn model evaluation that returns JSON) or `agent` (a subagent that can use read tools; experimental) [S25]. Codex supports `command` and `mcp_tool` handlers and parses but skips `prompt` and `agent` handlers [S27]. Kiro's shell-command action is the deterministic form, its agent-prompt action injects a prompt and consumes credits [S33]. pi and opencode run arbitrary TypeScript, which can call anything [S28][S29].
- Model-based approvers exist and their error is reported by their makers. The auto-mode classifier missed 17% of 52 real overeager actions, and its post says most misses were a wrong read of whether the session held real consent for the action [S34]. A research approver that first runs the command in a snapshotted sandbox and hands an independent approver a bounded report of the observed effects had the lowest harmful-outcome rate among seven systems on two benchmarks, one built by its authors (abstract-level) [S7]. The second feeds a model judgment with a deterministic observation, which is the form the judge result above favours [S7][S13].

## Engine shape and shared state

This section reads R5's and R12's findings first, and gathers evidence for the two SEED §9 questions that need it: whether the engine is a CLI the adapters shell out to or a library each adapter imports, and where state lives when two hosts share a repo. It also reports the "Code as Agent Harness" survey that R5 could not find.

- SEED §9 asks three open questions about this: whether the engine is a separate CLI or a library, where state lives when two hosts touch one repo, and how much of the loop is advisory skills against enforced engine at each ceremony level [S48]. The third is the subject of the Advisory and enforced section above. This brief gives evidence for the first two and leaves the choice to the synthesis (e04s02), which also takes the stack decision.
- An engine CLI serves the hosts with command hooks directly. R5 found three hosts call an out-of-process command with JSON and an exit code and two load in-process TypeScript, and recommended a command-line program that reads JSON on stdin and answers with an exit code, with a small TypeScript wrapper for pi and opencode [S41]. I confirmed the command-hook shape in Claude Code (exit code and JSON), Codex (command handlers) and Kiro (a shell command that receives session context as JSON on stdin, with the exit code deciding a Pre Tool Use block) [S25][S27][S31][S33]. pi and opencode run TypeScript in-process, so they can import a library or shell out to the CLI [S28][S29]. A library engine would serve the TypeScript hosts directly and need a CLI shim for the rest (an inference from [S41]).
- A third shape is an engine server that hooks call. Claude Code supports `http` and `mcp_tool` hooks and Codex supports `mcp_tool` handlers; Codex's MCP hooks reuse an existing connection, run synchronously, and a `SessionStart` hook can run before the server is ready [S25][S27]. A failed HTTP hook in Claude Code is a non-blocking error unless `onFailure` is `block` [S25]. R5 did not compare this shape. One research implementation of a pre-execution hook for Claude Code and Codex reports a median paired hook overhead of about 85 ms (abstract-level) [S54]; no source compares a CLI engine with a server, so the cost of starting a process per tool call, against a server that must be up, is unmeasured (unsourced; candidate R10 measurement).
- The host's own harness is large, which is a reason for an engine to call it and not repeat it. The analysis of Claude Code's public source describes "a simple while-loop" and puts most of the code in the systems around it: a permission system with seven modes and a classifier, a five-layer compaction pipeline, four extensibility mechanisms, subagent delegation and append-oriented session storage [S17]. That is a reading toward H9 and H16, not a test of either. A research system takes the other route: it interprets editable natural-language harness documents with its own shared runtime into agent calls, handoffs, state updates, validation gates and artifact contracts, with task outcomes comparable to code and prompted harnesses (abstract-level) [S16].
- R0 found one project (gstack) whose table marks its safety skills "enforced (hooks block)" on Claude Code and "advisory, not blocked" on Codex CLI, OpenCode, Gemini CLI and the other hosts it lists; R0 calls this one project's packaging, not a general finding, and reads it as support for H16, that the engine checks and the host only calls it [S36]; R5 reads the other hosts' advisory status as that project's packaging, because their hooks can block a call [S41]. R5's H16 verdict is refined: every host has a blocking tool-call hook, but the adapters are not equally thin [S41].
- The survey "Code as Agent Harness" is arXiv:2605.18747, first version 2026-05-18, 42 authors [S1]. My title search `ti:"Code as Agent Harness"` returned it first, and two plain queries returned it too. R5's search returned no entries on 2026-11-08, and I do not know why it missed it [S1][S41]. On H16 it supports the layering and no more: it defines the harness as the software layer around the model with "tools, APIs, sandboxes, memory, validators, permission boundaries, execution loops, and feedback channels", puts permission checks, policy rules and human gates in lifecycle hooks, and names MCP as the open protocol that standardizes how harnesses expose tools; it does not compare engine designs or adapters across hosts [S1]. On H9 it has no test: it describes Claude Code, Codex and the Copilot coding agent as packaging the loop themselves, with permissions, hooks, memory, subagents, sandboxes and branches, and it treats the harness as the object of study, not whether to compose a host's machinery [S1]. It is a survey with no experiment of its own [S1].
- With two hosts, each reads its own project directory, so registering the engine is per-host work: Claude Code reads project and local settings, Codex loads project hooks only when the `.codex/` layer is trusted, pi loads project extensions from `.pi/extensions` after the project is trusted, and Kiro reads `.kiro/steering` and `.kiro/hooks` [S25][S27][S28][S30][S31]. R5 lists `.opencode/plugins/` for opencode [S41]. The model-readable instruction file is not a safe place for shared state: `AGENTS.md` is read by default in only three of the five hosts R5 read, by Claude Code only when no `CLAUDE.md` exists, and Kiro always includes it [S41][S30]. State that the engine reads and writes on a hook or a command does not depend on which host loads which file (a reading of [S41][S30]).
- R12 required durable state in plain repository files written by one format-preserving tool, noted that the hosts keep their own memory in plain files and that Claude Code has a built-in task list stored outside the repository, and left where state lives for two hosts to R13; it advised against a database-backed tracker for the first release without a failure that plain files cause [S45]. R6 adds that beads' default embedded mode has a single writer, that bigpowers keeps `specs/state.yaml` plus a story lock in `specs/agent-locks.yaml`, that GSD's parallel executors each update `STATE.md` and `ROADMAP.md` with no reconciliation found, and that textual merge conflicts hit 41.7% of concurrent cross-agent pull-request pairs and 19.8% of same-agent pairs (rates of overlap without coordination, on pull requests, not on state files) [S50]. One writer, the engine, that both hosts go through removes the two-writers case on a plain file, if both hosts do go through it (a reading of [S45][S50]).
- No source I found compares an engine-written shared store with host-owned stores when two hosts share one repository (unsourced); the nearest is the design in [S53], which gives no comparison. H27 rests on design arguments from R5, R6 and R12, not on a measurement.
- The format-preserving writer is a requirement this repository has hit repeatedly. R2 and R12 both asked for it [S38][S45]. BUG-001: `bp-timing.sh` writes `state.yaml` back through PyYAML's dump, which drops the leading `---` and comments, leaves block sequences unindented and does not wrap long scalars, so every skill that called it re-broke the lint [S51]. BUG-004: `record-cycle-time.sh` removed the `---` line from `execution-status.yaml`, and because the warning does not fail the command, Preflight stayed green [S51]. The e03s07 kickoff commit a38d2e8 carries a reflowed handoff note of the same kind, consistent with BUG-001's cause [S51].
- Managed blocks have no new support. R8 refined H5: how often instruction files change and who edits them is open, no vendor documents managed blocks, this repository's fences carry no hash R8 could see, and no source shows a hash protecting an edit [S43]. Codex records trust for a hook against the hook's current hash and skips new or changed hooks until reviewed, which uses a hash to detect edits to a hook definition and does not merge generated text [S27]. Kiro documents a one-way upgrade (`/upgrade-agent`) that converts older hook formats [S31]. I found no source on merge-safe regeneration of generated files by hash (unsourced), so a managed block stays ceremony until a failure shows an overwrite.
- Formats differ per host, so each added host is one more adapter. Hook definitions are Claude Code settings JSON, Codex hook files, TypeScript modules in pi and opencode, and Kiro's `.kiro/hooks/*.json` with `"version": "v1"` and PascalCase trigger names [S25][S27][S28][S29][S31]. R5's H8 verdict says the same of subagent, hook and plugin formats [S41].

- H2: refined - R4 and R8 refined it on one fixed pipeline and one compliance benchmark [S40][S43]. For gate verdicts on declared constraints, executable checks (with an LLM judge for semantic constraints) beat model critique in the one benchmark that compared them: 88.3% constraint compliance against 67.0% for the AGENTS.md-in-context arm and 50.3% for LLM reflection, with the qualifiers that the oracle is the same check family, the instruction files were LLM-generated, and it ran one scaffold and 300 tasks [S2]. A model judge's recall depended on what it was shown and its paired discrimination was zero when it saw only the reply [S13], and half of the re-checkable self-asserted fix claims failed re-verification in a census of 10 [S10]. Against the claim, a deterministic check can be vacuous (47 vacuity defects pinned as regression cases in the authors' own 69-loop catalogue, some of them one gate counted again after a partial fix) [S11], gamed (the held-out gap grows with code size) [S9] or incomplete (7.8% of all patches count as correct while failing developer tests) [S21] or weak (80.2% of 86,156 agent-authored test patches carry weak or no explicit oracle signals, abstract-level) [S52]. Reading stack facts by command is still unshown [S40][S43]. The claim stands for gate verdicts and completion, with the rider that each gate is tested against a held-out failing case.
- H4: refined - R14 found the escape hatch and retirement rule built and unit-tested but never exercised, with 0 overrides and 1 block in the live ledger [S46]. R13 found no study of retiring agent-harness gates (unsourced), and this repository's ledger records use without counts: 26 waivers in four days, one gate that cannot pass by construction, and a one-release scope since e03s04 [S47]. An escape hatch the agent can propose is an attack channel: planted content elicited a broad allow-rule in 58% of instances and the exploit then reached its goal silently in 47 of the 58 eligible [S6]. Approval wears out: Anthropic reports that users accept 93% of manual prompts (vendor-reported), and clinical alerts are overridden in 49% to 96% of cases [S34][S24]. A gate can also be empty [S11]. Keep R14's advice: a one-shot, owner-written hatch with a log, false alarms counted with overrides, retirement unvalidated, and failure-derived guardrails as a design rule with one advisory worked example (injected-step tasks on one repository) and no comparison [S46][S8].
- H5: refined - R8's verdict stands: the need is partly supported and the hash mechanism is not [S43]. R13 found no host documenting managed blocks or merge-safe regeneration; Codex hashes a hook definition to decide trust, which is another job, and Kiro documents a one-way hook-format upgrade [S27][S31]. The failures seen here are tools rewriting a file's style (BUG-001, BUG-004 and the reflowed handoff note in commit a38d2e8), not a regeneration overwriting a human edit [S51]. A format-preserving writer answers those failures and a hash does not [S51][S43].
- H6: refined - R1 and R2 found tools build the workflow first and enforce softly or narrowly, and R14 found enforcement verified against fixtures with no workflow to enforce [S37][S38][S46]. R13 finds the order holds for what to build and fails if "second" means advisory: advisory text helped in one setup (abnormal execution 69.0% to 26.7% at 19.3% over-refusal) and was ignored in others (agents almost never retrieve repository rules, though reminders, rule quotes and verifier feedback fixed disclosure and verification in that study; no prompt-layer defence held across endpoints) [S8][S20][S4]. A hook is a guardrail whose failure mode decides whether it enforces: Claude Code fails open unless `onFailure` is `block`; Codex's page says a PreToolUse error, timeout or malformed response can let the tool run (in its cloud-orchestration section) and that MCP-tool hook errors do not block; Kiro blocks on any non-zero exit; and pi blocks the tool when a `tool_call` handler errors [S25][S27][S33][S28]. Better stated: workflow first, then one installed, fail-closed, verifiable hook for each rule that matters, added after an observed failure.
- H7: refined - R1, R2 and R3 found tiers by size, kind, human choice and a declared risk field, and none measured risk [S37][S38][S39]. R13 found no source comparing risk-scaled with fixed ceremony on pass rate and cost (unsourced). What exists: a risk-based testing taxonomy with no effectiveness evidence (abstract-level) [S18]; computed signals that predict pull-request acceptance (F1 above 0.95) but not review effort [S19]; more ceremony that bought reviewability and no correctness on small tasks, at +13% tokens and +38% wall-clock [S22]; evidence that a pass overstates correctness and that the held-out gap grows with code size [S9][S21]; per-action scaling by a model classifier, shipped, with vendor-reported misses [S34]; and this repository's single review gate on P2 work that failed every round [S47]. The claim stays a hypothesis for R10.
- H16: refined - R5's verdict stands: every host has a blocking tool-call hook and the adapters are not equally thin [S41]. R13 adds that command-hook hosts (Claude Code, Codex, Kiro) serve a CLI engine directly and pi and opencode need a TypeScript wrapper, and that Claude Code and Codex also accept HTTP or MCP-tool hooks [S25][S27][S33][S28][S29]. The adapter also owns the failure behaviour: it must set the host's fail-closed option or accept fail-open (pi and Kiro already block on a handler error or non-zero exit), register the hook, and, on Codex, get the hook reviewed and trusted [S25][S27][S33][S28]. The survey supports the layering and tests no adapter design [S1]. "Thin" holds for the call and not for the failure behaviour.
- H27: refined - no source compares an engine-written shared store with host-owned stores for two hosts (unsourced), so this is a design verdict and untested. In favour: each host reads its own project directories, so registration is per host while state need not be [S25][S27][S28][S30][S31]; instruction files are not read the same way by every host [S41][S30]; R12 required plain files and one format-preserving writer, and R6 found single-writer stores and frequent merge conflicts in uncoordinated concurrent work [S45][S50]; and this repository's helpers rewrote state files in a different style twice [S51]; one published design has the same shape, ESAA-Conversational, which captures visible turns from several coding agents (Codex, Grok, Claude Code) through hooks and watchers into an append-only event log and deterministically projects read models, but it does not compare designs against host-owned stores (abstract-level) [S53]. Not shown: the "through the engine" half is a requirement and not a finding, hosts keep their own session and memory stores so the claim holds for workflow state only [S45], and the cost of starting a CLI per call is unmeasured (unsourced).

## Implications for weftwork

These are proposals for the synthesis (e04s02), each with its evidence and none tested.

- Make the evidence gate the first enforced rule: a blocking tool-call hook that runs the declared command, plus a completion check, with the engine running it and a gate the worker cannot write to [S41][S25][S11]. Set the host's fail-closed option where it exists (`onFailure: "block"` in Claude Code), rely on Kiro's non-zero-exit block (its timeout behaviour is not stated) and pi's fail-safe `tool_call` error handling, and add a second layer for Codex, where the page says a PreToolUse error or timeout can let the tool run in the cloud-orchestration case and MCP-tool hook errors do not block [S25][S33][S28][S27].
- Build the engine as a CLI that reads JSON on stdin and answers with an exit code, with a thin TypeScript wrapper for pi and opencode, as R5 proposed; treat an HTTP or MCP server as a later option once the per-call cost is measured [S41][S25][S27].
- Make the adapter's install step register the hook, set the fail-closed option, get the hook trusted where the host asks for it (Codex does), and check that the hook is live, because R2 found a guard hook that does nothing until it is installed and was not registered here [S38][S27][S25]. Have the engine fail loudly when its own hook is missing (a proposal).
- Keep the gate scripts, hook registration and settings where the agent cannot write them, or under managed settings; Claude Code's `bypassPermissions` skips prompts for `.git` and `.claude` writes, and `disableBypassPermissionsMode` can lock it out [S26][S25][S15].
- Test each gate against a held-out failing case before trusting it; a gate that cannot fail is a vacuous gate [S11][S9].
- Write the escape hatch as owner-authored, one-shot and logged with a count, and do not let the agent propose allow-rules; count false alarms as well as overrides [S6][S46][S24] (a reading of the evidence).
- Keep workflow state in plain repository files written only by the engine through a format-preserving writer, with both hosts calling the engine; treat it as a requirement and a design choice, not a tested result [S45][S50][S51].
- Do not build hashed managed blocks or retirement logic yet: R8 and R14 found no failure that needs the first and no overrides for the second to count [S43][S46].
- Declare risk as a field first and compute it in code later as a hypothesis for R10; do not claim risk-scaled ceremony works [S38][S18].
- Keep model judgment for what code cannot check, and show the judge the evidence, not the claim [S13][S2]. Treat a model approver as a shipped option with reported misses, not as a gate [S34].
- Feed R15 the enforced stop conditions: a budget ceiling enforced inside an attempt and a gate verdict before done are the two this evidence supports [S11].

## Earns its place vs ceremony

- One blocking hook that runs the declared evidence command: earns its place. Every host offers a blocking hook, R14's one live catch was a status-claim gate, and the evidence for deterministic feedback is the strongest in this brief, but only if it is installed and fails closed [S41][S46][S2][S25].
- Making the hook fail closed and checking it is live: earns its place. The host docs show fail-open defaults in Claude Code and fail-open cases in Codex's cloud-orchestration and MCP-hook text, and R2 found a guard hook that was not registered here and observed no block [S25][S27][S38].
- A gate the worker cannot write to: earns its place in form, with a held-out failing case per gate as its test; the vacuity result comes from the authors' own catalogue [S11][S42].
- Executable checks compiled from instruction files: unproven, cheap to try. One benchmark, LLM-written instruction files and a self-built oracle [S2].
- A logged, one-shot, owner-written escape hatch: earns its place; this repository's free-text ledger already does part of it with no counts [S46][S47].
- An escape hatch or allow-rule the agent proposes: ceremony at best and an attack channel at worst [S6].
- Prose "HARD GATE" lines as enforcement: ceremony as enforcement and fine as guidance; R2 counted 74 of 80 skills carrying one [S38][S8][S20].
- Kiro-style steering files, and context-file rules in general, as enforcement: ceremony as enforcement; they load as text [S30][S23].
- A hashed managed block: ceremony until a failure shows an overwrite [S43][S51].
- Retirement logic (3 overrides, 0 catches): ceremony for now; nothing has flowed through it [S46].
- Risk-scaled ceremony computed in code: unproven; R10 measures it [S38][S18][S22].
- The independent-reviewer AND-gate on P2 research briefs: mixed. Review earns its place, since the waivers record real errors found each round, and the pass threshold failed every round and was waived five times, so as a pass condition it has done nothing yet (one repository, four days) [S47].
- gate-trace rule R1 in a repository with no code: ceremony; it cannot pass by construction and sits in six waivers, though the same gate's finding about missing verify evidence is unresolved [S47].
- A model-based approver in place of a human: unproven; the error rates are the vendor's own and the sample of real misses is 52 [S34][S7].
- An engine server called over HTTP or MCP: unproven; the per-call start cost it would save is unmeasured [S25][S27].
- A natural-language harness runtime in place of host machinery: unproven for this project; it is a research system whose outcomes were comparable to code, and it replaces the host's loop, which cuts against H9 [S16][S17].
