## Finding conventions

- Context files do not generally raise task success and raise inference cost by over 20% on average; instructions in them are well followed, repository overviews are not helpful, and the authors find such files useful for non-standard practices [S1]. A later two-agent ablation (Claude Code and Codex, 17 tasks, 288 runs) finds context strategy does not move correctness measurably, and that agents fail on implementation skill, such as feature design and pattern choice, rather than on missing repository knowledge [S2].
- Developers mostly write functional context in these files: test procedures in 75.9%, implementation details in 70.8% and architecture in 68.1% of 2,303 files; security (14.8%) and performance (14.5%) are rarely specified, and the files grow by frequent small additions like configuration code [S3].
- A catalog of six smells in AGENTS.md and CLAUDE.md files, found in 100 popular repositories, reports Lint Leakage in 62% of files, Context Bloat in 42% and Skill Leakage in 35% [S4]. The abstract does not define Lint Leakage; I read it as style rules written in prose that a linter could enforce, which is an inference.
- Instruction files do not reliably help agentic pull requests: in 15,549 agentic pull requests from 148 projects, 27.7% of projects raised their merge rate by at least 20% after adding an instruction file and 26.35% lowered it; the authors note, from a first exploration, that projects that improved had longer, more structured files [S45].
- When the file and the code disagree, agents follow the file: in 320 runs on 40 Python projects, 90.1% of choices followed the stale file, and Claude Code named the conflict in 79 of 80 runs and still followed the file [S5]. One sentence in the user-level file giving the existing code precedence raised the share of choices that follow the code from 4.2% to 91.4% [S5]. This was Python and two agents; the abstract's example conflict is print against logging and it does not say which other conventions were used, so transfer to other conventions is an inference.
- The convention can be stated in machine-checked config instead of prose: ESLint rules live in `eslint.config.js` and the tool reports the violations [S17]; Ruff ships a linter and a formatter with over 900 rules [S16]. LintCFG compiles a written coding standard into Checkstyle configs with F1 near 70% on fine-grained settings, and shows ESLint configs for generality only [S15]. Whether an agent follows a convention better from checks it runs than from prose it reads has some evidence. ContextCov compiles constraints documented in AGENTS.md into AST queries, shell shims and architectural validators; on SWE-bench Lite (300 tasks) it reached 88.3% constraint compliance, against 67.0% for prompt-only and 50.3% for LLM reflection, at 3.4 times lower feedback cost [S30]. That is one framework on one benchmark with the authors' own constraint set. Across over 5,000 Claude Code runs, random rules helped as much as curated ones (+13.8 points on a discriminative SWE-bench Verified subset), every individually beneficial rule was a negative constraint such as "do not refactor unrelated code", and every individually harmful rule was a positive directive such as "follow code style" (rules did not visibly accumulate damage in combination, 0 to 50 rules) [S31]. In 1,650 Claude Code sessions, the odds of complying with a trivial annotation convention fell about 5.6% per generated function within a session (not a constant per-step effect), while file size, position, structure and conflicting adjacent files had no detectable effect (the size and conflict nulls have Bayes-factor support; position and structure are only failures to reject; the within-session decline was found during analysis, not pre-specified) [S32].
- Reading stack facts (language, framework, commands) from manifests, lockfiles and config files instead of prose has no study in these queries; whether it beats a short context file is unsourced. The AGENTS.md format itself is a plain README for agents with dev-environment, testing and PR sections [S24]. Which hosts read AGENTS.md by default is in R5 [S27].
- Workflow tools carry their own convention documents. Spec Kit has a one-time `/speckit-constitution` step that sets principles such as code quality, testing and maintainability [S25]. Kiro steering keeps `product.md`, `tech.md` and `structure.md` (structure covers naming conventions, import patterns and architectural decisions), included in every interaction by default, with workspace files overriding global ones [S26]. Neither source measures an outcome, so the effect of these documents is unsourced. R1 judged GSD's seven-document codebase map ceremony by analogy to [S1] [S29]. In this repository `CONVENTIONS.md` holds the rules and `AGENTS.md` routes to it [S28].

## Principles

- SOLID: no study in these queries tests whether stating SOLID in a prompt or context file improves agent-written code; that part is unsourced. The one paper found tests detection: four LLMs asked to find SOLID violations in 240 examples do very differently by model, the best model still struggles with the dependency inversion principle, and accuracy falls as code complexity rises [S10]. Inference: an LLM verdict on SOLID is a weak gate.
- Functional core and imperative shell, and other principles such as immutability: unsourced as design principles for agent-written code. The one adjacent paper, FPEval (721 tasks in Haskell, OCaml, Scala and Java), finds that LLMs often write non-idiomatic functional code that follows imperative patterns and can partly self-repair with static-analysis feedback and hand-written instructions [S42]; that concerns functional languages, not a functional core inside an imperative language. No claim here that a functional core suits agents.
- Quality erosion over long tasks is measured: agents extending their own code across checkpoints show structural erosion rising in 77% of trajectories and verbosity in 75.5%; agent code is 2.3 times more verbose and 2.0 times more eroded than 473 open-source Python repositories [S7]. Explicit quality guidance cut initial verbosity and erosion by up to a third but did not change the rate of degradation [S7]. Inference: a prose rule helps the first step and does not stop drift.
- Code smells in generated code: across four LLMs on Java tasks, generated code had 63.34% more smells than reference solutions on average (73.35% more implementation smells, 21.42% more design smells), and the increase was larger for complex tasks and object-oriented topics [S8]. Prompt design and model architecture shape smell propensity [S9]. These are chat-style generation studies, not agent loops, so transfer to agents is an inference. A study of ten projects generated with Cursor (16,965 lines on average) found 1,305 CodeScene and 3,193 SonarQube design issues, mostly duplication, complexity and large methods, which the authors link to violations of SRP, separation of concerns and DRY [S50]. Optimizing non-functional quality through prompts was unstable on real patches with three LLMs [S51].
- Maintainability principles still affect cost: in minimal pairs of repositories that differ in static-analysis violations and cognitive complexity, cleanliness did not change Claude Code's pass rate across 660 trials, but agents on cleaner code used 7 to 8% fewer tokens and revisited files 34% less (33 tasks, six pairs) [S40]. This is the one sourced principle-level result found; it is about cost and navigation, not correctness.
- Structural constraints are hard to keep: as architectural and structural requirements accumulated in backend generation (80 greenfield and 20 feature tasks, eight frameworks), assertion pass rates fell by 27.28 points on average from baseline to fully specified, mid-tier models did worse in convention-heavy frameworks such as FastAPI and Django, and data-layer defects (query composition, ORM violations) were the leading root cause [S41]. The constraints were architectural patterns, databases and ORMs, not import direction or cycles.
- Passing tests overstate design quality: on 495 issues with 1,787 project design constraints from six repositories, fewer than half of resolved issues satisfied all of their design constraints, and functional correctness had negligible association with design satisfaction; issue-specific design guidance reduced violations but substantial non-compliance remained (compliance judged by an LLM verifier) [S49].
- Which principles fit is therefore a question of checkability. Import direction and cycles have tools that give a verdict [S21][S22][S23]; for complexity and duplication I read no tool docs, so that part is unsourced; SOLID and functional-core style need judgement and have only weak detection evidence [S10]. This split is my inference, not a finding.

## Keeping docs current

- Doc drift costs agents. A study of three real stale instructions (a test command, a code location, a procedure) over 732 trajectories found agents follow stale guidance when it is relevant; on the stale test command Claude Sonnet 5.5 used about two extra tool calls per run, a third more than with the corrected command; no agent repaired the instruction file; correcting the file removed operations on obsolete paths and removing it prevented most [S6]. Other cases showed no detectable difference, and only two models were tested [S6].
- A stale file is also followed over the code in the convention-conflict case: see the 90.1% result [S5]. That conflict is between a convention in the file and a convention in the code, so a resolution check would not catch it. Whether a command or path that does not resolve is worse than a missing one is not shown. [S6] is the closest: removing the stale instruction prevented most operations on obsolete paths, correcting it removed them, and leaving it stale cost extra tool calls in one of three cases.
- A check that every command, path and version in AGENTS.md resolves to the repository (H3) is deterministic and cheap. No source tests the lint itself, so its benefit is an inference from [S6]; [S5] is about convention conflicts only. A README and wiki consistency checker found stale code-element references in 23.0% of 356 repositories; the abstract presents this as evidence for AI configuration files, but the checker is a README and wiki tool and the abstract does not say it read instruction files [S33]. This repository's rule covers commands (`CONVENTIONS.md`, Generated and Managed Files) and relies on review, not a tool: no script in `tools/` resolves commands from `AGENTS.md` [S28].
- Mechanical checks for drift have thin but pointed evidence. In an exploratory six-week case study of one repository shared by three agent tools, stale documentation was the largest failure class (48 of 118 failures, 35 of them found on one audit day); of five replayed failures, only the stale-count failure came back without its check, and the check stopped it in every run (three runs per condition) [S47]. A Python prototype that fingerprints code units classified 50 changed and 17 unchanged cases correctly, where static rules snapshots detected none of the 50 stale cases (three repositories, 26 patch tasks) [S48]. Neither is a command-resolution check, and both are single-site or prototype results.
- Versions are a separate case, and I found no source on versions written in instruction files. Adjacent work is about models, not files: ten LLMs asked for Python code specified library versions in 26.83% to 95.18% of directly prompted cases, 36.70% to 55.70% of tasks carried at least one known CVE, and externally anchored version constraints substantially reduced vulnerability exposure and compatibility failures [S43]; version-conditioned code generation reached 48% to 51% for enterprise models on 328 problems [S44]. Inference: a version taken from a manifest or lockfile is a safer source than prose or model memory; whether an AGENTS.md version line drifts from the manifest is unsourced.
- LLM checks of documentation against code exist but are noisy. Plain LLM prompting flagged over 90% of functions as inconsistent; the best filtered setting flagged 14% and got an F1 of 0.77 [S14]. CASCADE reports an inconsistency only when the existing code fails a test and code generated from the documentation passes it [S13]. Both were tested on code documentation (CASCADE on Java, C# and Rust [S13]; DocPrism on Python, TypeScript, C++ and Java [S14]), not on instruction files, so use on AGENTS.md is an inference; the nearest data points are the README and wiki result above [S33] and an exploratory case study (one repository, three runs per condition) in which a monthly LLM audit of a rules repository found about half of 47 known stale statements, with at least 93% of its findings correct [S47].
- Managed blocks with hashes (H5): no vendor documents a managed block; the vendor routes to one shared file are generation, an `@` import, or committing one file to a path several hosts read [S27]. Kiro can generate its three foundation steering files from the IDE [S26]; the page I read does not say whether it rewrites them later. In this repository `AGENTS.md` has three `BEGIN`/`END` bigpowers fences, and I saw no hash in them [S28]; whether bigpowers writes hashes elsewhere is unchecked. Whether a hash prevented any overwrite of a human edit is unsourced.
- Evidence on how often these files change is mixed, and none of it says who edits them. A census of 22,854 repositories found four in five instruction sets edited after creation [S46]. Files grow by frequent small additions [S3], by +4.9 net instructions per commit and +226% over their lifetime across 1,867 repositories, with older instructions less likely to be deleted [S36]; but 73.8% of AI configuration artifacts in 441 repositories were committed once and never modified [S35], and 40.4% of 3,387 instruction files have one recorded modification [S34]. Divergent guidance across coexisting formats is a second drift risk: 16.1% of 386 section pairs differed [S34]. The same census found a third of instruction sets carry a generator-associated signature, a tool-inserted block, shared text or an AI-marked creation commit [S46]; generated or tool-written regions exist in practice, but the abstract merges four signals and does not isolate managed blocks. Whether humans or agents make the later edits, and whether a hash would protect any of them, is unsourced.

## Verdicts

- H2: refined - supported: compiler feedback raised compile and test pass rates in one system [S11], and executable checks compiled from AGENTS.md reached 88.3% constraint compliance against 67.0% for prompt-only and 50.3% for LLM reflection on one benchmark [S30]; indirect only: agents follow instructions over code even when they notice the conflict [S5] (a reason to keep facts out of prose, not a test of code-driven verdicts), a verification tool helps only where its reach covers how the work fails [S39], and model-written feedback limited self-repair in an older study [S12]; not shown: reading stack facts by command against a short context file (no study found), and context files did not raise success [S1][S2] and raised cost by over 20% [S1].
- H3: refined - the problem is evidenced: stale commands, paths and conventions in instruction files are followed (about two extra tool calls per run in one of three cases in [S6]; 90.1% of convention choices in [S5]), and a README and wiki consistency checker found stale code-element references in 23.0% of 356 repositories (not shown to have read instruction files) [S33]; the resolution check itself is untested, since no study found enforces one and measures an effect (the nearest is an exploratory single-repository case study of a stale-count check [S47]), [S5] concerns convention conflicts that a resolution check would not catch, and nothing found covers the version half of H3 (only adjacent work on model-chosen versions [S43]); the studies are small (two agents in [S5], two models in [S6]; Python only in [S5]).
- H5: refined - the need is only partly supported (instruction files grow and change often in some studies [S3][S36] and are rarely modified in others (73.8% of artifacts never modified [S35]; 40.4% of files have one recorded modification [S34]), and four in five were edited after creation in a census [S46], so how often they change and who edits them is open); the mechanism is not: no vendor documents managed blocks [S27], this repository's fences carry no hash I could see [S28], and no source shows a hash protecting an edit, so treat hashed managed blocks as ceremony until a failure shows an overwrite.

## Implications for weftwork

- Keep `AGENTS.md` about non-standard practice and omit repository overviews [S1]; keeping it short is an inference from the cost result [S1] and the Context Bloat smell [S4], and one exploratory result points the other way (improving projects had longer files [S45]). Prefer pointing to the linter config and the command over style rules in prose. This is an inference: [S4] names Lint Leakage the most common smell without showing harm, and positive directives such as "follow code style" were individually harmful in one benchmark [S31].
- Lint our own output (H3): add a check that every command and path written into `AGENTS.md` resolves in the repository, and run it in Preflight [S6][S33]. Where the file states versions, check them against the manifest or lockfile (inference [S43]). Candidate story.
- Compile the checkable conventions in `AGENTS.md` (Conventional Commits, the `Story:` trailer, YAML width) into executable checks, as ContextCov does [S30]. Where prose is needed, prefer negative constraints over positive directives, on the thin evidence of one per-rule correlation on one model [S31]. Candidate story for R10.
- Gate "done" on tool exit codes for format, lint and type check where the stack has them. This is a design choice, not a finding: [S11] measures compiler feedback inside generation, not an exit-code gate.
- Consider the one-sentence "existing code takes precedence over this file where they conflict" rule in the user-level instruction file, where [S5] tested it, and measure it on our hosts, including in a committed project file, before adopting [S5].
- Architecture tests (import direction, cycles) fit architectural constraints, whose compliance falls as structural requirements accumulate, though the leading root causes in [S41] were data-layer defects, which import rules do not check; they do not measure the concentrated complexity and verbosity that [S7] reports, which needs a complexity or duplication check whose tool docs I did not read. Which tool depends on the stack; e04s02 decides [S21][S22][S23].
- Do not rely on prose principles to stop quality drift: guidance reduced initial erosion but not its rate [S7]. R10 should measure erosion and verbosity on weftwork tasks.
- Write the code-style and test sections of `CONVENTIONS.md` after the stack choice, as a short list of commands and links to tool config, not as prose rules.

## Earns its place vs ceremony

- Context file limited to non-standard practice: earns its place [S1]; that it should also be short is an inference [S1][S4].
- Repository overview in the context file: ceremony [S1].
- Resolving commands and paths in `AGENTS.md` (H3): earns its place, as a cheap deterministic check; unmeasured as a lint [S6].
- Compiler or type-checker feedback in the agent loop: likely earns its place where the stack has it; one system, gains of up to 13% and 11% [S11].
- Linter and formatter as gates: deterministic, so likely to earn their place; measured effects exist only for static-analysis feedback on LLM generation [S37] and smell feedback in refactoring [S38], not for a plain linter or formatter as a gate in an agent loop [S16][S17][S18].
- Architecture tests: earn their place if architectural constraints lose compliance in weftwork's own tasks [S41]; ceremony until R10 measures it [S21][S22][S23].
- Executable checks compiled from `AGENTS.md` conventions: promising on one benchmark with the authors' own constraints [S30]; unproven for weftwork until R10 measures it.
- LLM-run SOLID review: unproven and weak in the one study (CodeLlama, DeepSeekCoder, QwenCoder and GPT-4o Mini; accuracy falls with complexity) [S10]; ceremony until measured on the models weftwork would use.
- LLM doc-consistency checkers on instruction files: unproven; high flag rates without filtering on code documentation [S13][S14], and one exploratory audit of a rules repository found about half of known drift [S47].
- Hashed managed blocks in `AGENTS.md`: ceremony until a failure shows an overwritten human edit [S27][S28].
- Convention documents such as a constitution or three steering files: unproven; no outcome measured [S25][S26][S29].
